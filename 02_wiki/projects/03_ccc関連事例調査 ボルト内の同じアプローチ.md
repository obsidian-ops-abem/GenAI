# ccc 関連事例調査 — ボルト内の「同じアプローチ」

> **ccc（Claude-Code-Communication）の5ロール協調・チケット駆動・階層的検証器の各軸について、ボルト内資料から同じことをしている事例12件＋補完ノード群を抽出。伝言ゲーム対策・権限の構造化・段階的移行の3点が最も応用可能。**

ccc 本体の設計は [[02_ccc-forgejo-actions自動配備]] を参照。本ページは Query 操作で抽出した ccc の周辺知見の書き戻し。

---

## ccc の構造（調査の基準）

5ロール（采/計/作/査/析）が Redmine チケットで協調し、自前 Forgejo（main保護・Forgejo Actions・自前runner）で動くマルチエージェント運用基盤。8つの調査軸:
1. マルチエージェント協調・チーム化
2. チケット/タスク駆動の協調
3. 階層的エージェント構造（orchestrator-worker / parent-child）
4. ハーネス・インフラ基盤（worktree・サンドボックス・並列）
5. エージェント間通信・メッセージング
6. CI/CD・自動配備・自律保守
7. HITL・承認ゲート・権限分離
8. Graph/Loop/Harness 3層・検証器パターン（checker/verifier/judge）

## ★ tier 1 — ccc に最も近い（複数軸で強く一致）

### 1. [[02_1チャットをエージェントチームへ Opus5 12ステップ]]
**軸: 1・3・8** — Claude Code サブエージェントで1チャットをチーム化する12ステップ。完成形は「オーケストレーター(Opus5/high) → lead → ワーカー(Sonnet5/low) ＋ verifier(Opus5/medium・仕事しなかった別役割)」の階層ツリー。
- **共通**: orchestrator-worker の階層（采→計→作に相似）、**「作った者は自分を採点しない」検証器の独立（査に一致）**、役割ごとのモデル/effortルーティング（ロール別権限・Tierに相似）、深さの構造的キャップ（ワーカーから `Agent` ツール削除＝権限剥奪）
- **相違**: ccc はプロセス内サブエージェントでなく **Redmine チケットを介したプロセス間協調**。ccc の方がプロセス分離が強く、状態外部化が徹底
- **応用**: ccc の権限分離（Tier1-3）を「ツール剥奪による構造的キャップ」で強化。検証器（査）の独立性を保証する設計の理論的根拠

### 2. [[01_エージェントファクトリの作り方 ビルダーズガイド]]
**軸: 7・8・2・6** — エージェントを工場生産する5ステーション（ジョブカード→組立→証明→認証→ブローカー）。「第2の首（毎回の出力ゲート）を機械化」「no evals, no production」。
- **共通**: **ジョブカード(ABOM)＝ccc の Redmine チケット**、ティアクランプ C0(観測)→C1(ドラフト)→C2(承認付き行動)→C3(単独行動)＝ccc の Tier1-3、証明場の封印スイート＝査の独立検証、**「自律は証拠であり自信ではない」＝ccc の根拠ベース判断**、digestチェック＝監査記録
- **相違**: ファクトリは「エージェントを認証して出荷」が目的、ccc は「継続的に協調して運用」が目的
- **応用**: ccc の Tier 分類を C0-C3 の4段階に拡張。「スキップしたチェックと合格したチェックが同じに見えてはならない」は伝言ゲーム問題対策の指針。7つの exit-1ガードは Forgejo Actions のCIゲートに直接応用

### 3. [[04_YC QM マルチプレイヤーエージェントハーネス]]
**軸: 1・5・4・7** — YC が社内で使っていたマルチエージェントハーネスをMIT公開。cron/webhookトリガー・エージェント間メモリ・共有ファイル・企業ブレインコネクタ。
- **共通**: **「会社全体（会計・法律・エンジニアリング）で動く」＝ccc の5ロール横断**、共有ファイル・メモリによる状態共有＝Redmine チケット、cron/webhook＝pushトリガーの Forgejo Actions、**「decouple the brain and hands（脳と手を分離）」＝采/計（脳）と作（手）の分離**
- **相違**: QM はクラウドファースト・Slack UI ネイティブ、ccc は自前 Forgejo・CLI
- **応用**: ccc を「エンジニアリング外」へ拡張する場合の参照アーキテクチャ。メトリクスのオントロジーは析（データ分析）ロールのガバナンス設計に直結

### 4. [[03_Graph of Loops Claude Code完全システム10リポジトリ]]
**軸: 8・3・4・2** — Graph（艦隊調整）+ Loop（信頼性）の二層を10リポジトリで構築。「**done を取り戻せるかが全10を採点する**」。
- **共通**: G1 bernstein（DAGスケジューラ・ワークツリー単位でCLI起動）＝ccc の采によるタスク振り分け、G4 insane-research の Phase6 コードゲート（モデルでなく `validate_ledger.py` が検証）＝査の独立・実装禁止、L5 claude-review-loop（第2モデル署名まで終了をブロック・最大4レビュアー並列）＝査の合格/不合格二値判定
- **相違**: 10リポジトリは技術スタックの組み合わせ、ccc は単一のRedmine+Forgejo基盤
- **応用**: ccc の「不合格時の差し戻し（done を取り戻す）」機構の実装参照。L5 の Stop hook＋複数レビュアー並列は、査の検証を並列化・強制する具体実装

## ★ tier 2 — ccc の特定の軸と強く一致

### 5. [[04_自己レビューエージェントのGraph設計 Anthropicメソッド]]
**軸: 8・7・3** — Anthropic の100万行移行を支える8ステップ。唯一の原理「**コードを直すのでなく、コードを生んだプロセスを直す**」。
- **共通**: Step1 判定器(judge)先構築＝査の二値判定、Step2 判定器をわざと壊す＝査の検証の健全性チェック、**Step6 お互いを見られない2人のレビューア（推論も履歴もなし・ルール引用強制）＝査の独立・伝言ゲーム対策**、Step5 state をディスク＝Redmine チケットへの状態外部保存、Step8 高価な操作の直列化＝采の決裁一元化
- **応用**: **ccc の伝言ゲーム問題（メタ誤り）への直接対策**。「不一致はルールブックの曖昧さ＝コイントスでなく編集」「3ファイルに3回引用されたルール＝3つの問題でなく1つの悪いルール」は、ccc の査→計→采の伝言で厳密さが失われる問題を構造的に防ぐ指針。ルールブック（rulebook.md）の運用は CLAUDE.md 相当の生きた文書

### 6. [[02_24時間自走する自律型AIエージェントの設計図]]
**軸: 7・2・6** — 24時間運用の本質は「壊れても安全に止まり、原因を残し、再開できる構造」。4層（Trigger/Workflow/Agent/Guardrail）・7原則・15チェック。
- **共通**: **状態機械（queued→...→completed/failed）＝Redmine チケットのステータス遷移**、**権限4段階（読取のみ→限定書込→承認後外部→条件付自動）＝ccc の Tier1-3**、「守られなければ困るルールは権限・コード・実行環境で守る」＝ccc の main保護・Forgejo Actionsゲート、「完全自動より安全な半自動の積み上げ」＝段階的移行（最初の5回は査が事後独立検証）
- **応用**: ccc の段階的移行（2/5完了）の設計根拠。「AIを増やせば速くなると思い込むな」は5ロール協調のコスト（引き継ぎ・状態同期・競合）を正当化。本番投入前15チェックは Forgejo Actions のCIチェックリストに転用可能

### 7. [[02_agmsg CLIエージェント間メッセージング]]
**軸: 5・1** — Claude Code/Codex/opencode 等、CLI で動く AI エージェント間でメッセージをやり取りする OSS。
- **共通**: **CLI エージェント間のメッセージパスング＝ccc の Redmine チケット介在通信**、メッセージ層と可視化層の分離、コミュニティ主導の成熟
- **相違**: agmsg はファイル・キュー等の軽量メッセージ、ccc は Redmine（重厚なチケットシステム）
- **応用**: ccc の Redmine 依存を軽量化したい場合の代替通信層。可視化ツール（agmsg-bubblelog・agmsg-tui）は5ロール間の対話を可視化する参考

### 8. [[01_Vibe Kanban コーディングエージェント用Kanbanワークスペース]]
**軸: 2・4・7** — コーディングエージェントの計画とレビューを支援する Kanban。各エージェントに専用ブランチ・ターミナル・開発サーバーを分離。核心「**差分＝引き継ぎポイント**」。
- **共通**: **Kanban イシュー＝Redmine チケット**、エージェントワークスペース分離＝ccc のロール分離、差分レビュー→フィードバック＝計によるGit管理・査による検証
- **相違**: Vibe Kanban は人間が複数エージェントを管理するUI、ccc はエージェント同士が協調。※サービス終了予定で採用リスクあり
- **応用**: 人間（采の監督者）側の UI 参照。差分を第一級オブジェクトにする思想は計のGit管理レビューの質向上

### 9. [[04_Graph Architectへの20ステップ5フェーズ]]
**軸: 3・8・7** — グラフアーキテクトへの20ステップ。orchestrator-worker（Step11）＝「ほとんどのマルチエージェントシステムの骨格」、HITL gate（Step14）＝「不可逆なものは全てこれを通す。本番ではオプションでない」。
- **共通**: orchestrator-worker＝采→計→作の階層、**validation gate（名前付き・交渉不可のチェックポイント）＝査の検証ゲート**、HITL gate＝採の決裁、**Step6「全ノードが LLM ではない（決定論的関数・validator を混ぜる）」＝析の実装禁止・査の二値判定**
- **応用**: ccc の5ロール構造を5パターン（router/orchestrator-worker/parallel fan-out/evaluator-optimizer/HITL gate）で正当化する理論枠。Phase4（信頼性）は監査記録設計の指針

## ★ tier 3 — 周辺軸と一致・補完

### 10. [[02_Loop Engineering Claude,GPT 実戦で効くもの]]
**軸: 8・7** — 実戦で効く5原則。「**接地した検証器（自己採点禁止）**」「不可逆作業前の人間チェックポイント」。
- **応用**: 査の検証を「モデルの意見の外」に置く設計の理論的根拠。4罠は査が陥り得る失敗モードの警告

### 11. [[01_LOOP vs GRAPH vs HARNESS ENGINEERING]]
**軸: 8・4・7** — 3層整理。「**自信でなく根拠でループを回す**」。故障診断表が実用的。
- **応用**: ccc の障害対応トリアージに故障診断表を直接流用。「作り手自身に採点させる」を高コストな間違いと指摘＝査の独立

### 12. [[03_AI協業の発注の型 HITL実務]]
**軸: 7・8** — 人が関与するのは「**依頼・承認・検証の3点だけ**」。3つの型＋コピペ可能なレシピ。
- **共通**: **依頼・承認・検証の3点＝ccc の 発注（計/作）・決裁（採）・検証（査）**、型③「結論を仮説に決め手ポイントだけ検証する2層レビュー」＝査の検証→採の決裁、**「個人技をチームで再現（レシピ化）」＝ccc のロール定義による属人化排除**
- **応用**: 採の決裁ポイントを「効く所だけ」に絞る設計指針

## ccc 運用への応用 — 最優先の気づき3点

### 1. 伝言ゲーム（メタ誤り）対策の出典
[[04_自己レビューエージェントのGraph設計 Anthropicメソッド]]（Step6「お互いを見られない2人のレビューア・ルール引用強制」）と [[03_Graph of Loops Claude Code完全システム10リポジトリ]]（「done を取り戻せるか」）が、ccc の未解決論点「検証済み記録が伝言で誇張される問題への構造的対策」に直接応用可能。**査の報告書に「ルール引用」を強制し、計→采への伝言で意味が変換されない構造が必要**。

### 2. 権限分離の構造的強化
[[02_1チャットをエージェントチームへ Opus5 12ステップ]]（「ワーカーの tools から Agent を削除＝構造的キャップ。設定は安全網で設計ではない」）と [[01_エージェントファクトリの作り方 ビルダーズガイド]]（「権限はモデル外で強制。プロンプトは決定に入らない」）が、ccc の Tier 分類を**プロンプトでなくツール/CIレベルで強制する**方法を示す。ccc の main保護・Forgejo Actions ゲートは既にこの方向。各ロールのツールアクセスを構造的に剥奪することで更强固に。

### 3. 段階的移行の理論的根拠
[[02_24時間自走する自律型AIエージェントの設計図]]（「完全自動より安全な半自動の積み上げ」・15チェック）と [[01_エージェントファクトリの作り方 ビルダーズガイド]]（「no evals, no production」・7日のロードマップ）が、ccc の「最初の5回は査が事後独立検証（現在2/5）」という段階的移行を正当化し、完了判定のチェックリストを提供。
