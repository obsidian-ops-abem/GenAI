# オントロジーで Claude 性能向上 — 知識グラフの実測

> **Claude Code に知識グラフ（オントロジー）を持たせ、同じ作業を「グラフあり/なし」で実測: コスト26%減・応答29%短縮・キャッシュ読取33%減。ファイル間の「書かれていない関係」を明示し、推測と探索を消す。導入は memory MCP サーバーで3ステップ・10分。**

## 一行で

@claudecode_lab による「Claude Code にオントロジー（知識グラフ）を持たせる」実践編。資料間の「書かれていない関係」を明示することで、AIの推測とファイル探索をなくし、コスト・時間・精度を全て改善する。3ステップ・10分で導入可能。

## 実測結果（核心）

同じ作業を「グラフなし（ファイル直接読取）」「グラフあり（知識グラフ参照・ファイル探索しない）」で比較:

| 指標 | 結果 |
|---|---|
| **コスト** | 約26%減 |
| **API応答時間** | 約29%短縮 |
| **キャッシュ読取トークン** | 約33%減 |

※引用元事例は「コスト半減・3倍速」だったが、筆者のリポジトリが小さいため26%減にとどまった。**リポジトリが大きいほど探索コストの割合が大きく、グラフの省略効果も大きくなる**はず。

## AIの精度が上がらない根本原因（構造的問題）

- **資料は並んでいるが、つながっていない** — order-service.md と payment-service.md がどう連携するかは**どこにも書いてない**（書き手に自明だから）。AIはこの穴を推測で埋める。だいたい当たるが5回に1回外れる
- **ある**: 情報の保存・名前付け・分類・検索
- **ない**: 情報どうしの関係と、それを辿る手段
- **資料を足すと逆に悪化する**ことも — ノイズ増・コンテキスト汚染。段ボールを増やしてもラベルがなければ探索コストが増えるだけ

## オントロジー（知識グラフ）の3要素

1. **エンティティ** — グラフの点。種類（type）付き。例: `x-collect (type: Skill)` / `browser-use (type: ExternalTool)`
2. **リレーション** — グラフの線（**最も重要**）。型付き。例: `x-collect --writes-to--> references/x-collect` / `claude-code --delegates-to--> x-article`。「関係がある」でなく「書き込む関係がある」「委譲する関係がある」と型で区別
3. **オブザベーション** — 各エンティティの短い説明（1-2行）

Claude はこれを読むとファイルを開かずに構造を答えられ、2段階以上辿れる。

## なぜ速く・正確になるか

- **スピード**: 探索が消える。グラフなしは「ファイル一覧→関係しそうなファイルを開く→読む→違った→次」の無駄ループ（外れ分もコンテキストに残る）。グラフありは「ノード検索→関係を辿る→終わり」。**ファイルを開く回数がゼロになる場面が出る**
- **精度1（推測が減る）**: 書かれていない部分を推測で埋めるが、関係が明示されると揺れが消える。日によって答えが変わるのは推測の余地が原因
- **精度2（嘘の範囲が狭くなる）**: 関係を「決められた型から選ぶ」と選択肢が有限に

## 導入手順（3ステップ・10分未満）

### 1. memory MCP サーバー追加
```
claude mcp add --transport stdio memory -- npx -y @modelcontextprotocol/server-memory
```
実体は `memory.jsonl`（1行1レコードのテキスト・読める・直せる・ブラックボックスでない）

### 2. Claude にグラフを作らせる
```
このプロジェクトを読んで、構造を知識グラフとして memory に登録してください。
```

### 3. グラフを確認
`memory.jsonl` を確認・手修正可能。

> **内部メモリ機能との違い**: Claude Code 本体の自動メモリとは別系統（同期しない）。MCP の方を使うのは管理と可読性（保存先を自分で決められる・テキストで読める・手修正可能）。自動記憶は何が入っているか確認しづらく構造もない。

## 本ボルト内の位置付け

- **「資料は並んでいるがつながっていない」** は本ボルトの構造的課題そのもの。`index.md`（カタログ）と Wikilink（関係）はあるが、**ノート間の意味関係（AはBを補完する・AとBは対立する等）が型付きで明示されていない**。オントロジー導入（リレーションに型を持たせる）は本ボルトの Lint（[[CLAUDE]] の Lint 操作）で抽出すべき「繰り返し言及されるのに専用ページがない概念」の次の段階
- **memory MCP サーバー（`@modelcontextprotocol/server-memory`）** は Claude Code への知識グラフ導入の標準手段 → [[02_Claude Code開発者ボリス推奨 MCPサーバー8選]]（MCP サーバー）・[[04_Claudeは多層実行エンジン Chatでない]]（MCP層）と同基盤
- **知識グラフ/RAG 系譜** → [[02_GraphRAG 知識グラフでRAGを置き換える]]（GraphRAG）・[[03_graphify コードベースを知識グラフ化]]（tree-sitter AST でコードをグラフ化）と同系。本記事は「プロジェクトの意味関係」をグラフ化する点で、graphify（コード構造）・GraphRAG（検索精度）の中間
- **「推測でなく明示」** は [[04_Stop Vibe Coding Spec駆動開発の5ブロック]]（曖昧さを先取り）・[[01_Agent Harness vs Loop vs Graph Engineering]]（自信でなく根拠）と同思想。オントロジーは「関係の曖昧さを先取り」する作業
- **コスト削減の実測** → [[01_知識グラフメモリをOpus5で安く運用する]]（キャッシュ/バッチでコスト圧縮）と並ぶ「知識グラフ + コスト最適化」の実践。本記事はモデル側でなく**探索の削減**によるコストダウン
- **「リポジトリが大きいほど効果大」** → [[07_Everything Fable 5 Mythosクラスとプロンプトガイド]]（長期多段階で真価・Stripe の5000万行）と同じ「規模で効く」系譜。大規模コードベースほどオントロジーの省略効果が大きい
- **本ボルト規模（中型）** は1Mコンテキスト（[[18_ULTIMATE SECOND BRAIN 第二の脳の新しい失敗モード]]）で収まる可能性があるが、オントロジーは「コンテキストに放り込む情報の質」を上げる手段として併用価値がある
