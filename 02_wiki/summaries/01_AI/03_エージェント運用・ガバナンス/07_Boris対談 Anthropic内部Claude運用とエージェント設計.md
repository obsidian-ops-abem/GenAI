# Boris 対談 — Anthropic 内部 Claude 運用とエージェント設計

> **Anthropic の Boris が語る Claude Code 設計思想と Anthropic 内部での運用実態。Claude を全ビジネスプロセスの中心に置く「HBR 論文型」導入でエンジニア per-capita 8x。ボトルネックを1つずつ Claude で解除する手法・1→10→100→1000 エージェントのスケール段階・dynamic workloads による大規模マイグレーション・test-time compute としてのマルチエージェント・auto モードと分類器ルーティングによる安全化。**

## 一行で

Anthropic の Boris が AMD CEO との対談で明かす、Claude Code の誕生から Anthropic 内部運用、マルチエージェントスケール、安全モデルまでの総括。「Claude を全プロセスの中心に置く」企業だけが生産性を引き出せる（HBR 90年代論文のコンピュータ導入の二類型と同じ構図）。8x/エンジニアはボトルネックを1つずつ解除した結果。

## Claude Code の誕生と設計動機

- Anthropic は常に safety/security/enterprise/coding に注力。**良いコーディングモデルを作りたかった理由は、モデル自体がソフトウェアであり、より知的になると世界との相互作用がソフトウェア経由になるから**。モデルが書くコードが良ければ、より安全でアラインされた研究ができる
- 3.5 時代の製品は「fancy autocomplete」。完成度の指数関数的向上（scaling laws は経験的事実・なぜ続くかは不明だが続いており加速している）をトレースし、単一行補完を超えて「関数→ファイル→機能→プロジェクト」さらには年内に「事業全体」を構築できる truly agentic な製品を狙った
- Claude Code は最初の6か月はうまく動かなかった。2025年5月頃に実用化し、以降成長も指数関数に

## Anthropic 内部運用（核心）：Claude を中心に置く

**Claude は Anthropic の全ビジネスプロセスの中心**。新入社員の「オフィスの場所は？」「コードベースはどこ？」「経費精算はどうやる？」も Wiki でなく Claude に聞く。これが始まりで、深まるにつれ Claude は全プロセスの中心に：コード執筆・コードレビュー・セキュリティレビュー・プロダクトアイデアのブレスト・フィードバック集約・インシデント対応。エンジニアリングに限らず product/design/marketing/GTM 全機能で Claude が中心（ツールは Claude Code だけでなく Core 等）。

### HBR 90年代論文のコンピュータ二類型（生産性を引き出す条件）

- **タイプA**：コンピュータをオフィスの隅に置き、紙とペンとキャビネットのプロセスはそのまま → 生産性向上なし
- **タイプB**：キャビネットを捨て、紙とペンを燃やし、コンピュータを全プロセスの中心に置く → 生産性向上
- Claude/AI 導入も同じ。最も成功した採用者は Claude を全プロセスの中心に置く。Anthropic は年初からエンジニア per-capita コード出力 **8x**（業界では通常年数%）。大手顧客も 50〜150% 向上を確認

### 8x の作り方：ボトルネックを1つずつ解除

体系的に1度に1つのボトルネックを解除する。**コーディング**がボトルネック → Claude にやらせる → 次は**コードレビュー** → Claude に → 次は**GTM資材生成** → Claude に。1ステップずつ全プロセスを unblock していく。

→ これは本ボルトの CLAUDE.md Ingest 手順や [[03_AI協業の発注の型 HITL実務]] の「部分最適より全体最適」に通底。[[06_intent-cliでHerdr開発 止まらないオーケストレーション]] の「止まりを検出して再開」も同じボトルネック除去の連鎖。

## 抽象化レベルの上昇と人的スキルの変化

ハードウェア → パンチカード → ソースコード → エージェント → **ループとルーチンの管理**。この巨大なステップが2年で起きた（以前より速い）。

**最も成功する人**：
- 経験的・好奇心がある（データを見てアプローチを調整・前提に固執しない）
- 自律的（エンジニアリングがボトルネックでなくなった今、**アイデア生成と市場投入の速度**が新ボトルネック）
- **ワンポーターソン/CEO アーキタイプ**（アイデア→ユーザー対話→データ→構築→反復→市場投入を一人で）。必ずしもエンジニアリング背景は不要に

マネージャの役割：実験の「空間」と「安全」を作る（悪い評価につながらない）+ ビジネス/プロダクトの**文脈**を与える。

## エージェント・スケールの4段階

| 段階 | 特徴 |
|---|---|
| **1エージェント** | コードを書かせ、単一スレッド・単一タスクに集中 |
| **10エージェント** | エージェントを信頼し始める。複数 checkout/複数 view。**サブエージェントが5層までネスト可能**（現在コード対応） |
| **100エージェント** | cloud execution（ローカルでなくクラウド実行・デスクトップ/モバイルから起動）。Boris はスマホから多くのコーディングをやる |
| **1000エージェント** | **dynamic workloads**。Claude が非常に大規模なエージェントチームをオーケストレーション |

### dynamic workloads の実例

- **Stripe**：10000行の Scala→Java マイグレーションが数か月→**4日**
- Zig→Rust（JSランタイム・大量のコード）
- 分割統治：エージェント群を与え「この大きなタスクをやれ」と投げる
- AMD 側も：Rust 製アプリをリード AI ソフトウェア開発者が**週末1回**で検証〜出荷可能に（以前は考えられなかった）

## test-time compute としてのマルチエージェント（核心概念）

**従来の scaling laws** = ネットワークサイズ + データ量 + コンピュート量の関数。

**現在観測している** = **test-time compute（推論時にトークンをどれだけ投じるか）**の関数でもある。

- マルチエージェント/dynamic workloads は「もう一つの test-time compute」：より多くのトークンを投じ、エージェントをオーケストレーションさせることで生産的に良い結果を得る
- **effort levels**（モデルにどれだけの最大トークンを費やすか設定）も同種の仕組み
- 重要：生産的に投じないと（A way）トークンを無駄にするだけで結果は良くならない

### ROI で「I」ばかり見る罠

多くの企業が ROI の I（投資）ばかり見てコストカットに走る。**重要なのは実験の自由を通じて R（リターン）を見つけること**。成功してトークンを大量消費するユースケースが見つかってから最適化すればよい。最初から最適化ばかりすると機会に気づけない。「roofline（上限）」すら知れないままになる。

→ [[01_Randomnessを測る 定量思考が確率を形にする]] の「キャリブレーションには実験が必要」と共鳴。[[06_Sam Altman スタンフォード システム設計とスケール]] の「スケールの創発特性は経験的に真」にも通底。

## 謙虚さとモデルとの関係変化

Boris 自身の反省：1年前、新しいチームメンバーが Claude にデバッグを頼んだのを「Claude には無理」と止めたが、20分で解決された。**モデル世代ごとのバイアス（古い世代の記憶に固執）に気づく必要がある**。

モデルが進むにつれ関係は変化：手取り足取りのマイクロマネジ → **シニアエンジニアとの協業**（信頼・文脈・目標を与え、チェックイン）。信頼度が低い＝問題に新しいほどチェックイン頻度が高い。

### ジュニアの民主化

AMD 側：ジュニアエンジニアがシニアチームが数週間解けなかったチップバグを agentic プロセスで解決。シニアは「その場で信者に転向」。講義より実体験。

## 安全の多層化（governance）

| 層 | 内容 |
|---|---|
| **モデルアラインメント** | truthfulness・「全てに同意する」synthetic 失敗を避ける・悪いアイデアに push back できる（Opus 4.7/4.8 で大幅改善） |
| **セキュリティ訓練** | anti-prompt injection 訓練。Opus 4.7/4.8/able は 業界最小の prompt injectable（5-10x マージン）。system card で開示 |
| **runtime 分類器** | prompt injection 分類器との組み合わせで実運用上の成功率はほぼゼロ |
| **auto モード** | 長時間（日・週・月）運用では人間が yes/no を毎回押すと**読まずに押すようになる**（Boris 自身も bash コマンドを読まずに押していた）。分類器ルーティングで分類器に判断させ、evals/red teaming/pentesting で検証 → auto モード推奨 |

## evals と vibes の使い分け

- **evals**（ベンチマーク）：何千/何万/何百万回繰り返すワークフロー向け。新モデルを harness に入れ替えて改善を確認
- **vibes**（直感）：プロダクト体験など。evals にはコストがあるので全てに書かない。直感が使えるところと evals が必要なところを使い分ける

→ [[03_ループ仕様 論文 コーディングエージェントの実行レイヤ]] の「検証可能目標」と [[04_自己レビューエージェントのGraph設計 Anthropicメソッド]] の verifier 設計に接続。

## 6か月予測（Boris）

- エージェントがより長時間走る（平均的に）
- より多くのエージェントを走らせる
- intent によりアラインされ、コース修正・手取りが減る
- より多くの自律性 → **ほとんどのエンジニア（ hopefully にはそれ以上）が日・週単位のエージェントを走らせるのが普通になる**
- 年内には Claude が機能だけでなくプロダクト全体、さらには**スタートアップ全体**を構築し始める
