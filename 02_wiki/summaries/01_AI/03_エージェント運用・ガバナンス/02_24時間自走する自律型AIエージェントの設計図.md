## 一行で

24時間運用エージェントの本質は「AIを増やすこと」でなく**「壊れても安全に止まり、原因を残し、再開できる構造」**。4層（Trigger/Workflow/Agent/Guardrail）への分離と、7原則・5実行環境で体系化する日本語実務ガイド。

## 核心: 作れること ≠ 運用できること

> **AIエージェントを作れることと、壊れずに運用できることは、まったく別の技術。**

モデルを高性能にしても残る問題（同一ジョブ二重実行・無限リトライ・状態未保存・コンテキスト膨張・依頼外操作・最初からやり直し・失敗理由不明）は、**モデルの知能でなく周囲の設計で決まる**。

## 全体を4層へ分ける

| 層 | 役割 | 例 |
|---|---|---|
| **Trigger** | いつ始めるか | 毎朝9時、GitHub PR、Slack絵文字、API |
| **Workflow** | 何をどの順で | 取得→重複除去→AI判断→保存→通知→承認後反映 |
| **Agent** | どこで考えさせる | 分類・重要度評価・要約・返信案・原因調査 |
| **Guardrail** | どこで止める | 同処理max3回・外部送信承認・予算超過停止・本番読取のみ・削除禁止 |

> **多くの失敗は、4層を一体化しすべてをAIへ判断させることで起きる。**
> **機械的に決められる部分をコード/ワークフローへ移し、判断が必要な部分だけをAIへ渡す。**

## まず作るのは「AIエージェント」でなく「状態機械」

24時間運用で最も重要なのは**現在の仕事がどの状態にあるかを明確にすること**。

```
queued → collecting → deduplicating → ranking → summarizing → awaiting_approval → publishing → completed
（失敗）→ retry_wait / failed / cancelled
```

> 状態が会話の中にしか存在しない設計では、**セッションが切れた瞬間に現在地を失う**。
> AIに長い記憶を持たせるより、**仕事の状態を外部へ持たせること**が先。

## 長時間運用で壊れる5つの理由

1. **コンテキストを「永続記憶」と勘違い** —— 情報が増えるほど重要制約が埋もれる。現在地と次行動を外部保存
2. **圧縮会話への依存** —— Compaction は有効だが情報損失あり。重要情報（設計理由・却下候補・承認内容・正確な数値）は会話の外へ
3. **テキストルールを「強制装置」として使用** —— 文章は方針であって制限でない。**守られなければ困るルールは権限・コード・実行環境で守る**
4. **失敗時挙動の未決定** —— ❌「成功するまで再試行」✅「一時エラーのみmax3回、待機30s/2m/10m、認証/権限/入力不備は即停止、3回失敗でfailed＋Slack通知」
5. **AIを増やせば速くなると思い込む** —— 引き継ぎ・状態同期・重複・競合状態のコスト増。**最初は1体の順次WFで十分**

## 壊れにくくする7原則

| # | 原則 | 要点 |
|---|---|---|
| 1 | **AIへ渡すのは「判断」だけ** | 決定的処理（取得/重複削除/JSON保存）=コード、非決定的（重要度/要約/返信）=AI。**担当範囲が狭いほど改善容易** |
| 2 | **各工程に「完了条件」** | 入力・出力・完了条件を定義。AIの「できました」でなく**システム側で判定** |
| 3 | **状態を外部保存** | セッション落ちを前提。重要は会話再現でなく**現在地復元** |
| 4 | **冪等性で重複防止** | 各ジョブに `idempotency_key`。副作用（送信/公開/課金/削除）には必須 |
| 5 | **リトライに上限と種類** | 3種（再試行可/人間確認要/再試行禁止）。max回数・待機・コスト上限・通知先・再開方法を決める |
| 6 | **権限は最小限から** | 4段階（読取のみ→限定書込→承認後外部→条件付自動）。**完全自動より安全な半自動の積み上げ** |
| 7 | **Hookと監視で「守る・見る・止める」** | 危険コマンド停止・編集後検証・連続実行検知・作業記録・外部操作前承認。**人間が後から理由を説明できること** |

## 5つの実行環境（用途で選ぶ）

| 環境 | 向き | 特徴 |
|---|---|---|
| **/loop** | その場で試す短時間監視 | セッション内、定期タスクは**7日で終了**、実験環境 |
| **Claude Routines** | PCを閉じても定期実行 | Anthropicクラウド、最小間隔**1時間**、無人で承認不可→権限最小限、リサーチプレビュー |
| **Modal/Trigger.dev** | AI判断不要を安定回し | Modal=Python/バッチ、Trigger.dev=TS/長時間WF/ステップ再試行。**AIを1部品として組み込み** |
| **Claude Agent SDK** | 自作アプリへ組み込み | 頭脳とループのみ提供。**「SDK使えば24時間動く」ではない**、運用体制は自作 |
| **Managed Agents** | 実行基盤管理を減らす | Anthropic管理/セルフホスト サンドボックス、長時間・非同期・ステートフル、ベータ |

> **絶対守らせたい処理がある → Hooks/権限制御/実行環境分離（どの方法でも追加）**

## 最初は「1時間・1体・1業務」

初心者が最初から作るべきは巨大AI組織でなく: 実行1時間以内・エージェント1体・業務1つ・外部書込は下書きのみ・再試行max2-3回・公開前は人間承認必須。

5段階の積み上げ: ①取得してSlack通知（AI判断なし）→ ②AI重要度＋要約（公開しない）→ ③X下書き（人間確認）→ ④承認投稿のみ予約 → ⑤実績十分な一部だけ自動。

> いきなり全自動にすると、**取得・判断・生成・公開のどこで壊れたか分からない**。

## 本番投入前15チェック（一つでもNOなら完全自動不可）

ユニークID / 二重実行防止 / 状態外部保存 / 途中再開 / 完了条件 / AI出力検証 / リトライ上限 / タイムアウト / コスト上限 / 読取書込権限分離 / 削除公開課金は承認制 / 同一ツール連続検知 / 失敗時通知 / ログ事後確認 / 緊急停止可能。

## 金言

- **「一度も止まらないことではなく、壊れても安全に止まり、原因を残し、正しい地点から再開できること」**
- **「守られなければ困るルールは、プロンプトではなく権限・コード・実行環境で守る」**
- **「AIの担当範囲が狭いほど、テストと改善が簡単」**
- **「コンテキストは思考のために使い、状態管理はシステムへ任せる」**
- **「完全自動より、安全な半自動を積み上げた方が結果的に早く本番へ到達」**
