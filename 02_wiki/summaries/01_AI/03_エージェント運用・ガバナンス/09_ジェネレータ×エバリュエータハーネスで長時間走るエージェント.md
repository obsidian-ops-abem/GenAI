# ジェネレータ×エバリュエータ・ハーネスで長時間走るエージェント

> **Anthropic Claude Code チーム（Ash & Andrew）によるハーネス設計の解説。エージェントが長時間走る3つの障害（context/planning/output generation）と、Claude Code 1年の歴史。核心は GANs から拝借した generator-evaluator の adversarial 構造。エバリュエータは Playwright で実際にアプリを操作して採点。プランナーを加えた3役（PM/IC/QA）、done の事前交渉、27の契約基準。Opus 4.6 で単一セッション+compaction が可能になりハーネスは簡素化。5つのテイクアウツ。**

## 一行で

Anthropic のエンジニアカンファレンスで Claude Code チームの Ash と Andrew が語る、長時間（時間・日単位）走るエージェントのハーネス設計。Claude Code の1年史（bash を書くのがやっと→日単位で自律）を振り返った上で、**GANs の generator-discriminator 構造をエージェントに持ち込んだ adversarial evaluator パターン**を核心に据える。「自己評価は罠。adversarial evaluator を使え」。

## 長時間走る3つの障害（Andrew・導入）

| 障害 | 内容 |
|---|---|
| **context** | コンテキスト窓の制限・深くなるほど低下する一貫性・窓の終端に近づくと急いで終わろうとする「context anxiety」 |
| **planning** | モデルは箱から出してすぐには計画が得意でない。1ショットで全部やろうとする/半分作って止める/コンテキストを使い切って未完成アプリを残す |
| **output generation** | （直感に反して）モデルは自分の出力の生成が本当に苦手。半分実装された機能を見て「できた」と言う/ボタンはあるがバックエンドがない |

解決の2軸：**モデル（重みに焼き込む）** と **ハーネス（モデル周のスキャフォールド）**。minimal scaffold で50%タスク完遂できる時間は 0.3.7 で約1時間→0.4.6 で12時間（1年で12倍）。

## Claude Code の1年史（Andrew）

- **Sonnet 3.5**：初めてコーディングで有望。artifacts で自分の出力を verify できるように
- **computer use pre-release**：クリック・スクショ・自己テスト
- **MCP spec**：ツール使用
- **Feb 2025 / Claude Code リサーチプレビュー**（Sonnet 3.7）：「開発者が Claude をコーディングにどう使うか理解し、将来のモデル改善に活かす」が目的（実験的）
- **May 2025**：Opus 4 / Sonnet 4・コンテキスト管理とタスク完遂が向上・Claude Code GA・**Claude Code SDK（ハーネス）公開**
- **rAL loop**（Geoffrey Huntley・2025年7月論文）：プロンプトを Claude Code CLI に流し込みループで完遂まで回す。計画→タスク選択→新規セッション（fresh context）で作業。Claude 公式プラグインは単一セッション内で compaction に頼る版（「真の rAL でない」との批判も）
- **Boris** の言葉（Claude Code 1周年）：「1年前は bash コマンドと文字列エスケープで苦労し20分が限界。今は Claude Code のほぼ全てが Claude Code で書かれ、日単位で走る」

## 核心：generator × evaluator の adversarial 構造（Ash）

**GANs（generative adversarial networks）から拝借**：generator（構築）と discriminator/evaluator（採点）の間に adversarial pressure を置く。

- **コンテキスト窓・システムプロンプト・役割を完全に分割**
- evaluator は diff を読むだけでなく **Playwright で実際にページを開き・クリックし・試して** critique を generator に返す
- 対比：多くの人が「1つのコアエージェントに自分の作業をチェックさせる」やり方

### なぜ evaluator も LLM なのにハルシネーションしないのか

**鍵のアイデア**：evaluator は LLM で LLM 出力を好むバイアスがあるが、**standalone critic を厳しく調整するのは非常に扱いやすい**。一方 **builder を自己批判的に調整するのはそうではない**。

人間の比喩：美術作品や食事を批判するのは容易だが、自分で描く/自分を批判するのははるかに難しい。**LLM の critic 能力と generator 能力のギャップを利用**。

→ [[04_自己レビューエージェントのGraph設計 Anthropicメソッド]] の「judge を先に構築・わざと壊す」と同じ問題意識。本講演はその Claude Code チーム内部の実践詳細。

### テイストを採点する（design taste）

「テイストは採点できない」と言う人が多いが、**十分に強い意見を持ちそれを書き下せば採点できる**。

4つの採点基準（rubric）：
1. **design**（重み大）
2. **originality**（重み大）
3. **craft**
4. **functionality**（Opus 4.6 では既に十分なので相対的に重み下げ）

問題：紫のグラデーション・「AI slop」的な美的の防止。参照サイトで few-shot 校正。

### ピボット能力（単一ループとの差）

generator がある基準（例: originality）で詰まると、**evaluator は全体を捨てて最初からやり直す**。単一パスやループでは同じものを patch し続ける。長期間にわたるコース修正能力は、役割を分割した構造特有。

## プランナー追加：PM/IC/QA の3役

もう1役 planner を加え、1行プロンプトを **意図的に高レベルな spec（スプリント群）** に分解。

- **granular な技術詳細は計画しない**（誤りが全スプリントに波及し時間単位で誤差が拡大するため）
- これは **PM / IC (=generator) / QA (=evaluator)** のアーキテクチャ。発明でなく「各役割に独自のコンテキスト窓を与えた」

### done の事前交渉（key innovation）

generator が1行書く前に、**2エージェントが「done とは何か」を交渉**：
- generator「X 機能を作る。Y でテストして検証すべき」
- evaluator「スコープが大きすぎる。テストが弱い。XYZ のエッジケースが抜けている」
- ファイルオンディスクで往復（一方が書き、他方が読んで反復・両者が合意するまで）
- 合意後に構築開始。**evaluator は元の spec でなく、2者が決めた契約に対して採点**

→ [[04_Stop Vibe Coding Spec駆動開発の5ブロック]] の spec 駆動と [[03_AI協業の発注の型 HITL実務]] の「受け入れ基準」をエージェント間で自動交渉させた形。

## 実例：retro game maker

同じプロンプト・同じモデルで、ソロループ vs ハーネスを比較：

| | ソロ（ハーネスなし） | ハーネスあり |
|---|---|---|
| 見た目 | シンプルだが無難。スプライトエディタのカラーピッカーが黒四角だけ | retro forged と自分流に命名・新規プロジェクトダイアログ・54色パレット（プロンプトにない） |
| 機能 | プレイモードで矢印キー/スペースキーが効かない。スコア・体力が動かない | 物理 loop が走り矢印キーで移動・城壁に衝突。デバッグ HUD |
| AI 機能 | （企図すらされない） | プランナーが「AI 機能」と言及しただけで、アプリ内の AI レベルアシスタント（「お城を作って」と指示）が完成 |
| コスト/時間 | — | 200ドル・6時間 |

evaluator が実際にゲームを起動してプレイしたからこそ判明したバグ：FastAPI ルート順序・delete キーの boolean ロジックバグ等。**契約基準は27項目**（ granularity が findings を実行可能にする。曖昧基準→曖昧批判→generator が肩をすくめる）。

## Claude の QA 能力の罠と修正

**箱から出した Claude は本当に悪い QA エージェント**（sycophancy/generosity bias）。早期実行ではバグを見つけても「後で直す・2週間かかるかも」で済ませていた。

→ **トレースを読むのが主デバッグループ**。実験を増やすのでなく、agent が実際に何をしたかを読み、人間の判断と分岐した場所を見つけ、プロンプトを調整。スタックトレースを読むのと同じ稽古。ツールティップ：agent トランスクリプトをファイルに書き出し、別 agent に読ませてプロンプトを更新させる（ループを閉じる）。

## ハーネスはモデル進化で簡素化する（重要）

「harness design は死んだか」議論に対し Ash の答え：**各モデルの spiky な挙動を掴み、ハーネスで隙間を埋める**。

| 項目 | Opus 4.5 | Opus 4.6 |
|---|---|---|
| context reset | 必要（context sensitivity 高） | 不要（1M窓 GA・単一セッション+compaction で足りる） |
| sprint evaluation | 真面目に意見を持たなかったが超重要 | 2時間連続ビルドを一貫して保持・1機能ずつ強制しなくてよい |
| evaluator の実行頻度 | 毎スプリント | ワンショット生成の終わりだけ |

**「ハーネスが間違っていたのではなく、4.5 に対しては正しかった。frontier は移動する」**。簡素化版でもほぼ半額で同等の長時間走行。

### ファイルシステムを状態の source of truth に
長時間実行 agent では線形コンテキストでなく **ファイルシステムを sharded state に**使うことを推奨。

## 5つのテイクアウツ（Ash・最重要スライド）

1. **自己評価は罠**。adversarial evaluator を使え
2. **compaction ≠ 一貫性**。lossy summary は本当に drift。**構造化された handoff と clean context** が良いパターン
3. **主観的品質は読めないと思わない**。強い見解があれば書き下せ（アプリ品質に巨大な差を生む）
4. **モデルのトレースに向き合え**。そうして初めて scaffold の何を消し何を残すかが分かる（特に frontier が動くとき）
5. （暗黙）ハーネスの各部は「正しかった/間違っていた」でなく「そのモデルに対して正しかった」と評価する

## Q&A の要点

- **evaluator の再利用性**：特定アプリに特化させたら自分でプロンプトするのと変わらない。汎用パターン（design taste 等）を抽出し再利用
- **dumb zones / smart zones**（コンテキスト位置による性能差）：モデルが良くなり一時的な問題になりつつある。Opus 4.6 で単一セッション+compaction が可能に
- **Playwright MCP の推奨**：browser control には Playwright MCP または computer use MCP。「作業を見守りたい」は trust gap。トレースを読んで信頼に至るまでが初期段階。Opus 4.6 では vision がネットワークエラー・コンソールエラー・要素の重なりまで読める

## 所感

「自己評価は罠。adversarial evaluator を使え」は、[[08_Claudeを会社にする 42スキルの組織図]] の Average Person コメント「LLM verifier は2人目の楽観主義者。gate は違う」と完全に一致。Anthropic 自身が内部でこの問題に取り組んでおり、解が「standalone critic を厳しく調整する（generator を自己批判的にはしない）」。done の事前交渉（ファイル往復で合意形成）は、本ボルトの CLAUDE.md Ingest 手順（原典→要約→index/log の順で処理）と同じ「合意後に実行」の精神。frontier が移動するたびに scaffold のどの部分を削れるかを見極めるには、トレースを読む稽古が不可欠という結論は、長時間運用の本質を突く。
