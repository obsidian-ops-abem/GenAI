# 1チャットをエージェントチームへ —— Opus 5 の12ステップコース

> **「アップグレードとはエージェントを増やすことではない。高価なモデルがファイル検索でなく決定にトークンを使い、厄介なことはすべてあなたが読まなくていいどこかで起きること」** — Claude Code サブエージェントのチーム化を12ステップで教える実践コース。

出典: [[30_1チャットをエージェントチームへ Opus5 12ステップ（出典）]]（Rody @0x_rody, 2026-07-30。本文はユーザー提供クリップから再構成）

---

## 一行で

Claude Code のサブエージェントで**1つのチャットをチームに変える**12ステップ。最初のワーカーから3階層ツリーまで、**各層でのモデル/effortルーティング・深さの構造的キャップ・検証器**までを具体例付きで示す。

## 核心: なぜチームが単独セッションに勝つか

| 単一チャット | サブエージェントチーム |
|---|---|
| 読んだすべてを抱える（行き止まり・捨てファイル・誤迂回が残る） | 独自のコンテキスト窓・システムプロンプトで走る |
| ノイズが本題と注意を争う | **ノイズがあなたの会話に触れない** |
| 高価なモデルがファイル検索にもトークンを使う | 高価なモデルは**決定**だけに集中 |

> 2レベルで「ノイズのノイズ」もあなたから遠ざかる。

Anthropic のネスト調整: 6月（深さ5上限）→ **7月21日 全面無効化** → 3日後に**デフォルト深さ3**で復帰。

## 12ステップ（4フェーズ）

### Phase 1: 最初のサブエージェント（Step 1–3）

- **Step 1**: サブエージェントは「長いプロンプト」でなく**厄介さを持ち帰らせない別コンテキスト窓**
- **Step 2**: `.claude/agents/` に frontmatter 付き markdown 1ファイル（`name`/`description`/`model`/`effort`/`tools`/`maxTurns`）
- **Step 3**: 最小の仕事（検索・チェック・要約）を与え、**大きいものを作る前に1回の完全実行を見る**

### Phase 2: チームにする（Step 4–6）

- **Step 4**: タスクではなく**ワークストリーム（領域）で分ける** —— API / テスト / ドキュメント
- **Step 5**: **ファイルに触れないオーケストレーター**（分割・委譲・組み立てのみ）
- **Step 6** ★金のレバー: **役割ごとにモデル/effortをルーティング**

```bash
export CLAUDE_CODE_SUBAGENT_MODEL=claude-sonnet-5  # 安いデフォルト
```
→ frontmatter で必要なものだけ昇格: **オーケストレーター=Opus5/high**（決定が伝播）、**ワーカー=Sonnet5/low**（機械的）

> ツリー全体を1設定で走らせるのが、チームが**良くならず高価になる**道。

### Phase 3: 深さと制御（Step 7–9）

- **Step 7**: ワークストリームが**2度分割する時だけ**中間層(lead)を置く。受け取った曖昧さをそのまま下に渡すleadは不要
- **Step 8 ★重要**: 構造的に深さをキャップ —— **ワーカーの `tools` から `Agent` を削除**（そのツールなきサブエージェントは何もspawnできない）。`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` は安全網で設計ではない
  - **罠**: allowlist構文はメインスレッド時のみ適用、ネスト内では**暗黙無視** → 安全境界にするな
- **Step 9**: 全定義に `maxTurns`（機械的=8、オーケストレーター=30）

### Phase 4: 品質と規模（Step 10–12）

- **Step 10 ★**: **仕事をしなかった検証器**を置く —— 元の要件に対してチェックする別役割。作った者は自分を採点しない。`verifier`（Opus5/medium、pass/fail/unclear＋証拠）
- **Step 11**: stream-json ＋ `--forward-subagent-text` で**1回の完全実行を見る**。さもないと深い作業は終わるまで不可視
- **Step 12**: **チームを刈り込む** —— ほとんどは2階層で十分。高価なモデルは最上位のみ

> **Depth 3 is a ceiling, not a target.**

## よくある5つの間違い

1. 2階層の仕事に3階層を構築（余分な層＝プロンプトOH＋引き継ぎロス）
2. 1モデル・1effortをどこでも（ファイル検索にオーケストレーター料金）
3. ワーカーのtoolsに `Agent` を残す（**構造的制限が設定に勝る**）
4. 検証器なし（チェックせず転送するleadは中継でしかない）
5. 完全実行を一度も見ない（**チームは引き継ぎで静かに失敗する**）

## 20分セットアップ

1. ワーカー1ファイルを書き実際の検索タスクで実行（6分）
2. `Agent` を持つオーケストレーター追加（5分）
3. サブエージェントモデル環境変数を安いデフォルトに（2分）
4. ワーカーから `Agent` 削除で深さ2にキャップ（1分）
5. `--forward-subagent-text` で1タスク実行しトレース全体を読む（6分）

## チーム構造の完成形（推奨）

```
オーケストレーター (Opus5 / high / Agent持つ)
├── lead (必要な時だけ / Sonnet5 / Agent持つ)
│   ├── ワーカー (Sonnet5 / low / Agentなし = 構造的キャップ)
│   └── ワーカー
├── ワーカー
└── verifier (Opus5 / medium / 仕事しなかった別役割)
```

## 金言

- **「アップグレードとはエージェントを増やすことではない」** —— 高価なモデルが決定にトークンを使い、ノイズが読まなくていい所で起きること
- **構造的制限 > 設定** —— ワークツールから `Agent` を削除する方が環境変数より確実
- **作った者は自分を採点しない** —— 検証は別役割（→ [[02_Loop Engineering Claude,GPT 実戦で効くもの]] の「接地した検証器」と同じ原則）
