# Boris Cherny 講演 — Claude Code ハーネス設計と product overhang

> **モデルは「設計対象」でなく「生き物」。新モデルが出る毎にシステムプロンプトの80%を削除し、ハーネスを一から再構築する。product overhang（モデルの能力を製品が邪魔している状態）を解放（unhobbling）することが、Claude Code 自身の誕生秘話であり次世代製品の機会。Bun の Zig→Rust 書き換え（11日・プロダクション採用）と、Claude Code 自身の自律ルーチン保守がその実証。**

出典: [[61_Boris Cherny 講演 Claude Codeハーネス設計とproduct overhang（出典）]]（Boris Cherny 講演の音声書き起こし。本文はユーザー提供トランスクリプトから主題別に再構成）

## 一行で

Claude Code リードエンジニア Boris Cherny が、ハーネス（Claude Code）の設計思想・モデル毎の再構築・product overhang・dynamic workflows・ルーチンによる自律保守を語る。核心は「**経験主義でモデルに向き合い、足場を削って難しいタスクを任せよ**」。

## 1. プロンプトインジェクション耐性（Opus 5 / Fable 5）

- **Opus 5 はプロンプトインジェクションできない**（「信じられないほど」）。1年前なら悪意あるインターネット指示に従った
- 3層で実現: ① well-trained モデル（3年の学習研究）② プロンプトインジェクション分類器（**因果メカニズム解釈性** — 発火するニューロンを脳内で直接観察）③ AutoML 分類器
- ハーネス・エージェント・製品設計に大きく影響（[[04_Claudeは多層実行エンジン Chatでない]] の Safety 層）

## 2. システムプロンプトの80%削除 — モデル毎のハーネス再構築

- **新モデルが出る毎に**システムプロンプト・ツール群・ツールのプロンプトを削除・追加・変更（モデル毎に挙動が全く異なるため）
- Opus 5 は知的なので「モデルが知っているべきだが知らなかった挙動の修正」の多くが不要に → **80%削除**
- **simple mode**（非公式）: 環境変数 `CLAUDE_CODE_SIMPLE=1` で全システムプロンプト削除。**プロンプトなしの方がモデルは少し賢く**なる
- 再構築手順: ①削除 → ②使う（推測しない）→ ③同じ箇所で繰り返し躓いた時だけ追加し戻す（モデルは毎回読むため本当に必要か確かめる）

> **モデルは設計対象でなく生き物。世代毎に性格が違い、時間をかけて知り、ハーネスを調整する。理論でなく経験科学。** → [[06_Context Engineering Claude Codeの文脈設計]]・[[02_Claude Code 計画と実行を分けるワークフロー]] の実践版

### eval の扱い
コード・プロンプトは削除すべきだが **eval は定数で追加し続ける**。ただし eval も飽和して捨て・作り直しが頻繁（モデル向上が急速なため）。

## 3. product overhang — モデルの能力を製品が邪魔している

| 概念 | 意味 |
|---|---|
| **product overhang** | 現モデルができる（製品化されていない）能力 |
| **hobbling** | 製品がモデルの能力を邪魔すること |

**事例（初代 Claude Code）**: 3.5 は当時最高のコーディングモデルだったが、当時の製品は「1行補完・読み取り専用チャット」程度。関数全体・ファイル全体を書く能力があったのに製品が邪魔していた。Claude Code は「足場を全部取り除き最もシンプルなハーネス」を与え、能力を解放した → [[02_Claude Code開発者ボリス推奨 MCPサーバー8選]]（Boris の3原則）と同源

**現代にも product overhang が巨大にあり、スタートアップが取り込めていない**。

### unhobbling の2方針

**① 難しいタスクを任せる**（自分ができると思っているより難しいもの）
- ❌ よくある誤り: 過剰に具体的指示（「こうして、1→2→3→4」）
- ✅ より高レベルに — タスク・目標・制約を記述し、モデルに任せて戻る。6ヶ月前は通用しなかったが今は通用する → [[04_Stop Vibe Coding Spec駆動開発の5ブロック]]（spec で過剰指定を避ける）と対比

**② 実験し創造的に遊ぶ**
- 例: OpenCV を Opus 5 に渡して絵を描かせる（ポートレート・動物・風景）。訓練していないのに、正しく頼めばできる。遊んでいて偶然発見

## 4. 具体例: Bun の Zig→Rust 書き換え（11日・プロダクション採用）

- Claude Code は Bun（JSランタイム・Zig 製）上で動く。Zig は手動メモリ管理でリーク問題
- Jared がテストスイートを定義し、**1プロンプト・dynamic workflow で11日間走らせ Zig→Rust へコードベース全体を書き換え**
- 人間の最良エンジナでも1年以上（10万行超・JSランタイムは超複雑）
- **プロダクション採用** — 現在 Claude Code が動くのはこの Rust 版
- 教訓: 実用問題があり前モデルでできなくても、最新モデルならできるかもしれない。**投げ続けよ**

## 5. Boris 自身の実験: Electron→Swift 書き換え（15日以上・実行中）

Claude Tag（Swift 版 Claude）で「Electron アプリを Swift に書き換え、Mac 仮想マシンで両者を走らせピクセル比較せよ。終わるまで止まるな」→ **15日以上実行中**。派手な工夫は不要。**タスク＋検証手段を与えればモデルは進む**。Claude は自発的に Slack チャンネルを作り進捗スクショを投稿し始めた。

## 6. トップ1%の Claude ユーザになる方法

> **「LinkedIn インフルエンサーや Twitter を読むな。『1つの奇妙なトリック』は存在しない」**

1. 注意深くタスクを与える（自分がやるより少し難しめに）
2. 仕事を検証するツールを与える（自分がやる時と同じように）
3. どこで躓くか観察する
4. より良いプロンプト・スキル・MCP で修正

**長年のコード経験があるエンジニアほど過剰指定する**（モデルに「自分と同じやり方」を強要）。モデルは同僚のように扱う — それが今の知能水準。→ [[03_CLINEに全部賭けろ コーディングエージェント時代のプログラマ]]（ドライバー席を譲る）と通底

## 7. dynamic workflows とルーチン — 新しいテスト時計算

### dynamic workflows
- 1タスク（コードベース書き換え・超深度分析・複数段階機能）を多数エージェントに分割
- 第1パス→検証/要約の第2パス→再分析の第3段…と**生産的にオーケストレーション**（関数型プログラミング発想: 逐次・並列の道具を用意）
- **スケーリング則に対する新しいテスト時計算の編成** — 数千エージェントを生産的・効率的に

### loops と routines
- **loop**: ローカルで走る Claude
- **routine**: クラウドポッドで走る Claude
- dynamic workflows が「1タスクをチャンク分割」なら、loops/routines は「反復タスクを繰り返す」（毎時・5分毎・毎日）

## 8. Claude Code が Claude Code 自身を保守（自律ルーチン）

Claude Code チームは **Claude Code 自身で Claude Code を保守**。毎日多数のルーチンが CI・iOS・Android・デスクトップを含むコードベースを維持:

- **デッドコード掃除**（毎日・1文プロンプト・指示していないのに静的/動的解析を自分で考え PR を出す）
- **出し尽くした実験の削除**（100%ロールアウト後コードベースから削除）
- **テストカバレッジ不足箇所へのテスト追加**
- **不要テストの削除**（古いモデル/人が追加した無意味テスト）
- **「abstraction please」** — 大規模コードベースで散在するほぼ重複の抽象化を毎日全コードベース横断で見つけ統一

毎日数十〜数百（時には数千）エージェントが走り、かつては数十〜数百人のエンジニアが必要だった作業をこなす。完全自動化へ途上。→ [[18_ULTIMATE SECOND BRAIN 第二の脳の新しい失敗モード]]（nightly compiler・保守をエージェントへ）のソフトウェア版

## 9. 優れたビルダーの資質 — 先入観を捨てる

- **経験的** — モデルについて学んだこと・CS理論を忘れ、モデルを見て試し躓きを見て調整する
- **先入観（priors）を捨てる** — 以前うまくいかなかったことも再び試みる
- 理論科学でなく経験科学

## 10. 学生への助言 — 実践から入る

Boris は中学で TI-83 電卓の BASIC を学んだ（数学テストでズルするため・クラスメートにシリアルケーブルで配布）。**プログラミングは常に実践的**。CS だけでなく応用（スタートアップ・製品・デザイン・ビジネス感覚・データサイエンス・ユーザと話す）を学び、組み合わせたところに価値がある。「**まず自分が欲しいものを作り、次にレベルアップして人々が欲しいものを作れ**」
