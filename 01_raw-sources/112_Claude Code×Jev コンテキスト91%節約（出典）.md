# 原文（@yama_threads の X ポスト全文・構造化）

約100万トークンあったClaudeのセッションを、わずか1秒で86Kまで圧縮する。Alex Volkov氏がJevで実測した数値として、TypeSafe AIの「Jev Engineering」ガイドに記載されている実績です。削れた割合は約91%。トークン代が安くなったのは、モデルのグレードを落としたからではありません。**そもそも「生成」させるのをやめたから**です。

## Jevとは何者か
- TypeSafe AI の「System 1（直感的・瞬間的な判断）」モデル。構造化した状態と選択肢を渡すと、型付きの回答と確信度だけを返す。**文章は1文字も書きません**
- 質問の型は3つ: **Choice**（最大255選択肢から1つ）／**Score**（スコア付け）／**Noul**（可否ゲート）
- 価格: 入力$0.042/百万トークン・出力課金なし。1判断1,000トークン換算で**1万回の判断が約42セント**（公称値）

## まず「よくある節約論」を疑う
「安いモデルに切り替えればいい」は半分しか合っていない。下手に切り替えると**長いプロンプトのキャッシュが破棄され逆に高くつく**罠。本当のコスト漏れは:
- **文脈（コンテキスト）が肥大化し続けること**
- **ちょっとした「判断」のために生成モデルを何度も呼ぶこと**

この2つは価格の問題でなく**設計の問題**。

## 「要約」と「選別」の決定的な違い
従来のコンテキスト圧縮=「要約プロンプト」（生成・遅い・情報欠落リスク）。Jev は履歴エントリごとに関連度をスコアリングし無関係なものだけ削る。**文章の書き直しは一切しない**。
> "Compaction is not a summarization prompt. It is a relevance filter."（圧縮とは要約プロンプトではなく、関連性フィルターである）

フィルターは「判断」→1秒。生成なら1分。**コンテキストを後から掃除するのではなく、最初から散らかさない**。

## 具体手順（3ルート）
1. **Playground で1問だけ**: 状態を貼り「この履歴エントリは現在のゴールに関連するか？」を Noul で。コード不要
2. **外部スクリプトで手動**: セッションログを読み込み、エントリ単位で Score。閾値未満を削って書き戻す
3. **Hook で自動化**: コンテキスト量が一定を超えたら自動フィルター。※閾値を厳しすぎると必要な前提情報まで落ちる

回答がおかしい時の修正対象は「モデル」でなく「状態（渡すデータ）」。ガイドにも **"the fix is almost always the state, not the model"** と明記。

## 圧縮より先にやる「2層の防御」
Jev Engineering ガイド第8ステップの「ルータ」と「ゲート」:
- **上層（ルータ）**: タスクに応じて適切なモデルへ振り分け
- **下層（ゲート）**: 危険なツール実行を事前にストップ（rm -rf を含む Bash・force push・本番への接続文字列）

「このコマンドは安全か？」の判定に高価な LLM は不要（「生成」でなく「判断」だから）。**コンテキストに入ってから削るより、入る前にゲートで弾く方が事故コストは圧倒的に小さい**。

## 踏みがちな落とし穴
- **定額プランでの「節約」は金銭コストでない** — 得られるのは「使用枠の温存」と「レスポンス速度向上」。月額請求は変わらない
- **Jev 側の利用料は別途発生** — トータルでお得かは利用量次第
- **公称値は一例** — 「1秒で86K」は報告事例。万能な数字でない
- **「選別」で情報が落ちる** — 削られて困る前提は state として明示的に渡し直す設計が必要

## 目的別アプローチ
- 長いセッションを軽くしたい → Score で関連度フィルター
- 危険なコマンドを止めたい → Noul で安全性判定（ゲート）
- 次の担当を決めたい → Choice でディスパッチ

> **「判断はJev、生成はLLM、実行はコード」**この3分割の設計思想こそが、エージェント構築の骨格

## 今日まずやること
「Playground で1問だけ投げる」。返ってきたレスポンスに「文章が1行も含まれていない」を見た瞬間、役割分担の必要性が腑に落ちる。ツールや価格は変わるが、**「生成と判断を分ける」という設計の本質は変わらない**。
