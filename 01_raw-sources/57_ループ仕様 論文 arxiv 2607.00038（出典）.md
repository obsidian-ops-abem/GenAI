# 本文（再構成）

## コーディングエージェントのための「欠けていた実行レイヤ」

> この論文、めっちゃぶっ飛んでる。コンピュータサイエンスの論文が、コーディングエージェントのための**欠けていた実行レイヤー**として**ループ仕様（loop spec）**を定義している。

### ループ仕様の4要素

再利用可能なループ仕様は以下をバンドルする:
1. **明示的なトリガー**（explicit trigger）
2. **検証可能な目標**（verifiable goal）
3. **停止ルール**（stopping rule）
4. **メモリ**（memory）

これらが**手動のステップバイステッププロンプティングを排除**する。

### ループエンジニアリングの中身

- ループエンジニアリングが**人間の手取り足取りを自動化された検証ラダーで置き換える**
- 実世界のループの **70%** が以下を用いて**自律ゾーン**で実行される:
  - **決定論的チェッカー**（deterministic checkers）
  - **明示的な終端状態**（explicit terminal states）
  - **メイカー・クリティック分割**（maker-critic split）

### 手動プロンプティング → 境界付き自己修正ループ

ほとんどの開発者は今でも実行のあらゆるステップでコーディングエージェントを手動でプロンプトしている。このフレームワークは**手動プロンプティングを境界付き自己修正エージェントループで置き換える**。

## コメント欄の洞察

- **@Systeo16**: "explicit stopping rule" が実際に必要だった部分。Hermes がサブタスクでループし、曖昧な終端状態にヒットし、"done" の共有契約がなかった。台帳制約として手書きしたが、正式名があるとは知らなかった
- **@jurlycat**: loop spec の角度は興味深いが、非決定論的な agent 挙動を実践的にどう扱うか疑問。spec は LLM がまだ持っていない多くの制御を前提としている
- **@saen_dev**: loop spec はよりクリーンな抽象化だが、事前に検証可能な目標を定義できることを前提にしている。オープンエンドな研究タスク（done がどう見えるか分からない）ではどうか?
- **@milessy_bc**: ほとんどの agent デモは、誰もいつ止めるか教えないとき壊れる
- **@biektive**: 新しい agent 論文はすべて「モデルに自分で採点させるのをやめろ」という別の言い方に過ぎない
- **@sindikitil**: 計画と実行の間の欠けていたピースのように感じる。ほとんどの agent は "what next" を行き来するだけで、done までループしない
