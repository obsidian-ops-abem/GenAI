# 本文（再構成・日本語原文保持）

## 核心テーゼ

> **AIエージェントを作れることと、壊れずに運用できることは、まったく別の技術です。**

理想（朝になればニュース整理・X下書き・問い合わせ分類・コードレビュー）だけ見れば、AIエージェントは24時間働く社員に見える。しかし長時間動かすと多くの人が同じ壁にぶつかる: 数時間後から判断ズレ、同じ処理の反復、複数エージェントの同一作業、誰が何を担当か不明、失敗しているのに処理継続、API料金だけ減少、人間の監視が必要。

24時間自走の本質は、AIを増やすことではない:

> **一度も止まらないことではなく、壊れても安全に止まり、原因を残し、正しい地点から再開できること。**

## 最初に結論: 24時間運用は「AIの賢さ」ではなく「システム設計」で決まる

モデルを高性能に変えても残る問題: 同一ジョブ二重実行、外部API落ちで無限リトライ、成功/失敗状態未保存、過去会話膨張で判断不安定、依頼外操作、途中落ちで最初から、失敗理由の事後確認不可。**これらはモデルの知能でなく周囲の設計で決まる。**

## 全体を4層へ分ける

### 第1層: Trigger（いつ始めるか）
毎朝9時 / 1時間ごと / GitHub PR作成時 / フォーム送信時 / Slack絵文字 / API呼び出し

### 第2層: Workflow（何をどの順番で）
情報取得 → 重複除去 → AI判断 → 結果保存 → 人間通知 → 承認後外部反映

### 第3層: Agent（どこで考えさせるか）
分類 / 重要度評価 / 要約 / 返信案 / 原因調査 / 次行動候補選択

### 第4層: Guardrail（どこで止めるか）
同じ処理最大3回 / 外部送信は承認制 / 予算超過停止 / 本番は読み取りのみ / 削除禁止 / 失敗時通知 / タイムアウト

> **多くの失敗は、4層を一体化しすべてをAIへ判断させることで起きる。**
> 「毎朝ニュース集めて重要度判断し記事書き画像生成しX投稿し反応見て改善」は一見理想だが、決まった手順・創造的判断・外部書き込み・繰り返し・評価・改善・公開権限が全部混在。
> **機械的に決められる部分をコード/ワークフローへ移し、判断が必要な部分だけをAIへ渡す。**

## まず作るべきは「AIエージェント」ではなく「状態機械」

24時間運用で最も重要なのは、**現在の仕事がどの状態にあるかを明確にすること**。

ニュース収集エージェントの状態遷移:
```
queued → collecting_sources → deduplicating → ranking → summarizing → awaiting_approval → publishing → completed
（失敗時）→ retry_wait / failed / cancelled
```

状態が定義されていれば、エージェントが途中停止しても「どこまで終わったか・次に何を・再実行可否・人間確認必要か」を判断できる。

> 反対に、状態が会話の中にしか存在しない設計では、**セッションが切れた瞬間に現在地を失う**。
> 24時間動かすなら、AIに長い記憶を持たせるより**仕事の状態を外部へ持たせること**が先。

## AIエージェントが長時間運用で壊れる5つの理由

### 理由1: コンテキストを「永続的な記憶」と勘違いする
長時間動かすと会話・ツール結果・ファイル・エラー・修正履歴が増える。情報が増えるほど: 重要な制約が埋もれる、新旧状態が混ざる、解決済問題を再調査、過去の誤推測が残る、無関係情報が判断へ影響。

最低限、次の状態を外部保存:
```json
{
  "job_id": "news-2026-07-30",
  "workflow_version": "1.2.0",
  "status": "ranking_completed",
  "current_step": "summarizing",
  "processed_items": 42,
  "selected_items": 5,
  "retry_count": 0,
  "cost_usd": 0.84,
  "next_action": "generate_summaries",
  "updated_at": "2026-07-30T09:18:00+09:00"
}
```
> 会話の流れを覚えていることより、**現在地と次の行動が保存されていること**の方が重要。

### 理由2: 圧縮された会話へ依存する
Claude Code の Compaction（圧縮）は有効だが、要約には必ず情報損失がある。特に消えやすい: なぜその設計を選んだか・どの候補を却下したか・一時的例外条件・未完了作業・担当範囲の境界・正確な数値やID・失敗した試行・人間が承認した内容。

**外部へ保存するもの**: ジョブ状態 / 完了済み工程 / 未処理項目 / 重要な意思決定 / エラー履歴 / 成果物保存先 / 承認履歴 / 実行コスト / 使用入力データ識別子。

> **コンテキストは思考のために使い、状態管理はシステムへ任せる。**

### 理由3: テキストルールを「強制装置」として使う
CLAUDE.md に「本番を絶対変更しないで」と書くのは大切。しかし**文章は方針であり、物理的な制限ではない**。本当に書き込ませたくないなら:
- 読み取り専用の認証情報
- 書き込みツールを渡さない
- 対象ディレクトリを制限
- **Hookで危険操作をブロック**
- 実行環境を分離
- ネットワーク接続先を限定

> **守られなければ困るルールは、プロンプトではなく権限・コード・実行環境で守る。**

### 理由4: 失敗したときの挙動を決めていない
正常手順だけ考え失敗時を決めていないエージェントは必ず止まる。ニュースAPI失敗時: すぐ再試行か / 何秒待つか / 最大何回か / 一部取得なら続けるか / 人間通知か / 次回持ち越しか。

- ❌ 悪い設計: 「失敗したら成功するまで再試行してください」
- ✅ 良い設計: 「一時的通信エラーのみ再試行。待機30秒・2分・10分、最大3回。認証/権限/入力不備は再試行せず停止。3回失敗で failed へ変更し、エラー内容・最終成功工程・再開方法を Slack 通知」

> AIに判断させる前に、**エラーの種類と停止条件を決める**。

### 理由5: AIを増やせば速くなると思う
役割を分けると立派なAI組織に見えるが、エージェントを増やすと増えるコスト: 引き継ぎ / 状態同期 / 重複作業 / 出力形式調整 / コンテキスト複製 / 権限管理 / 失敗箇所追跡 / 実行コスト / 競合状態。

独立並列化できる仕事なら有効。前工程を待つ仕事を無理に分けると引き継ぎコストが大きくなる。**最初は1体が小さなワークフローを順番に進める設計で十分。**

複数エージェントへ分けるのは次の条件を満たす場合だけ: 作業が明確に独立 / 同時に進める意味 / 入出力形式固定 / 失敗作業だけ再実行可能 / 権限を役割ごとに分離 / 同じデータを同時更新しない / コスト増に見合う時間短縮。

## 壊れにくいAIエージェントを作る7つの設計原則

### 原則1: AIへ渡すのは「判断」だけにする
処理を2種類へ分ける:
- **決定的な処理**（同じ入力なら同じ結果）= コード/ワークフロー: API取得、日付絞込、重複削除、JSON保存、Slack通知、ファイル名変更、集計、スキーマ検証
- **非決定的な処理**（文脈を読み判断）= AI: 重要ニュース選択、切り口考案、問い合わせ意図分類、コード問題分析、返信文作成、複数案から最適選択

AIニュース収集の構造: `[コード]RSS取得 → [コード]重複削除 → [AI]重要度評価 → [AI]上位5件要約 → [コード]JSON検証 → [コード]Notion保存 → [コード]Slack通知`
> **AIの担当範囲が狭いほど、テストと改善が簡単。**

### 原則2: 各工程に「完了条件」を持たせる
「ニュースを調べる」では終わったか判定できない。工程ごとに入力・出力・完了条件を定義。
- リサーチ工程の完了条件: 5媒体確認済 / 過去24時間のみ / 重複除去済 / 最低10件 / 取得時刻と出典URLあり
- 要約工程の完了条件: 上位5件 / 各200文字以内 / 事実と推測分離 / 元URL保持 / JSON適合 / 重要度理由記載

> 完了条件があれば、AI自身の「できました」でなく**システム側で判定できる**。

### 原則3: 状態を外部へ保存する
24時間運用では**セッションが落ちることを前提にする**。状態保存先: 小規模=JSON/SQLite、チーム=PostgreSQL、長時間WF=Trigger.dev、クラウド=サービス側履歴。

> 重要なのは会話を再現することではなく、**仕事の現在地を復元できること**。

### 原則4: 重複実行を「冪等性」で防ぐ
各ジョブに一意の `idempotency_key` を持たせる（例: `news-summary:2026-07-30`、`invoice-reminder:customer-123:2026-07`）。
処理開始前の確認: completed→何もしない / running→既存状態を返す / failed→再開条件確認 / 未作成→新規開始。
> 特に**送信・公開・課金・削除**のような副作用がある処理には必須。

### 原則5: リトライに上限と種類を持たせる
エラーを3種類へ分ける:
- **再試行してよい**: 一時的ネットワーク障害、レート制限、サービス一時停止、タイムアウト、5xx
- **人間の確認が必要**: 入力意味が曖昧、想定外形式、仕様不一致、品質基準未満、AI判断低信頼
- **再試行してはいけない**: 認証無効、権限不足、対象不存在、禁止操作、予算上限超過、入力値不正

必ず決める: 最大試行回数 / 待機時間 / 累計コスト上限 / 失敗時通知先 / 再開方法。
> 「一時エラーのみ最大3回、待機30秒・2分・10分、同じツール呼び出し5分以内3連続で停止、累計$3超で停止、停止時は Slack 通知」

### 原則6: 権限は最小限から始める
24時間動くエージェントは人間が見ていない時間にも操作するため、対話型より厳しい権限設計が必要。
最初から渡してはいけない: 本番データ削除、無制限外部送信、任意シェル実行、全リポジトリ書き込み、決済購入、SNS無承認投稿、機密情報広範アクセス。

段階的に権限を広げる:
- 段階1: 読み取りのみ（下書き保存）
- 段階2: 限定された書き込み（専用フォルダ/ブランチ/下書きチャンネルのみ）
- 段階3: 承認後の外部操作（公開・送信・マージ）
- 段階4: 条件付き自動実行（運用実績十分・ロールバック可能な処理のみ）

> 最初から完全自動より、**安全な半自動を積み上げた方が結果的に早く本番へ到達**。

### 原則7: Hookと監視で「守る・見る・止める」を仕組みにする
Claude Code の Hooks は、モデルへお願いするのでなく**決定的な処理として実行できる**点が価値。
- 例1: 危険コマンド停止（`rm -rf`・本番DB直接操作・強制push検知でブロック）
- 例2: 編集後に検証（formatter・lint・型チェック・テスト自動実行）
- 例3: 同一処理連続実行検知（短時間反復で停止・通知）
- 例4: 作業記録保存（完了時に実行内容・変更ファイル・検証結果をログへ）
- 例5: 外部操作前に承認（送信・公開・削除前に停止・人間確認）

最低限記録: 開始時刻 / 入力データ / 使用ツール / 出力結果 / エラー / リトライ回数 / 実行コスト / 承認者 / 状態遷移。
> 運用で重要なのは「成功したか」だけでなく、**人間が後から理由を説明できること**。

## 実践例: 毎朝AIニュースを届ける自律型エージェント

> 毎朝8時にAIニュースを収集し、重要度高の5件を要約して Slack へ届ける

- **Trigger**: 毎日8:00
- **Workflow**: ①記事取得 ②24時間以内のみ ③重複削除 ④AI重要度評価 ⑤上位5件要約 ⑥JSON検証 ⑦Notion保存 ⑧Slack通知
- **AIが判断**: ニュース重要度 / 読者関連性 / 要約 / 注目理由
- **コードで固定**: 記事取得 / 日付フィルタ / 重複削除 / JSON検証 / Notion保存 / Slack送信 / ジョブ状態更新
- **Guardrail**: 取得0件で停止 / AI評価は最大1回 / JSON不正時のみ最大2回再生成 / Slack送信は1ジョブ1回 / 1回上限$2 / 元URLなき要約は送信しない
- **失敗時**: 通信エラー→最大3回 / 認証エラー→即停止・Slack通知 / 記事0件→warning通知で終了 / JSON不正→最大2回再生成 / Slack送信失敗→要約は保存し送信工程だけ再実行

> 工程を分ければ、AIが失敗しても**全体を最初からやり直す必要はない**。

## 24時間動かす方法は用途によって選ぶ

### 1. /loop —— その場で試す短時間の繰り返し
開いているセッション内でプロンプト定期実行。`/loop 10m PRの状態を確認し...`
- 向き: デプロイ監視、ビルド確認、短時間ポーリング、試作
- 不向き: PCを閉じても継続したい処理、数週間以上の永続、厳密時刻の基幹、完全無人本番
- 現在公式docでは定期タスクは**作成から7日で終了**。永続には Routines や Desktop スケジュール。**本番運用の完成形でなく実験環境**。

### 2. Claude Routines —— PCを閉じても動く定期・イベント実行
Anthropic 管理クラウド環境で Claude Code 処理を実行。スケジュール/API呼び出し/GitHubイベントがトリガー。
- 向き: 毎朝情報収集、Issue定期整理、PRレビュー、デプロイ後検証、ドキュメント差分監視、通知
- **無人実行のため承認ダイアログに答えられない** → リポジトリ/push権/コネクタ/ネットワーク/環境変数/外部サービス権限を最小限へ
- 現在リサーチプレビュー、定期実行**最小間隔1時間**。短間隔なら /loop、即時反応なら API/GitHub トリガー。

### 3. Modal・Trigger.dev 等 —— 決まったワークフローをクラウドで回す
AI判断がほとんど不要なら Claude Code 常時動かす必要なし。
- **Modal 向き**: Python中心、バッチ、データ処理、必要時だけ計算、AI以外中心
- **Trigger.dev 向き**: TypeScript中心、長時間WF、ステップ単位再試行、ジョブ状態追跡、イベント駆動
- AI判断が必要な工程だけ API/Agent SDK を呼ぶ。**AIを一つの処理部品として組み込む**。

### 4. Claude Agent SDK —— 自分のアプリ内でエージェントを動かす
Claude Code のエージェントループ・ツール利用を自作 Python/TypeScript アプリへ組み込む。
- 向き: 自社サービスへ組み込み、独自UIから動かす、自インフラでジョブ管理、ツール/権限の細かい制御、複雑WFのコード化
- **「SDKを使えば24時間動く」ではない**。SDKは頭脳と実行ループを提供。24時間運用の身体と運用体制は自分で作る。

### 5. Managed Agents —— 実行基盤の管理を減らす
Anthropic が実行基盤を提供。モデル/システムプロンプト/ツール/MCP/Skills を定義し、Anthropic管理 or セルフホスト サンドボックスでセッション実行。
- 向き: 長時間・非同期エージェント、サンドボックス自管理したくない、セッション/イベント履歴保存、APIから起動、再利用可能設定
- 現在ベータ、データ保持/コンプライアンス要確認。
- **Agent SDK との違いは「誰が実行基盤を管理するか」**。細かい制御なら SDK、基盤管理減なら Managed。

## 結局どれを選ぶべきか

| 目的 | 選ぶもの |
|---|---|
| その場で試したい | **/loop** |
| PCを閉じても定期実行 | **Claude Routines**（1時間以上/API/GitHub） |
| AI判断不要を安定回し | **Modal/Trigger.dev/通常クラウドWF** |
| 独自アプリへ組み込み | **Claude Agent SDK** |
| 実行基盤まで管理してほしい | **Managed Agents** |
| 絶対守らせたい処理がある | **Hooks/権限制御/実行環境分離**（どの方法でも追加） |

## 最初のAIエージェントは「1時間・1体・1業務」で作る

初心者が最初から作るべきは巨大AI組織でなく:
- 実行時間: 1時間以内
- エージェント数: 1体
- 対象業務: 1つ
- 外部書き込み: 下書きのみ
- 再試行: 最大2〜3回
- 人間承認: 公開前に必須

5段階の積み上げ:
1. ニュース取得し候補を Slack へ（AI判断なし）
2. AIが重要度付け・上位5件要約（外部公開しない）
3. AIがX投稿下書き（人間確認）
4. 承認投稿だけ予約登録
5. 運用実績十分な一部だけ自動実行

> いきなり全自動にすると、取得・判断・生成・公開の**どこで壊れたか分からない**。

## 本番投入前に確認する15項目

1ジョブに一意ID / 二重実行防止 / 現在状態を外部保存 / 途中から再開 / 各工程に完了条件 / AI出力形式を検証 / リトライ上限 / タイムアウト / コスト上限 / 読取と書込権限を分離 / 削除・公開・課金は承認制 / 同一ツール連続実行検知 / 失敗時通知 / 実行ログ事後確認 / 人間が緊急停止可能。

> **一つでも答えられない項目があるなら、まだ完全自動へ進める段階ではない。**

## コピペで使えるAIエージェント設計プロンプト

```
次の業務を、長時間運用できる自律型AIエージェントとして設計してください。

## 対象業務
[自動化したい業務]

## 目的
[最終的に実現したい成果]

## 設計方針
すべてをAIへ任せず、次の4層へ分けてください。
1. Trigger  いつ、何をきっかけに開始するか
2. Workflow  決まった順序で行う工程
3. Agent  判断、推論、生成が必要な工程
4. Guardrail  権限、停止条件、承認、コスト制限

## 必ず設計するもの
- 各工程の入力と出力 / 各工程の完了条件 / 状態遷移 / 外部に保存するジョブ状態 / 冪等性キー
- 再試行可能なエラー / 再試行してはいけないエラー / 最大リトライ回数 / タイムアウト / コスト上限
- 同一処理の重複防止 / 人間の承認が必要な操作 / ログと通知 / 停止後の再開方法 / 緊急停止方法

## 制約
- 最初はエージェント1体で設計する
- 決定的な処理はコードまたはワークフローへ移す
- AIは判断が必要な工程だけに使う
- 削除、公開、送信、課金、本番変更は自動許可しない
- 会話履歴だけを状態管理に使わない
- 失敗時に無制限リトライしない

## 出力形式
1.全体構成 2.状態遷移 3.処理フロー 4.AIへ任せる部分 5.コードで固定する部分
6.状態管理 7.冪等性設計 8.エラー・リトライ設計 9.権限設計 10.監視・通知
11.適した実行方法 12.小さく始める実装手順 13.本番投入前チェックリスト
```

## まとめ

最強のAIエージェントは、止まらないエージェントではない。

> **異常を検知して安全に止まり、原因を残し、必要な地点から再開できる存在です。**

まずは1体に、1つの業務を、1時間だけ任せる。そして成功したかより先に確認: 失敗したら止まれるか / 何をしたか追跡できるか / 同じ処理を重複しないか / 途中から再開できるか / 人間が安全に引き継げるか。ここまでできて初めて「任せられるAIエージェント」。
