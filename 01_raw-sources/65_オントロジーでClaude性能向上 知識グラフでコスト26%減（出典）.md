# 原文（@claudecode_lab の X ポスト全文・構造化）

第1回ではオントロジーという概念そのものを扱いました。今回は実践編です。Claude Codeに知識グラフを持たせる手順を示したうえで、まったく同じ作業を「グラフあり」「グラフなし」で1回ずつ実行し、コストと時間とトークンと中身を比較します。

結論を先に置きます。**コストは約26パーセント減、API応答時間は約29パーセント短縮、キャッシュ読み取りトークンは約33パーセント減**でした。

## 用語整理

### オントロジー
**ある領域に登場する概念と、概念どうしの関係を、機械が読める形で明示的に書き下したもの**。元は哲学の用語（存在論）。情報科学では Tom Gruber の「概念化の明示的な仕様」という定義が有名。やっていることは単純 — 「AとBはこういう関係にある」という頭の中にしかない了解を、外に取り出して文字にする。新しいデータを作るのでなく、すでにあるデータに意味の層をかぶせる作業。

### 知識グラフ
オントロジーを、点と線のネットワークとして表現したもの。実務上はオントロジーとほぼ同じ意味。

### エンティティ（entity）
グラフの点。登場する要素そのもの。種類（type）を付けて登録。
例: x-collect (type: Skill) / browser-use (type: ExternalTool) / articles/industry (type: OutputStore)

### リレーション（relation）
グラフの線。要素どうしの関係。**ここが最も重要**。
例: x-collect --writes-to--> references/x-collect / x-collect --uses--> browser-use / claude-code --delegates-to--> x-article
線に名前が付いているのが要点。「関係がある」ではなく「書き込む関係がある」「委譲する関係がある」と型で区別。

### オブザベーション（observation）
各エンティティに添える短い説明（1-2行）。
例: x-collect: 指定トピックでXをバズ順検索し上位20件を保存する

### MCP（Model Context Protocol）
AIと外部ツールをつなぐための共通規格。知識グラフを持たせるときも MCP 経由でサーバーを追加。Claude Code 本体にも内部記憶機能があるが別系統（同期しない）。MCP の方を使うのは管理と見た目の分かりやすさが理由（保存先を自分で決められる・テキストとして読める・間違いは手で直せる）。

## AIの精度が上がらない理由（構造的問題）

### 資料は並んでいるが、つながっていない
order-service.md と payment-service.md がある。どちらも丁寧。しかしこの2つがどう連携しているかは**どこにも書いてない**（書き手に自明だから）。AIはこの穴を推測で埋める。だいたい当たるが5回に1回外れると、その1回が「なんか今日は調子が悪い」の正体。
- **ある**: 情報の保存・名前付け・分類・検索
- **ない**: 情報どうしの関係と、それを辿る手段

### 資料を足すと、かえって悪化することがある
不安になって関連ファイルを追加するとノイズも増える。長いマルチターンではコンテキストが汚れ精度が落ちる。段ボールを増やしてもラベルがなければ探索コストが増えるだけ。

## AIに関係を入れるとは（3つだけ）

1. 登場する要素を、種類を付けて登録する（エンティティ）
2. 要素どうしのつながりを、型を付けて登録する（リレーション）
3. 各要素に短い説明を足す（オブザベーション）

Claudeはこれを読むと、ファイルを開かずに構造を答えられる。2段階以上辿れる。「references/x-collect を読むスキルは何か」から「そのスキルの成果物はどこに出るか」まで線を辿るだけで到達。

## なぜ速くなり、なぜ正確になるのか

### スピード向上：探索が消える
グラフがない状態: ①ファイル一覧取得 ②関係しそうな名前のファイルを開く ③読む ④違った。次を開く ⑤3-4を繰り返す ⑥ようやく揃う。②〜⑤が無駄になる可能性を含み、外れだった分も全部コンテキストに残る（トークン・時間消費）。
グラフがある状態: ①関係するノードを検索 ②周辺の関係を辿る ③終わり。**ファイルを開く回数がゼロになる場面が出る**。応答時間29%短縮はここから。

### 精度向上1：推測が減る
書かれていない部分を必ず推測で埋める。関係が明示されるとその揺れが消える。同じ質問なのに日によって答えが変わる現象は推測の余地が残っていることが原因。

### 精度向上2：嘘をつける範囲が狭くなる
関係を「決められた型から選ぶ」形にすると選択肢が有限になる。

## Claude Codeにオントロジーを入れる手順（3ステップ・10分未満）

### ステップ1：memory MCPサーバーを追加する
```
claude mcp add --transport stdio memory -- npx -y @modelcontextprotocol/server-memory
```
グラフの実体は `memory.jsonl`（1行1レコードのテキストファイル・中身は普通に読める・ブラックボックスでない）。初回起動時に「Pending approval」と出たら承認（最初の一度だけ）。

### ステップ2：Claudeにグラフを作らせる
プロジェクトを読ませて構造を知識グラフとして memory に登録させる。
```
このプロジェクトを読んで、構造を知識グラフとして memory に登録してください。
```
memory に entities（種類つき）と relations として記録。

### ステップ3：グラフを確認する
memory の中身（`memory.jsonl`）を確認。テキストファイルとして読める・間違いは手で直せる。

## 実測：同じ作業を2回やってみた

- **条件A（グラフなし）**: MCPメモリを使わずファイルを直接読んで解析
- **条件B（グラフあり）**: 登録済み知識グラフを情報源とし、ファイル探索は基本的に行わない

### 結果
- **コスト約26%減**
- **API応答時間約29%短縮**
- **キャッシュ読み取りトークン約33%減**

引用元の事例では「コスト半減・3倍速」だったが26%減にとどまった。理由は私のリポジトリが小さいからかと考えられる（リポジトリが大きいほど探索コストが占める割合が大きく、グラフの省略効果も大きくなるはず）。
