# 前半: ADK Go で仮想試着室＋スタイリングエージェント

## 二つのユーザージャーニー
1. **仮想試着室**: 商品の「Virtual try on」→自分の写真を選択→服装を着た画像を生成（写真差し替え可）
2. **スタイリングフロー**: 「特別な機会・目的地」を送信→アウトフィット候補カルーセル→フィードバックで調整→「Add to Bag」で一括カート投入

## アーキテクチャ
- **Flutter**（Web/iOS/Android クロスプラットフォーム）+ **Go バックエンド**（単一バイナリ・Cloud Run・全部 ADK）・プレーン HTTP で接続
- **4エージェント協調**: フィッティングルーム／スタイリング（フロントから直接呼ばれる）→カタログ（両者から委譲される）・スタイリングは画像生成ツールを直接使用可能

## サービス共通の3ステップ
1. **Session**: 会話履歴の追跡。試着は毎回新規セッション、**スタイリングは同一セッションIDを再利用**（フィードバックを覚えて洗練）
2. **Run**: POST で name/session_id/message。message の parts 配列に text（指示）と inline_data（base64画像）
3. **Artifacts**: **大きな画像をレスポンスで直接返さず GCS へ保存し参照名のみ返す**→フロントが GET で取得。「軽く・速く・予測可能」

## ADK とは
- Google の OSS。Gemini を「質問に答えるだけでなく行動するエージェント」へ。**生モデル呼び出しと本番対応システムの違い**を埋める: ツール呼び出し・マルチエージェント調整（委譲）・セッションとメモリ（永続コンテキスト）・デバッグUI
- エージェントのループ: メッセージ受信→考える（ツール呼ぶ/委譲する/直接応答）→返す
- **共有state（key-valueストア）で協調**: 試着エージェントが生成画像の artifact 名を state に書き、スタイリングが読む。**直接通信なし・state が共有メモリ**
- Runner が全実行。**callbacks**（フック）: before/after tool 等。ユーザー画像を自動で artifact 保存しデバッグUIに表示
- エージェント型: LLM agent（標準）／Custom／Workflow（sequential/parallel/loop）
- 実装: main.go で構築し launcher へ。各エージェントは独立 Go パッケージ。**instructions.md を分離し Go の embed で読み込み**（コード中の巨大文字列回避）
- **カタログエージェント**: list_products（YAML読み・実DBでも可）+ get_product_image ツール
- **試着エージェント**: fitting ツール（Gemini 2.5 Flash Image）+ load_artifacts + **カタログエージェントを agent_as_tool でツール化** + before_model_callback でユーザー画像を artifact 保存
- **スタイリングエージェント**: 同じツール・**指示だけが違う**（イベント/場所に合う商品を検索）

## Flutter 側
- 宣言型（UI=stateの関数）+ Provider で state 管理。**UIとビジネスロジック、データソースを分離（MVVM）**
- 試着画面=3状態のステートマシン（写真選択/ローディング/結果表示）。スタイリングはスワイプ可能カルーセル+フィードバックチャットバー（**AnimateSwitcher で状態遷移をアニメーション**）

# 後半: ADK 2 ラボ（Anyuan）— グラフ・コラボレーティブ・ダイナミック

## 出発点: メガプロンプトの問題
- 全指示を1つのプロンプトに入れる単一エージェントは機能する場合もあるが、**複雑ワークフローには最適でなく信頼性に欠ける**
- モデルは非決定的で指示通りの順序を保証できない。外部接続なしでは事実を作り上げる（ハルシネーション）
- 改善第1歩: **ツール**（決定的ロジックを追加・幻覚削減）

## ADK1 vs ADK2
- ADK1 にも sequential/parallel/loop + ルーティングエージェントあり
- **ADK2 グラフの優位性**:
  1. **排他的ルーティング**: モデルに解釈させるのでなく**コードでルールによる分岐**
  2. **join ノード**: 並列実行の同期・結果集約（バリア）
  3. **functional ノード**: fetch/validate/format 等の**決定的ロジック**（ツールより柔軟）
  4. **ハイブリッドシステム**: agent ノード＋functional ノードを混在→決定的は functional/ルーター、非決定的は agent。**信頼性と柔軟性と制御**
- 例: fetch_condition を agent にさせる→トークン消費・信頼性低・コスト増。**functional にすれば LLM 呼び出しゼロ**

## 並列ファンアウト＋join＋戦略エージェント
- fetch_weather / analyze_course / fetch_fitness を**並列 function ノード**で実行→**join で統合**→**戦略 agent のみが AI**（入力 schema を指定）
- 「**ワークフロー全体が決定的。AI に依存するのは戦略 agent だけ=トークン大幅節約**」
- join の役割: バリア＋結果の schema 保証（ADK2.5 で実際のノードに）

## ルーター（決定的 vs 非決定的）
- **決定的ルーター**: 温度>78→hot 戦略 / <40→cold / それ以外 normal。**明確なルールがあるなら決定的が信頼性高い・安い**
- **非決定的（AI/LLM）ルーター**: ロジックを指示に書きモデルの推論に任せる。**エッジケースが多い・条件を列挙しきれない時に柔軟**。実務では**重い推論モデルをルーターに使わない**（遅いため）
- 判断基準: ルーティング戦略の見当がつくか／サブエージェント設計の概形があるか

## コラボレーティブパターン（3モード）
デモ: レース戦略の質問→専門家（geo/栄養/天気…）から**モデルがサブセットを選び並列実行**
- **chat モード**（デフォルト）: **制御をサブエージェントへハンドオフ**。会話は移り、親は自動復帰しない。**並列実行できない**
- **single-turn モード**: サブエージェントを**ツールとして wrap**。制御を渡さず**並列実行が可能**。ただし**一方向で人間入力不可**
- **task モード**: single-turn に似るが**一時停止して人間の入力を待てる**（例: 靴のサイズを聞く→入力→**同一セッションで全コンテキスト保持のまま再開**）
- chat は「会話のハンドオフ」／single-turn は「ツールのチーム」／task は「human-in-the-loop 可能なツール」

## ダイナミックワークフロー
- **事前に木構造が不明な問題**（ディープリサーチ: 「この人について知っていることを全て」）
- **実行時に木を生成**: トピック分解→サブ質問に dynamic fan-out→さらに再帰
- **再帰の深さを制限可能**（max depth／幅=サブ質問数）。深さ制限で無限展開を防ぐ
- 判別方法: parallel に dynamic 指定があるか・構文警告

## いつ何を使うか（まとめ）
- 単純なら ADK1 の sequential/parallel で十分（**グラフは必須でない。単一エージェントが最適な場合も・AI 不要が最適な場合も**）
- **事前にフローを描ける** → グラフ（functional＋ルールベースルーティング）
- **インテントベース・チーム・人間入力** → コラボレーティブ（モード使い分け）
- **木構造が事前に分からない** → ダイナミックフロー（実行時生成・再帰）
