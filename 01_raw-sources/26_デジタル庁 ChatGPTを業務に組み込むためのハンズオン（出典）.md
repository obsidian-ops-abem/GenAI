# 本文（スライドテキスト抜粋）

## 導入：アイデアの価値は「検証」してみないとわからない（p.2, 46）

- 「Microsoft でテストされたアイデアのうち、改善を示すメトリクスを実際に改善できたのは3分の1にすぎない」(Microsoft社元Vice President)
- 「もしあなたが実験主導のチームにいるなら、70%の仕事が捨てられることに慣れてください」(Slack社Director)
- 一方で「アイデアの価値を見積もることは難しい。年間1億ドルの価値ある単純な変更が何か月も遅れていた」こともある
- **要するに、作って終わりではない。が、作らないと話にならないので、さっさと作りましょう**
- 出典: A/Bテスト実践ガイド「真のデータドリブンへ至る信用できる実験とは」

## ChatGPT と GPT API の関係（p.3）

- GPT3.5/GPT4 はモデル直接配布なし（GPT-2のみ公開）
- ChatGPT = Webアプリ経由、GPT API = API経由。**ChatGPTの方が制約が大きく、APIの方ができることが多い**
- ただし API による ChatGPT の完全再現は困難

## このスライドの目的（p.4–5）

ChatGPT的な処理を既存業務フローに組み込む設計を自在にできるようになること。具体例：
1. 電話の注文を文字起こし → 注文フォーム自動入力
2. チャットツールからマニュアル検索
3. 複雑な独自発注ルールを読み込ませたチャットボット
4. 諸外国の法令検索結果をリアルタイム和訳・関連法令比較

**対象**: ChatGPTで何ができそうかは知っているが、システム組み込みのイメージがない非エンジニア

## デジタル庁内の利用環境整備（p.7）

- 非エンジニアでも検証・改修可能な HTML テンプレート
- デフォルトで ChatGPT 風アプリ、モデル切替ボタン、1リクエストごとの料金表示
- プロンプトをHTMLに埋め込み（メモ帳レベル）で多様ユースケースに対応
- セキュリティ: Global Protect のIP制限 + キー認証（2段階）+ API Management + リクエスト/レスポンスのロギング（GPT入出力文字列も保存）で不正利用の個人特定が可能

## token 数とコスト（p.8）

- token = 入出力文章の分割単位。**日本語は文字数より細かくなることが多く不利**
- token数が多いと (1) レスポンス悪化 (2) 料金増 (3) 精度低下傾向
- 上限: GPT3.5=4k、GPT4=8k or 32k
- コスト(当時): 3.5は1000token=0.002USD、4(8k)は入力0.03USD/出力0.06USD（32kは倍）

## ブラックボックスを相手にする（p.10）

- 入出力の対から性質を判断するしかない。いろんな入力パターンを試すことが重要
- 入力が少し変わるだけで出力のニュアンスが変わる。**完全制御は難しいので、それが許容できるユースケースを探し出す**
- 「どのくらい実現できそうか」には濃淡がある（全くできない〜ほぼできる）

## 開発工程での位置付け（p.11–13）

要求分析→要件定義→基本設計→詳細設計→コーディング の中で、**要求分析段階で「どのくらい実現できそうか」を推定**することで（１）どこで（２）だれに（３）どのように使わせるか、の解像度が大幅に上がる。

従来のAI開発（データ準備→機械学習）が不要になり、**プロジェクト初期の試行錯誤の回数を大幅に増やせる**。fine tuning は副作用が大きいので、まずは fine tuning なしでできるか検討を推奨。

参考: AIプロダクト品質保証ガイドライン (qa4ai.jp)

## GPT (Chat) API の messages 構成（p.15–24）

主に意識するパラメータ: `model`（3.5推奨、4は15〜30倍高い）、`messages`

- **system**: このGPTは何をするか
- **user**: GPTへの入力
- **assistant**: GPTへの出力（過去履歴として直接書き換え可能）

APIは状態をもたないため、会話履歴を毎回入力する。上限token数により保持履歴に限界。

system と user の自由度: ドキュメントAを要約させたい場合、
- `system: 「以下についての質問を受け付ける。{A}」` + `user: 「要約して」`
- `system: 「与えられた入力を要約する」` + `user: 「{A}」`

のどちらでも書ける。プログラムの性質（Aについて答えるくん vs 文章要約くん）で選ぶ。

## プロンプトの書き方のコツ（p.27）

- コンテキストを明確に: Good「候補を5つ」/ Bad「候補をできる限り」
- **「step by step で考える」** を指示
- 相手はSFのロボットだと思って丁寧な会話をする
- 法令をsystemに書き込んだ場合、想定QAや理解度確認テストを作らせて専門家が確認

## デモ（p.28）

1. 「できるだけ」だと10個、「20個」と指定すると20個出力
2. 「2025を7で割った余りは？」は誤答だが、「think it step by step」で正答

## デジ庁AI班サンプル（p.29）

- 逐条解説より個人番号について答えるくん（GPT4必須、高コスト・低速）
- 手続きラベリングくん（関連度を出力、ハイコンテキストなラベルは定義別途）
- 手続き箇条書き作成くん（申請書項目の欠落問題）

## 逐条解説を system prompt に埋め込む（p.30–33）

GPTの知識は古く（2021年9月まで）誤った見解も反映されるため、新規法令はプロンプトに直接書き込む（国語の読解問題に）。逐条解説はtoken上限超過 → **GPT自ら項目ごとに要約**（508文字→204文字）。

文節ごとに要約する理由: (1) 参照元を回答可能 (2) 人間の見落とし確認 (3) 精度向上。重要情報の落下リスクあり → 実際に応答させおかしなところを逐次修正。

おかしなところの調べ方（user例）:
1. 「XXXについて1000文字程度の解説記事を作って」
2. 「XXXについての想定QAを10個作って」
3. 「XXXについての理解度確認クイズを作って」
4. 実際の問い合わせを入力してみる

> 作る際に「XXXについての専門家が必要」＆「AIが専門家を上回ることはない」の2観点が重要

## プロンプト開発の試行錯誤手順（p.34）

1. model を GPT3.5 に
2. system と user を書き挙動確認
3. どうしても直示したい場合は assistant 指定
4. 不満なら GPT4 へ。**GPT4でダメならプロンプトが悪いか課題が難しすぎる（だいたい前者）**
5. GPT4でOKなら、3.5でも動くようプロンプトを平易化できないか検討、それでも無理ならGPT4採用

## 発展: GPT の入出力の書き換え（p.38）

品質安定化＆不適切コンテンツ（ハルシネーション・偏り・差別・犯罪助長・著作権侵害）対策:
- **手法1**: ユーザ入力を書き換えてGPT APIへ（例: 「(第N条によると、の形式で回答)」を付与）
- **手法2**: GPT出力を書き換えてユーザへ（例: json指定し一部キーのみ返却、jsonでなければエラー）

プロンプトインジェクション対策にも有効（限界は https://prptinj.net/ で体験可能）

## 他システムと GPT API の組み合わせ（p.39–42）

2パターンの組み合わせで多様なユースケース:
- **他システム出力 → GPT**: 法令検索APIの結果をGPTで要約
- **GPT → 他システム入力**: GPTで表記ゆれ吸収・フォーマット成型してDB登録（検索パラメータ生成には embedding も）

GPT API を階層的に用いるパターン: 「どの法令か判定」→「該当法令のプロンプトで回答」。

**従来NLPとの使い分け（p.42）**: GPTを使うまでもない処理（形態素解析など）は従来型が (1)品質安定 (2)高速 (3)安価。辞書整備は依然重要。

## GPT 以外の API と将来（p.43）

- Google GCP Vertex AI も生成AI API を近日リリース（6/15 英語版GA、日本語は未対応）
- 将来的には「どのモデルか」を意識せず、大量のAPI回答を統合したものが主流になるかも
- 既にオープンソースも（gorilla: 適切なAPIを選択するAI）
- 機械学習歴史的に「個別大量モデルを統合」アプローチ（Boosting等）は単独モデルより良い傾向

## 結び（p.45）

> **100回の会議より、1回のAPI callの方が理解が進みます。まずは試してみましょう！**
