## 概要（スペイン語原文より抽出）

多段階エージェントを作る人の大半は「直線」を作ってしまう。ステップ1→2→3と前置きを丁寧に待つ。しかし**そのステップの半分は何も待つ必要がなかった**。ルーティングせず、分岐せず、並列化せず、ただ列を作る。この14ステップのロードマップで、その縦列を**グラフ**に変える。

### フレームシフト

- プロンプトは1文。ループはサイクル。ハーネスはエージェントが立つ床
- しかし**仕事そのものの形**（何が何より先に走るか・何が同時に走れるか・何が全部待つ必要があるか）はグラフ
- **ノードは考え、エッジは結果を運ぶ**
- Claude Code の dynamic workflows が直接 tooling を提供: Claude がプレーンな JavaScript のオーケストレーションスクリプトを書き、協調するサブエージェント艦隊を実行。**協調自体はモデルトークン0**（会話でなくコードなので）

### 4ブロック構成

- **01–04**: 既にあるグラフを見る
- **05–08**: 艦隊を動かす
- **09–11**: 出力を信頼する
- **12–14**: 破産させない

### Block 1 の要点（01–04）

**01. ノードは依頼、エッジは流れるもの**
- ノード = 作業単位（エージェント・境界のある依頼・入力・出力）
- エッジ = 依存関係（このノードの出力があのノードの入力を養う）。それ以上でも以下でもない
- エラーは「そしてその後（y luego）」をエッジ扱いすること。「このファイル要約して**そして**天気教えて」にはエッジがない。天気は要約を消費しない。**データが本当に跨るときだけエッジは存在する**
- 描き方: 箱 = agent() 呼び出し1つ。矢印 = ある呼び出しの return から別の prompt へ入る変数。矢印が描けなければ（変数が跨らなければ）その2箱は独立
- **ルール: エージェントの「そして」ごとに、次ステップが前の出力を読むか問え。読まないならその待機は捨てた時間**

**02. 線形スクリプトは既にグラフ（退化したもの）**
- 「A, B, C, D とやれ」は枝のない鎖。入出力エッジ各1本
- 鎖は冗長性がない: C が詰まると D は永遠に起きず、A の仕事は行き場を失う
- graph engineering の最初の技能は**鎖を描き直すこと**。矢印ごとに01の問いを立てる。大半の鎖には2〜3本、データを運ばない矢印がある（打った順序の名残だけ）。それを切ると鎖は広い形に崩れ、同時に走れる独立ノード群＋全部を必要とする1ノードになる。**費用ゼロ・新道具ゼロで、買える何よりも多くの待機を消す**
- **ルール: 何か追加する前に、データを運ばないエッジを消せ**

**03. 各ノードに契約を与える**
- 推論できないノードは並列化できない
- 契約 = 境界ある入力・境界ある出力・1つの仕事だけ
  - 入力 = ノードが読むもの。明示的に渡す。共有ウィンドウからは**決して前提にしない**
  - 出力 = 定義された形式（理想は検証済み）。次ノードが推測なしで消費できるように
- workflow では契約は **schema で強制**される。agent() 呼び出しに JSON schema を渡すと、サブエージェントは有効な構造化データの返却を**義務付け**られる。検証は tool call 層で起こるため、合わなければ再試行があり、フリーテキストを parse して祈る代わりになる

**04.**（クリップ範囲では 03 まで確認済み。以降 05–14 は艦隊移動・信頼・コストのブロック）
