# 原文（Zenn 記事・構造化要約）

## システム開発のプロセス
要件定義 → 基本設計 → 詳細設計 → 実装 → テスト → 移行・保守運用（ウォーターフォール前提だが実際は反復）

## プロジェクト関係者
- **自社開発**: クライアント=自社（企画→開発→運用まで自社）
- **受託開発**: クライアント=外部（顧客の要望を聞いて開発）

## 要件定義と基本設計の違い（核心）
- **要件定義**: 「何を（What）」作るか。業務要件・機能要件・非機能要件を定義。**ビジネス側面**
- **基本設計**: 「どう（How）」実現するか。ITシステム全体の構成・画面・DB等を設計。**IT側面**

## 要件定義
### なぜ必要か
- 認識のズレを防ぐ（ステークホルダー間・開発チーム間）
- スコープを明確にする（何をやる/やらない）
- プロジェクトの進行・マイルストーンの基準

### 機能要件と非機能要件
- **機能要件**: システムが「何ができるか」。ユーザー登録・商品検索・決済等の機能
- **非機能要件**: 機能以外の要件。**可用性・性能・拡張性・セキュリティ・移行性・運用保守性**（6つの非機能要件群）

### 要件定義の流れ（6ステップ）
1. **プロジェクトのスコープと目的の明確化** — 何のために・誰のために・何を解決するか
2. **ステークホルダーの識別と関与** — 誰が関わるか・役割・影響度
3. **要望の調査** — ヒアリング・アンケート・既存資料分析
4. **要求の細分化** — 要望を要件へ（MECE・優先順位付け）
5. **要件のドキュメント化** — 要件定義書（機能要件・非機能要件・業務要件・制約・前提条件）
6. **要件の承認** — ステークホルダー合意・ベースライン設定

## 基本設計
### 基本設計と詳細設計の違い
- **基本設計**: システム全体の構造・画面設計・DB概要・API仕様など「IT全体像」。非エンジニアにも分かるレベル
- **詳細設計**: プログラムが動くための詳細（クラス設計・メソッド・DBのカラム型・正規化など）。エンジニア向け

### 基本設計成果物（架空サンプル: ECサイト）
- システム構成図・ネットワーク構成図
- 画面遷移図・画面設計書（ワイヤーフレーム）
- DB概要（ER図・テーブル一覧）
- API仕様書

## 詳細設計
### 詳細設計が不要とされるケース
- アジャイル開発（実装と並行）
- プロトタイプ・PoC
- 小規模プロジェクト

### DDD と詳細設計
- DDD（ドメイン駆動設計）では「ドメインモデル」が詳細設計の役割を担うことがある
- 実装と設計の境界が薄い

### 開発スタイルによる影響
- ウォーターフォール: 詳細設計書が必須
- アジャイル: スプリント毎に設計→実装を反復

### 詳細設計成果物（架空サンプル）
- クラス図・シーケンス図
- DB詳細設計（正規化・カラム型・制約・インデックス）
- テスト仕様書
