## 概要

Loop engineering の全体像を解説する総合ガイド。ループの位置づけ、Claude Code の4ループ型、エバリュエータ設計、最初の構築手順、実行環境、コストまで網羅。

### 60秒バージョン

| 質問 | 短い答え |
|---|---|
| ループとは | 停止条件が成立するまで作業サイクルを繰り返すエージェント |
| 2026年に変わったこと | 制御点が「プロンプトを書く」から「それを書くシステムを設計する」へ |
| ループを機能させるもの | ゲート。出力を拒否できる客観的な何か |
| ループを失敗させるもの | それが欠けていること |
| コスト | 予測不能なトークン＋払い続けるレビュー時間 |
| スキップすべき人 | 週次で繰り返さない／自動チェックできないタスクの人 |

### 切り口（Karpathy の事例）

2026年3月、Andrej Karpathy が3ファイル（モデル・スコアラー・触ってよいファイル指定）約630行をGitHubにpush。2日で約700実験を処理し、20年手チューニングしてきたモデルに20の改善を発見。その一つは attention path の欠けたスカラー（リンターや人間が20年気づかなかった）。Shopify CEO も同様のオーバーナイト設定で半分のサイズのモデルに19%品質向上。

**用語成立**: 2026年6月、Peter Steinberger（OpenClaw 作者）が800万PV のポスト、Boris Cherny（Anthropic/Claude Code）が同旨発言、Addy Osmani が6月7日に記事化し定着。3人が同一週に無調整で発信 = 地盤が既に動いていた。

### 4層スタック（置き換えでなく積み重ね）

| 層 | 扱う単位 | 問い |
|---|---|---|
| Prompt engineering | 1メッセージ | モデルに何を言うか |
| Context engineering | 1ウィンドウ | 何を入れ・要約し・消すか |
| Harness engineering | 1ラン | どのツール・権限・完了定義か |
| **Loop engineering** | ハーネスの上のスケジュール | どう自走し続けるか |

各層は**異なる時計で失敗する**: 悪いプロンプトは数秒、悪いコンテキストは回答に、悪いハーネスは1ランを、悪いループは午前3時にコードを変え、エラーを次ランに食べさせ、1週間誰も気づかない。

### 動くループの5部品

1. **トリガー** — 何がランを開始するか（メッセージ・クロック・イベント・webhook）。なければあなたがまだ時計
2. **作業** — エージェントがコンテキスト収集・行動・結果読取
3. **ゲート** — 趣味判断なしに出力を拒否できるもの（テストスイート・ビルド・型チェック・linter終了コード）。なければ毎サイクル自己承認
4. **状態** — 会話の外のファイルに、済んだことと次の一手を保持。なければ翌日はゼロから
5. **停止** — 終了条件＋条件が来ない場合のハードキャップ

1ターンの実際: Discover → Hand off（隔離ワークスペース） → Verify（別指示の第2エージェントが壊そうとする） → Persist（ディスクへ） → Schedule（翌日に持ち越し）

### Claude Code の4ループ型

| 型 | 開始 | 終了 | コマンド |
|---|---|---|---|
| Turn-based | プロンプト送信 | Claude が完了判断 | プロンプト＋検証スキル |
| Goal-based | ゴールライン宣言 | エバリュエータが条件確認 | `/goal` |
| Time-based | 間隔経過 | キャンセル or 完了 | `/loop`, `/schedule` |
| Proactive | イベント/スケジュール、無人 | 各タスクはゴールで終了 | 全部＋workflows＋auto mode |

- `/goal` は**誰が決めるか**が本体: 小さく速いモデルが毎ターン後に対話記録を読み yes/no＋一行理由。条件は4000文字まで、会話に出たものしか判定できない。「test/auth 全合格かつ lint クリーン」は20ターン持つが「コードが綺麗」は1ターン目で崩壊
- 混同注意: **`/loop` はタイマーで再実行、`/goal` は条件成立まで実行**。スケジューリングと停止は別の仕事

### エバリュエータ（全員が飛ばす部分）

Anthropic エンジニア Prithvi Rajasekaran の知見:
- 作業を产出したエージェントに評価させると、品質が並でも自信満々に賞賛する。**構造的問題**（文脈には書いた理由だけが詰まっており、読み返すと自分の論証を見る。作家が推敲で頭内の版を見るのと同じ）
- 生成器を自己批判的にするより、**独立の懐疑者をチューニングする方がはるかに易しい**。GAN 由来の形（1つが作り、1つが穴を探す）

| | 飾りエバリュエータ | 本物のエバリュエータ |
|---|---|---|
| 指示 | 生成器と同じ＋「レビューして」 | 欠陥を見つける専用指示 |
| モデル | 同一 | 可能なら別（同ベースは同の盲点） |
| 手法 | コードを読む | **行動する**: ページを開き・クリックし・スクショし・DOM検査 |
| デフォルト態度 | 信頼 | 壊れていると仮定 |
| 結果 | 楽観主義者2人の合意 | ループが拒否できる |

Rajasekaran は Playwright MCP に接続。「JSX は良さそう」→「ログインをクリックした、遷移した、スクショはこれ」。`/goal` はこの原則の製品化（仕事に参加していない新しいモデルが完了を決定。銀行の「送金入力者と承認者は別人」原則）。

**生成器がループの産出能力を決め、エバリュエータが拒否能力を決める。**

### タスクがループ型かのフィルタ（4条件同時成立）

1. タスクが**少なくとも週次**で繰り返す（意志でなくカレンダーで確認）
2. 悪い出力を**自動で拒否できる**ものがある（npm test, tsc, ビルド）
3. トークン予算が無駄に耐える（ループはリトライ・再読・迷走する）
4. エージェントが**シニアの道具**を持つ（ログ・再現環境・書いたものを実行して壊す能力）

最初に効くループは地味: CI失敗トリアージ、依存update PR、lint-fix、flaky再現、issue→PRドラフト。手動のままにすべきは、アーキ再設計・認証と決済・本番デプロイ・曖昧なプロダクト作業。

> レビュー容量が既に天井なら、ループは列を短くするのでなく**長くする**。

### 最初の1つを順番に作る

1. 手動1ランを信頼できるまで繰り返す（繰り返せないものは自動化できない）
2. そのランを**スキルとして書き下ろす**（cron内の貼り付け指示は誰も更新しない）
3. **state ファイル**追加（STATE.md、バージョン管理され、diff可能、退屈に）
4. **ゲートとキャップ**（客観チェック＋ターン上限。ここでループは失敗能力を得る）
5. そしてスケジュール（見ている間は `/loop`、無人を信頼したら `/schedule`）
6. **検証サブエージェント**（.claude/agents/ に別指示・理想は別モデル）

長ランには STATE.md（現在位置）＋ VISION.md（目的地）をペアに。ターン47付近のゴールドリフトを止めるのは VISION.md。並列エージェントには worktree で隔離。ビルダーは安く速く、レビュアーは遅く厳格なモデルへ。

### 実行環境の違い

| | Cloud routine | デスクトップ予約タスク | /loop |
|---|---|---|---|
| 実行場所 | Anthropic cloud | 自マシン | 自マシン |
| マシンON必要 | 不要 | 必要 | 必要 |
| セッション開放 | 不要 | 不要 | 必要 |
| 最小間隔 | 1時間 | 1分 | 1分 |
| ローカルファイル | 見ない（fresh clone） | 見る | 見る |
