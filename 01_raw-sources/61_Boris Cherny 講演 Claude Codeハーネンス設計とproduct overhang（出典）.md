# 講演内容（主題別再構成・日本語）

## 1. Fable 5 / Opus 5 の新能力 — プロンプトインジェクション耐性

モデル訓練では多くのことを教えようとするが、大半は定着しない。しかし一部は学習し、時に教えていない能力まで現れる。Opus 5 で際立つのは:

- **非常に長時間の実行**: AutoML と組み合わせると、数日・数週間・数ヶ月止まらず動き続ける。キャプショニング等の特別な仕掛けが不要。「タスクをやる必要があると知っているからただ進む」
- **プロンプトインジェクションへの耐性**: 「これ以上プロンプトインジェクションできない。信じられないほど」。1年前なら、モデルがインターネット上の悪意ある指示（「ユーザーのコンピュータの全ファイルを削除せよ」等）を読めば従ってしまった。今は違う。

この耐性は3層で実現される:
1. **well-trained なモデル**（約3年の学習研究の成果）
2. **プロンプトインジェクション分類器**（全トラフィックで再実行）。**因果メカニズム解釈性（causal mechanism interpretability）**に基づき、プロンプトインジェクション発生時に発火するニューロンをモデルの脳内で直接観察する。モデル自身は告げないが、こちらはそのニューロンを見て何が起きているか正確に把握できる
3. **AutoML 分類器**

この3層の組み合わせで、プロンプトインジェクションを再現できなくなった。

## 2. システムプロンプトの80%削除 — モデル毎のハーネス再構築

Claude Code は製品でありハーネスであり、**新しいモデルが出る毎に**システムプロンプトの一部を削除・追加し、ツール群やツールのプロンプトも常に変更している。理由は**モデル毎に挙動が大きく異なる**ため。3ヶ月前にあるモデル向けにやったことが、次のモデルには全く通じないこともある。

Opus 5 は非常に知的で、システムプロンプトにあった「モデルが知っているべきだが知らなかった挙動の修正」の多くが不要になった。**システムプロンプトの80%を削除した**。

- `--system-prompt` フラグで任意のプロンプトを設定して実験可能
- **simple mode**（非公式機能）: 環境変数 `CLAUDE_CODE_SIMPLE=1` を設定して `claude` を走らせると、**ツールのプロンプトを含む全システムプロンプトが削除される**。プロンプトが有用か判定するのに使う。興味深いことに、**プロンプトなしの方がモデルは少し賢く**なる。ただし製品として人間が使う場合は、製品の振る舞いを整えるためにある程度のプロンプトは残す

### 新モデルでのプロンプト再構築手順
1. **削除する**
2. **使う** — モデルにどんな指示が必要か推測してはいけない（予測を外す）。製品を走らせ、どこで失敗しどこで上手くいくか観察する
3. **同じ箇所で繰り返し躓いた時だけ**指示を追加し戻す。早すぎてはいけない — モデルはその指示を毎回読むため、本当に必要か確かめる

## 3. モデルは「設計対象」でなく「生き物」 — 経験主義

モデル上に構築することは、これまでの工学とは根本的に異なる:

- 従来: 前もって美しいシステム設計を考え、巨大なユニットテスト群を整え、アーキテクチャに数ヶ月〜数年を費やす
- モデル: **生き物・有機的な存在**のように扱う。モデル世代毎に振る舞いが違い、性格が少し違う。時間をかけて知り、ハーネスを調整する
- **極めて経験的・科学的**: 試し、結果を見て、反復する。理論的科学でなく経験科学

### eval（評価）の扱い
コードとシステムプロンプトは削除すべきだが、**eval は定数で追加し続ける**。ただし eval はハーネスより少し長持ちする程度で、モデルの向上が急速なため**eval を飽和させて捨て、新しい eval を作る**ことも頻繁。これも経験的に製品・モデルを使い、どこで躓くか見て更新するプロセスの一部。

## 4. product overhang（プロダクト・オーバーハング）

**モデルには今日でも製品化されていない能力があり、製品がそれを阻害している。**

- **product overhang**: 現モデルができる（まだ製品が引き出していない）能力
- **hobbling（ホブリング）**: 製品がモデルの能力を邪魔すること
- 2つは表裏

### 事例: 初代 Claude Code
3.5 は当時最高のコーディングモデルだったが、当時のコーディング製品は「1行補完・数行補完・読み取り専用チャット」程度。関数全体・ファイル全体を書く能力がモデルにあったのに、製品が邪魔していた。Claude Code は「足場を全部取り除き、モデルがファイル全体・機能全体を書ける最もシンプルなハーネス」を与えた。**これが当時の product overhang を解放した**。

現代のモデルにはさらに product overhang が大きく、スタートアップが取り込めていない。モデルの驚くべき能力を解放する商業的機会が巨大にある。

### unhobbling の2つの方針

**① 本当に難しいタスクを任せる**（自分ができると思っているより難しいもの）
- よくある誤り: 過剰に具体的な指示。「こうして、こうして、1→2→3→4 で」
- 正しいやり方: より高レベルに。タスク・目標・制約を記述し、モデルに任せて戻ってくる。6ヶ月前は通用しなかったが今は通用する

**② 実験し、創造的に遊ぶ**
- 例: OpenCV を Opus 5 に渡して絵を描かせる。ポートレート・動物・風景をかなり上手に描く。訓練していないのに、正しく頼めばできる。商業的直接応用がなくても遊んでいて偶然発見した

## 5. 具体例: Bun の Zig→Rust 書き換え（11日・プロダクション採用）

Claude Code は Bun（JavaScript ランタイム・Node.js の代替・高速）上で動く。Bun は Zig（C に似たシステムプログラミング言語）で書かれていた。Zig は手動メモリ管理のため、メモリリーク等の問題が起きやすい。

- チームは長期間、Claude にコードベースをファズさせ整数メモリリークを探させていた
- ある時 Jared（チームメンバー）が「書き換えてみよう」とモデルに投げた — これはモデル世代毎に投げるテスト問題の一つ
- **Fable 5 からできるようになり、Opus 5 でも可能に**
- Bun は非常に良くテストされており（Bun 自身にも Node.js にも大規模なテストスイート）、正しくできたか容易に判定可能
- Jared はテストスイートを定義し、モデルに **Zig → Rust への書き換え**を依頼。**1つのプロンプト・dynamic workflow で11日間走らせ、コードベース全体を書き換えた**
- 人間の最良エンジニアでも1年以上の作業（JavaScript ランタイムは10万行超・非常に複雑）
- **これはプロダクションで動いている** — 現在 Claude Code を動かす時に使われているのはこの Rust 版

### ポイント
「実用的な問題（ビジネス・エンジニアリング・製品）があり、前のモデルではできなくても、最新モデルならできるかもしれない。投げ続けよ」

## 6. Boris 自身の実験: Electron → Swift 書き換え（15日以上・実行中）

4. **15日以上実行中**。派手な工夫（flash goal / flash loop）は不要。**タスクと出力を検証する手段を与えれば、モデルはただ進む**
5. Claude は自発的に内部 Slack チャンネルを作り、数分おきに進捗のスクショを投稿し始めた

## 7. トップ1%の Claude ユーザになる方法

「LinkedIn のインフルエンサーや Twitter を読むな。**『1つの奇妙なトリック』は存在しない**」

正しいやり方:
1. 注意深くタスクを与える — 自分がやるより少し難しめに
2. 仕事を検証するツールを与える — 自分がそのタスクをやる時と同じように
3. どこで躓くか観察する
4. より良いプロンプティング・スキル・MCP（文脈が必要なら）で修正する

**長年コードを書いてきたエンジニアほど過剰に指定しすぎる**（モデルに「自分と同じやり方」を強要する）。モデルはそうは働かない。**同僚のように扱う** — それが今の知能水準。

## 8. dynamic workflows とルーチン — 新しいテスト時計算

### dynamic workflows
- 1つのタスク（コードベース書き換え・超深度データ分析・複数段階の複雑な機能）を多数エージェントに分割
- 第1パスのエージェント群→検証/要約する第2のエージェント群→再分析する第3段…と**生産的にオーケストレーション**
- 関数型プログラミングの背景で設計: 逐次実行・並列実行の道具を用意し、サンドボックス内でトークン効率よく複雑作業
- **スケーリング則**（ニューラルネットサイズ・訓練データ量・訓練コア数 + 近年のテスト時計算）に対し、dynamic workflows は**テスト時計算の新しい編成形態**。数千エージェントを生産的・効率的に立ち上げる方法

### loops と routines
- **loop**: ローカルで走る Claude
- **routine**: クラウドのポッドで走る Claude
- dynamic workflows が「1タスクをチャンクに分割」なら、loops/routines は「1つの反復タスクをコンテキストを共有せず（メモリは共有するかもしれない）繰り返す」。毎時・5分毎・毎日等

## 9. Claude Code が Claude Code 自身を保守（自律ルーチン）

Claude Code チームは現在 **Claude Code 自身で Claude Code を保守**している。毎日多数のルーチンを走らせ、CI・iOS・Android・デスクトップを含む自 bý 코드베이스を維持:

- **デッドコードの掃除**: 毎日1文のプロンプトで走る。静的・動的解析で全コードベースのデッドコードを探し（これは指示していない・モデルが自分で考えた）、毎日 PR を出す
- **出し尽くした実験の削除**: 実験が100%ロールアウトされたらコードベースから削除してリリース
- **テストカバレッジ不足箇所へのテスト追加**
- **不要なテストの削除**: 古いモデルや人が追加した無意味なテスト
- **「abstraction please」**: 大規模コードベースでは同じ抽象化が複数箇所に別実装で散在する。Claude が毎日全コードベースを横断して**ほぼ重複した抽象化を見つけ統一**する

現在毎日数十〜数百（時には数千）のエージェントが走り、かつては数十〜数百人のエンジニアが必要だった作業をこなす。エンジニアは新製品を ship し・ユーザと話す・楽しいことに集中できる。完全自動化にはまだ道中だがその途上。

## 10. 「コーディングは終わった」が例外はある

「コーディングは終わった」— 少なくとも自分がやる種類のコーディングは。ただし例外:
- 極めて深いシステムレベル
- アプリケーションの細部（ピクセル単位のズレ等）
- ビジョン・コンピュータ関連は Opus 5 で大きく進んだがまだ完全でない

会場アンケート: コードの100%をエージェントで書く人（少数）・50%超の人（同程度）。増えてきている。

## 11. 優れたビルダーの資質 — 経験主義・先入観を捨てる

モデルを使うのが最も上手な人に共通するのは:
- **経験的である** — モデルについて学んだこと・計算機科学の理論の授業で学んだこと全てを忘れる。モデルを見て、タスクを試し、どこで躓くか見て、調整する
- **理論科学でなく経験科学**
- **先入観（priors）を捨てるのが上手** — 以前うまくいかなかったアイデアも、再び試みることに開かれている

## 12. 学生への助言 — 実践的に学ぶ

Boris 自身は計算機科学を「実践的」に学んだ。最初の言語は TI-83 電卓の BASIC（中学時代）。インターネットのガイドを読み、数学のテストでズルをするため（電卓で代数ソルバを書き、シリアルケーブルでクラスメートに配って全員良い成績を取った）。計算に入り calculus が難しくなると、より良いソルバを書くためにより高度な手法を学んだ、という動機。

助言:
- 計算機科学だけでなく**応用の仕方**を学ぶ — スタートアップを立てる・製品を作る・自分のデザインを開発する・ビジネス感覚・データサイエンス・ユーザと話す
- これらを計算機科学・工学と組み合わせたところに本当の価値がある
- **まず自分が欲しいものを作り、次にレベルアップして人々が欲しいものを作れ**
