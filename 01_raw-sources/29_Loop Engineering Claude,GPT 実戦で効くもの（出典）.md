# 本文（再構成・英語原文保持）

## Loopとは何か

3年間、AIを使うとは**あなた自身がループだった**。プロンプトを打ち、回答を読み、次を決め、また打つ。AIは1ステップをこなし、その間の「決定」はすべて人間が担っていた。

**Loopはあなたを中間から外す。** 各回答の後に「次に何をするか」を人間ではなくシステムが決める。機能し、結果を見て、自ら次の手を考え、仕事が終わるまで繰り返す。

> The rhythm inside every loop is the same three beats: **reason, act, observe**. Think, do, look, repeat. それがループ。

## Loop vs Chain —— 決定的な違い（本記事の核心の一つ）

| | Chain（連鎖） | Loop（ループ） |
|---|---|---|
| 経路 | **固定レシピ**。事前に全ステップ定義 | 経路を**前もって知らない**。試し、結果を見て次を決める |
| 適所 | 「要約→翻訳→整形」のように手順が既知 | 「このバグを直せ」のように**次ステップが前ステップの結果に依存** |
| 判定 | **番号付きチェックリストを渡して立ち去れる**ならChain | 「これを試し、結果次第で次のいずれかを選ぶ」と言う必要があるならLoop |

> Real, messy, multi-step work almost always needs a loop.（現実の厄介な多段階仕事はほぼ常にループが必要）

## 2026年にLoopが主流になった理由

reason-act-observe パターン自体は**2022年の研究**、自己批評エージェントは**2023年**に既に存在。新しいのはアイデアではなく、**モデルがついに十分信頼できるようになった**こと。

- 初期モデルはループ内でドリフト・混乱・悪化し、監視なしでは走らせられなかった
- 2026年、フロンティアモデルが長く多段階な作業に十分信頼できるようになり、**人間が中央でタイプするのがボトルネック**になった
- スキルが変化: 「完璧なプロンプトを書く」→「AIに代わってプロンプトするループを設計する」＝ **loop engineering**

## Claude はどうやるか

Claude エコシステムでは Claude Code が中心。構成要素:
- **ビルトインのループ機能** — チェックが通るまで繰り返す（1コマンドずつ発行しない）
- **スケジューリング** — タイマーでループ実行（これが「一晩中走る」仕組み）
- **Hooks** — 特定瞬間にルール自動発火（毎変更後にテスト実行等、検証をスキップさせない）
- **サブエージェント付き動的ワークフロー** — 大仕事を並列ワーカーに分割し主エージェントが調整

下部構造: ツールには **MCP（Model Context Protocol）** 経由で触れる。**skills**（保存手順）・**worktrees**（並列作業の衝突防止）。

> Claude 圏の哲学: 長時間走り**自ら本物のテストで検証し続ける**ループ。

## GPT はどうやるか

OpenAI 圏では **Codex** が中心。要素は精神として同じ:
- **Automations**（構成可能なスケジュール）— タイマー実行、「寝ている間に走る」
- **サブエージェント生成** — 並列ワーカーへ分割
- **skills** と **MCP** 統合も同様にサポート

> 両エコシステムは**同じ基本アーキテクチャに収束**した。名前も詳細も違うが形は同じ —— 問題が要求する形に従っているから。

## 考え方を変えるべき洞察（プラットフォーム比較より重要）

> The valuable, durable part of a loop is not the model at the center. It's everything around it: **the loop logic, the tools, the checks, the memory, the guardrails**. And that outer part is largely **portable**.

Claude↔GPT 切替は主に**中央の脳**を入れ替えるだけ。設計したループ・構築した検証器・配線したツール・書いた「doneの定義」はすべて持ち越せる。

→ **「どのモデルが最善か」論争は見かけほど重要でない。** 努力は再利用可能な**外層**に投じよ。今月ほんの数ポイント良い脳を言い争い続けるな。

## 実際に効くもの（What Actually Works）—— プラットフォーム非依存

5つの原則:

1. **機械がチェックできる「doneの定義」** — 第1の失敗は曖昧な目標。「良くしろ」では止め時がわからない。「全テスト合格」「出力がこの形式に合致」ならOK。**毎回、最初に書け。これで大半のループ失敗を防げる。**

2. **接地した検証器（自己採点ではない）** —— 最大のポイント。モデルは自分の作業を**ほぼ常に承認**する（自分の宿題にAをくれる）。成功を決めるチェックは**モデル自身の意見の外**から可能な限り: テストスイート、linter、ビルドコマンド、外部バリデータ。検証器が本物のコマンドなら、おべっかの余地がない。**これが「出力を改善するループ」と「自信満々のゴミを生むループ」の差。**

3. **階層化された終了ロジック** — 出口のないループは現場で最も高価なミス。複数の出口を重ねよ: 成功チェック、反復ハードキャップ、予算/時間制限、無進行検出。単独では不十分、組み合わさって初めて「立ち去って安全」になる。

4. **コスト規律** — ループは単発プロンプトの**10〜100倍**モデル呼び出す。各ステップを**最も安い能力十分なモデル**へルーティング（単純振り分けは小さく速いモデル、最終困難レビューだけ大きいモデル）。反復部分を再利用し毎イテレーション全額払わない。**品質を落とさずコスト劇減。**

5. **不可逆な作業の前に人間のチェックポイント** — ループは調査・起草・コーディング・検証を一日中独りでできる。しかし**メッセージ送信・デプロイ・共有ブランチpush・送金・削除**は承認待ちにすべき。野望の欠如ではなく、**監視なし運用を本当に安全にするもの**。

## デモでは良く見えるが実戦で失敗するもの

- **曖昧なルーブリックで自己採点するループ** — 常に自チェックを通すので働いているように見えるが出力は間違っている。「立派に見えて役立たず」。チェックを接地せよ。
- **ガードレールのない無限自己改善** — 外部接地なしに何百回も自己批判・改訂すると**改善せずドリフトする**。2026年の研究は**驚くほど少ない反復で測定可能な劣化**を発見。あるビルダーはエージェントが統計をでっち上げ、自作の数字を事実として引用し始めたのを目撃。自己改善は**接地したチェック・メモリ衛生・ハードリミット**があって初めて機能。
- **すべてへの最大自律** — 「たいてい正しい」からと監視なしで不可逆操作をさせるのが、取り消せない悪いデプロイを生む道。プロは**不可逆を門番し、可逆を解放する**。
- **システム構築よりモデル追いかけ** — 検証器が壊れ終了ロジックもないまま、ベンチマーク数ポイントのために脳を替える。モデルが問題だったことは稀。

## 最初のループ —— ステップバイステップ（両プラットフォーム共通）

1. **doneを機械検証可能に書く** — 「ファイルが検証を通る」「全テスト緑」等。**書く最重要の1行**（止め時を告げるもの）
2. **検証器を特定** — コードはテスト/linter、データは検証チェック、執筆は別レビュー手順が使うルーブリック。**エージェント自身の意見の外**に置け
3. **出口を設定** — 反復ハードキャップ、予算/時間制限、無進行停止ルール。**走らせる前に書け**
4. **走らせて見る** — 最初は立ち去るな。永遠ループ・弱い自チェック通過・目標から逸脱等の失敗を探す
5. **信頼できたら無人運転へ**、繰り返すタスクなら**スケジュール化**。それが「操作するもの」から「ただ起きるもの」への転換点

> 午後1つで作れる。

## ループを使うべきでない時

- **単一ステップ** → プロンプトで十分（質問、要約、メール1通）。ループは費用と複雑さを増すだけ
- **全ステップが事前既知で前ステップに依存しない** → chainを使え。ループの利点（適応）が無駄
- **doneがチェック可能な形で定義できない** → まだループの準備ができていない。**目標を先に明確に**
- **高 stakes・不可逆・人間チェックポイントの余地なし** → ループ向きではない

> The skill isn't using loops for everything. It's recognizing the tasks that are genuinely **loop-shaped: repetitive, multi-step, adaptive, and checkable**.

## 歴史（平易に）

- **2022年**: reason-act-observe リズムの研究（すべてのループの心臓）
- **2023年**: 失敗を省みて教訓を持って再試行する**自己批評エージェント**の研究
- **2026年**: フロンティアモデルが長い多段階作業に信頼できるようになり、研究的好奇心から**主流の働き方**へ。「loop engineering」と命名され数週間で普及

→ ループパターンは**十年前のアイデアがつい使い物になった**もの。流行ではなく深く学ぶ価値がある。

## LoopについてのFAQ（著者の答え）

- **コード必要?** — 最強のコーディングループにはコード安心感が大事。しかし核心思考（done定義・チェック構築・出口設定）はコードではなく、研究/執筆/データの有用ループは想定より技術深さなしで構築可能
- **どのプラットフォームで学ぶ?** — **既に使っているもの**。両エコシステムとも同じ基本アーキテクチャでスキルは移転する。選択で停滞するな
- **良いモデルでloop engineering不要になる?** — **逆**。良いモデルはループを強力にし、設計スキルをより価値あるものにする。モデルは「やる」を担い、「何をするか・doneの意味・どう検証するか」はあなたに残り、モデルが強くなるほどレバレッジが効く
- **単なるハイプ?** — 用語にはハイプあり。しかしあなたが毎ステップ打つ → システムが自走する、という根本シフトは本物

## 正直な真実

> A loop will not fix a task you can't clearly describe.

実践全体は**2つの難しいこと**に還元される:
1. **システムが運転できるほど正確に仕事を記述する**こと
2. **失敗を捕らえるほど正直なチェックを構築する**こと

プラットフォーム機能は簡単な部分。**明確さと接地した検証器が本物の仕事**であり、いかなるモデルもそれを代行しない。

良いニュース: モデルが良くなるほど、希少で残るスキルは**ループを設計すること**（基準を設定し、判断をチェックとして符号化し、「正しい」を知る）。そのスキルは**全プラットフォームで携帯可能**で**全モデルリリースを通じて耐久**がある。自動化されない。より価値になる。
