# GraphRAG: 知識グラフでRAGを置き換える

> [!info] 出典
> Sprytix（@Sprytixl）、2026年7月19日18:47公開（X記事）
> [元記事](https://x.com/Sprytixl/status/2078778799064584535)
> 詳細メタデータ: [[06_Graph Engineering replaced RAG（出典）]]

原題「Graph Engineering replaced RAG at Microsoft, Stanford and Anthropic」。通常のRAGは**テキストを探す**が、知識グラフを使うアプローチは**関係を探す**、という主張のもと、Microsoft・Stanford・Anthropicの事例・論文をまとめて紹介する記事。

## 通常のRAGの天井

RAGの基本形は「質問→文書検索→関連チャンク→モデルが回答生成」。単純な質問には効くが、「3月に売上が落ちた理由は？」のような複雑な質問には弱い。RAGは "sales" "March" を含む文書の断片を返すだけで、供給元の問題→倉庫トラブル→レビュー悪化→転換率低下、のような**因果の連鎖**は見つけられない、というのが記事の出発点。

## 引用されている資料

| 資料 | 要点 |
|---|---|
| **Microsoft GraphRAG** | 文書→チャンク分割→エンティティ/関係抽出→グラフ構築→コミュニティ検出→レポート生成→埋め込み→検索、というパイプライン。特定エンティティに答える「ローカル検索」とデータセット全体のパターンに答える「グローバル検索」の両方に対応。産業図面向けのChatP&ID論文の実測として、精度+18%・トークンコスト-85%・1タスク約$0.004という数字が引用されている |
| **Stanford DSPy/STORM/スケーリング則論文** | DSPyは「モデルはグラフの1ノードであり中心ではない」という理論的基盤で、パイプライン自体をグラフとして最適化する。STORMは文章を書く前に構造化されたリサーチ手順のグラフで知識を組み立てる。26のOSSモデルを比較したスケーリング則論文の結論は「大きいモデル＋悪いグラフ」より「小さいモデル＋良いグラフ」の方が結果が良い、というもの |
| **MIT Press論文（関係性メモリ）** | テキストの塊ではなく明示的な関係グラフに接続したモデルは、より一貫性があり論理的誤りが少ない文章を生成するという知見 |
| **KEPLER** | 言語モデルの学習と知識グラフの埋め込みを同時に最適化する手法。事実に関する質問での精度差が大きいとされる |
| **Anthropic/Claude** | Anthropic自身は「Graph Engineering」という製品名は持たないが、Claudeがグラフアーキテクチャに組み込まれる3層があるとする：①テキストからのグラフ抽出（エンティティ/関係抽出・重複排除・正規化）②自然言語をCypher/SPARQLクエリに翻訳してグラフに問い合わせ、結果を平易な言葉で説明③MCPがグラフDBへの恒久的な接続層になる |
| **LaunchNotesの事例**（Anthropic公式ケーススタディ） | GitHub・Jira・Linearを繋いだ「エンジニアリング作業のグラフ」をClaudeが分析。インシデント検知が最大5倍高速化、ミーティング時間が約50%削減、リリースノートを数秒で自動生成 |

## 知識グラフの基本概念

情報を「主語→関係→目的語」の3つ組（トリプル）として保存する（例: `Anthropic → created → Claude`）。通常のデータベースは会社や製品のテーブルはあってもその間の関係は明示的でないが、知識グラフは関係そのものを構造化されたデータとして保存する。

## Graph Engineeringパイプライン（9ステップ）

生資料の収集 → エンティティ抽出 → 関係抽出 → スキーマ設計（エンティティ型・関係型の定義） → 重複排除と正規化（"Microsoft Corp"と"MSFT"は同一エンティティ、等） → グラフDBへの保存（Neo4j、Amazon Neptuneなど） → 検索層の構築（ローカル/グローバル） → モデル接続（MCPや直接APIで問い合わせ） → 継続更新（新しい文書でグラフが拡張され、矛盾はレビュー対象としてフラグが立つ）。

引用されている「LLM支援ナレッジグラフ構築」論文の留保: LLMは抽出・正規化の補助としては優秀だが、スキーマ設計や重複排除をゼロショットで本番品質にするにはまだ人間のレビューが要る。

## パイプラインを回す5段階のプロンプト（役割のみ）

1. **抽出**: エンティティと関係を、根拠・確信度つきで構造化して返させる
2. **正規化**: 2つのエンティティが同一か・関連するが別か・無関係かを、明確な根拠なしに統合しないという条件つきで判定させる
3. **グラフクエリ**: 自然言語の質問をCypherクエリに翻訳させる。スキーマにない関係・プロパティを創作しない制約つき
4. **根拠に基づく回答**: 取得したグラフの経路だけを根拠に回答させ、不確実性を明示し、相関から因果を推論しない制約つき
5. **グラフ保守**: 新しい事実を「新規/重複/矛盾/更新/不確実」に分類させ、根拠なく既存の事実を上書きしない制約つき

## 知識グラフの上に作れる5つの事業（例示）

デューデリジェンス基盤（投資ファンド・法律事務所向け）、営業インテリジェンス、エンジニアリング・インテリジェンス（LaunchNotesが実際に販売している領域）、リサーチ・インテリジェンス、そして**個人用ナレッジOS**（Obsidianノート・メール・カレンダー・PDF・連絡先・タスクを統合し、「誰とこの話をしたか」「どのタスクが誰の返信待ちか」に答える）——このボルト自体がまさにこの実践例に当たる。

## 所感

- 著者は自己紹介からして「テクノロジーを実収入に変える」系のグロース志向アカウントで、断定口調と具体的すぎる収益額（月額$2,000〜10,000等）が目立つ。数字の一部（精度+18%・コスト-85%・$0.004/タスク）は産業図面という**ニッチなドメインの1論文**由来で、あらゆるRAGタスクに一般化できる保証はない
- 「AnthropicはGraph Engineeringという製品を持たない」と記事自身が認めており、LaunchNotesの数字（5倍・50%）は顧客事例**1件**からの引用。母数1件を「Microsoft・Stanford・Anthropicが独立に到達した結論」と呼ぶのはやや誇張が強い
- 一方で核心のアイデア——明示的な関係を持つ知識グラフの方が複雑な推論に強い、モデルを大きくしてもグラフが悪ければ結果は悪い（スケーリング則論文）——自体は、[[04_Graph Engineering エージェントを行列から解放する]] や [[13_知識グラフメモリをOpus5で安く運用する]] とも矛盾しない、地に足のついた主張
