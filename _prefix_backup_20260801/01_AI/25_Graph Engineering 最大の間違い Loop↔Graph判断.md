# Graph Engineering 最大の間違い —— Loop↔Graph の判断

> **「デフォルトはループ。特定のシグナルが出た時だけグラフに昇格せよ」** — Graph Engineering 流行に対する健全な懐疑と、問題が実際にいくつノードを必要とするかの判断基準。

出典: [[31_Graph Engineering 最大の間違い Loop↔Graph判断（出典）]]（wandermist @wandermist, 2026-07-30。本文はユーザー提供クリップから再構成）

---

## 一行で

「Graph Engineering 最大の間違い = **必要でないのにグラフを作ること**」。ループは1ノードのグラフに過ぎず、**5つのシグナル**が現れた時だけノードを追加すべき —— という Loop↔Graph 判断の実践ガイド。

## 核心テーゼ

> **ループとは、1ノードと自分自身へ戻るエッジを持つグラフである。** 二つの哲学の間で選ぶのではない。**問題がいくつノードを必要とするかを選んでいるだけ。たいてい1つ。**

四半期に作るものの大半は、チェック可能なdone定義を持つ単一タスク（テスト修正、起草＋自己レビュー、受信箱トリアージ、1問いの調査と執筆）→ **すべてループで、グラフはいらない。**

Loop Engineering から持ち込む1行: **ループでは検証器がボトルネックであってモデルではない。** 検証器を正しく作れば、単一ループが驚くほど出荷する。

## ループを超える5シグナル（グラフを正当化するもの）

| # | シグナル | ループが苦戦する理由 |
|---|---|---|
| 1 | **ステップごとに異なる専門性**（リサーチャー/ライター/レビュアー） | 1エージェントが3仕事を切り替えると全てが平坦に |
| 2 | **並列ファンアウト→合流**（8ファイル/5競合/20チケット同時分析） | ループは逐次、実時間が全コスト |
| 3 | **ステップごとに異なるモデル/ツール**（安いモデルでトリアージ、フロンティアで推論） | 単一ループは1モデル・1ツール方針を端から端まで |
| 4 | **監査可能・分岐する制御フロー**（規制/高stakes） | 自由に動くループの経路は事後再構成困難 |
| 5 ★ | **検証器が仕事多すぎで失敗し続ける**（正確性・トーン・安全性・完全性を一度に判定） | 専用レビューノード分割はプロンプト拡大でなく**グラフのエッジ** |

> **シグナル5を最も注視** —— ループ→グラフの線が真に有用になる場所。単一検証器過負荷の修正は「長いプロンプト」でなく「その1チェックだけする別ノード」= **存在する最小の誠実なグラフ**。

> @rohit4verse の組織図メタファー: **専門家を雇う時にノードを追加するのであって、その前ではない。** 実シグナルにつき1ノード。

## 必要でないグラフのコスト（懐疑派が正しい理由）

グラフは**無料の洗練ではない**:
- 各ノード = 設計すべき別物・失敗しうる別場所・検証すべき別出力
- 各エッジ = **調整レイテンシ**（単一ループなら1コンテキスト内で済んだもの）

> @PawelHuryn の辛辣な反発: "I call BS on graph engineering. Loop engineering was already confusing." —— これはノイズでなく、**必要でないグラフこそ彼が指す混乱**。

**懐疑派の最強版**: 「グラフは悪い」でなく、**「グラフに手を伸ばす大半の人は、ループ形の問題と、強化を怠った検証器を持っている」**。グラフは問題が真にマルチ専門・真に並列の時にのみ複雑性を稼ぐ。それ以外は**見返りのない税**。

**罠に落ちた兆候**: 各ノードを強制した5シグナルのどれかを指し示せない。図がまし見えるから存在するノードなら**削除せよ**。

## 30秒決定木（ループに意図的にバイアス）

```
新しいタスク
    │
    ▼
DISTINCT な専門性（research/write/review）に分解できる？
    │
    ├─ no ──→ TRUE な並列（ファンアウト→合流）が必要？
    │              ├─ no ──→ ステップ別モデル/ツール or 監査可能分岐が必要？
    │              │              ├─ no ──→ 1検証器が多すぎるものを判定して失敗？
    │              │              │              ├─ no ──→ ★ ループに留まれ。検証器を強化し出荷
    │              │              │              └─ yes ─→ 検証器を独自ノードに分割（最小グラフ）
    │              │              └─ yes ─→ GRAPH（ルーティング/分岐）
    │              └─ yes ─→ GRAPH（ファンアウト→合流）
    └─ yes ──→ GRAPH（専門性ごとに1ノード）
```

> **ほとんどの実タスクは左下出口（ループに留まれ）に落ちる。それは意図された結果で、フローの失敗ではない。**

## フレームワークは不要（既存FWが両端を表現）

- **LangGraph** —— ノードとエッジを状態グラフに組む。**単一ノードが自分にループするのがループ、ルーティング付き特殊化ノードを追加するとグラフ**（同一コードベース）
- **Google ADK** —— テンプレートWF（逐次/並列/ループ）＋エージェントルーティング

> フレームワークは両方の語彙を与えるが、**決定は下さない。問題のシグナルが決定する。**

## ループかグラフかのチェックリスト（6項目）

1. **デフォルトはループ** — シグナルが2番目を強制するまで1ノードと仮定
2. **シグナルを声に出して名指せ** — 5つのどれか。名指せなければまだグラフではない
3. **実専門性につき1ノード** — 分割できそうなステップにつき1ノード、ではない
4. **ノード追加前に検証器を直せ** ★ — 「グラフが必要」ケースの半分は弱い検証器の変装
5. **調整のコストを計れ** — 各エッジはレイテンシ、各ノードは失敗点
6. **折りたためる状態に保て** — ノード削除で結果が同じなら削除

> **問題が必要とするグラフを、1ノード余分に作らずに済むこと** —— それが懐疑派が叩けない唯一の「graph engineering」版。

## 金言

- **「ループは1ノードのグラフ」** —— 二つの哲学ではなく、ノード数を選ぶだけ
- **「ループでは検証器がボトルネックであってモデルではない」**
- **「専門家を雇う時にノードを追加するのであって、その前ではない」**（@rohit4verse 組織図メタファー）
- **「グラフが必要ケースの半分は、弱い検証器の変装」**
