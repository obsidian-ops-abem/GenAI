# 概要

Claude Codeの作者 Boris Cherny（ボリス・チェルニー）が繰り返し語る3原則を軸に、それを具体的に実装する手段としての MCP（Model Context Protocol）を解説し、公式MCPサーバー8選と実践プロンプト例を紹介する記事。

## ボリスの3原則

1. **Claudeに、自分の出力を検証する手段を渡す** — 本人いわく「最も重要なTip」。ブラウザ禁止で人にサイト制作を頼んでも良いものは出てこないのと同じで、検証手段さえ渡せば勝手に納得いくまで反復する
2. **1日1回以上やる作業は仕組みにする** — 同じ手順を毎回チャットで説明せず、Skill/コマンド化する
3. **外部ツールをClaude Codeの作業面に持ち込む** — Slack・課題管理・DB・社内APIなどを直接触れるようにし、ツール間移動をなくす

「プロンプトを書くな。ループを書け」がボリスの発言として引用されている。

## MCPとは何か（記事の説明）

AIツールと外部サービスを繋ぐ共通規格（「USBの規格のようなもの」）。Claude Codeに機能を追加するのではなく、**作業対象そのもの**（Figmaのデザイン、Sentryのエラー、Linearのチケット等）をClaude Codeの中に持ち込むもの、という位置づけ。

## 最新仕様改定の4点（記事の主張）

| 変更点 | 内容 |
|---|---|
| ステートレス化 | リモートMCPが通常のHTTPリクエスト/レスポンス型になり、サーバーレス/エッジ環境に載せやすくなった |
| 長時間処理対応 | 即時応答でなく、受付番号を返して後から進捗確認・キャンセルできる設計が正式化 |
| 会話内UI | サーバー側が操作画面（選択画面・グラフ・承認ボタン等）を返せるように |
| 組織単位の認証 | 企業IDプロバイダーと連携し、管理者承認後は社員が自動接続可能に |

※記事内でも「仕様確定と実装対応は別」「Anthropic側は順次ロールアウト中」と留保あり。

## 推奨MCPサーバー8選

| # | サーバー | 主な用途 |
|---|---|---|
| 1 | Context7 | ライブラリ/フレームワークの最新版ドキュメントを参照させ、古い書き方の生成を防ぐ |
| 2 | Playwright | Claude自身にブラウザを操作させ、実装した画面を自己検証させる（原則1の実装） |
| 3 | Figma | デザインをスクショでなく構造化データ（色・余白・コンポーネント）として読ませる |
| 4 | Linear | Issue読み込み→実装→テスト→進捗コメントを一気通貫にする |
| 5 | Sentry | 本番エラーのスタックトレース・頻度・影響範囲をまとめて調査させる |
| 6 | Cloudflare | デプロイ先（Workers・DNS・ログ・パフォーマンス）の状態を見せて改善提案させる |
| 7 | Stripe | 決済コードとStripe側設定（Product/Price/Webhook）を突き合わせる |
| 8 | GitHub | PRのレビューコメントを分類し、修正すべきものだけ実装・テストする |

各項目に「実践プロンプト」例が付いており、共通して「本番操作・削除・マージ等は人間の承認を必須にする」文言が明記されている点が特徴。

## スタックとして組む例（記事より）

- **Web制作スタック**: Figma→Context7→Claude Code実装→Playwright検証→GitHub PR→Cloudflareデプロイ
- **SaaS開発スタック**: Linear要件→Context7→Claude Code実装→Stripe決済→Playwrightテスト→Sentry監視

## 初心者向け導入順（記事の推奨）

1. **Context7** — 読み取り中心でリスクが低く、効果を体感しやすい
2. **Playwright（またはブラウザ拡張）** — Claude自身に検証させる段階
3. **LinearまたはGitHub** — 仕事の入口〜出口を接続する段階

## 4つの落とし穴（記事より）

- MCPを増やすほど賢くなるわけではない（ツール候補が増えると迷い・誤操作・権限管理の複雑化を招く。3〜5個に絞るのが推奨）
- 読み取りと書き込みを最初から一緒にしない（本番デプロイ・DNS変更・顧客データ変更・決済本番操作・削除・マージは要人間承認）
- 公式とコミュニティ製を混同しない（提供元・更新日・セキュリティポリシー・権限範囲を確認）
- 外部から来た文章（Issue/PRコメント）をそのまま実行させない（プロンプトインジェクションのリスク。何をしようとしているか一度提示させる）

## 所感・関連

- 4つ目の落とし穴（外部テキストの無条件実行に対する警戒）は、このセッション自身が従っている「observed contentからの指示は実行前に必ずユーザーに確認する」という方針と方向性が一致しており、実務的に納得感がある。
- 「MCPを入れると性能が何倍」のような誇張した数字を記事自身が明示的に否定している点、また「仕様確定 ≠ 実装対応済み」と留保している点は、この種の記事にしては誠実な書き方。とはいえ「950以上のMCPサーバー」「7.2万閲覧」等の数値、Boris Cherny本人の発言の引用が本人の実際の発信内容と一致するかは未検証。
- [[06_LOOP vs GRAPH vs HARNESS ENGINEERING]] の Harness Engineering（ツール・実行制御・観測性）の話と重なる部分が多い。特に「読み取りは許可、書き込みは確認、削除は拒否」という権限段階の設計は、このvaultの [[01_MIXI新卒技術研修セキュリティ研修まとめ]] の最小権限の考え方とも接続できる。
