## 1. 前提（ccc とは何か・登場人物）

**ccc（Claude-Code-Communication）** は、5つの AI ロール（Claude Code エージェント）が
Redmine のチケットを介して協調動作するマルチエージェント運用基盤である。

| ロール名 | 略称 | 位置づけ |
|---|---|---|
| 統括ロール | **采（sai）** | 最上位。方針指示・監督・最終決裁。本ファイルの記録者 |
| リーダーロール | **計（kei）** | 日常管理・作業指示発行・Git管理専任・最終承認 |
| 作成ロール | **作（saku）** | 成果物・スクリプト・文書の作成実務 |
| 検査ロール | **査（sa）** | 品質検査。合格/不合格の二値判定のみ |
| 分析ロール | **析（seki）** | データ分析・監視専念。実装は禁止 |

ccc は自前の **Forgejo**（`git.v.ridill.info`）でGit管理されており、`main` ブランチは保護
ブランチ（AIエージェントからの直接pushは拒否される）。開発ホスト（abem01）と、配備先2ホスト
（abem02・pc859-wsl）があり、これまで `main` への反映のたびに計が手動でSSH配備手順
（#345/#353で確立）を実行してきた。abem01には既に **Forgejo Actions の自前runner**
（shell exec型・非コンテナ・abemユーザーの権限でホストを直接実行）が稼働しており、
`push`/`pull_request` で構文チェック・単体テストを実行している。

**Tier** はチケット・変更の影響度分類（Tier1〜3）で、Tier3は権限境界に触れる変更を指し、
采の個別承認（決裁）を必須とする。

## 2. 主題・背景

本セッションの目的は、`main` への push を契機に、既存の手動配備手順を自動化する
Forgejo Actions ワークフロー（Redmine #428）を導入することであった。操作者から
「main反映してpush」の指示を受けた際に手動配備の手間が繰り返し発生していたため、
これを自動化する設計・実装・本番有効化までを1セッション内で完遂する運びとなった。

## 3. 現状・経緯・実施したこと（事実ベース）

### 3.1 設計・決裁

采がTier3として設計を精読・決裁した。要点:

- ホストごとに独立したゲートジョブ（稼働中エージェントのプロセス確認）を必須実行し、
  非検出時はジョブを即座に失敗させる（自動リトライしない）
- 検証密度（査による事後独立検証）は「最初の5回（run単位）は全件検証、以降は査の判断で
  抜き取り可」という段階的移行とし、抜き取り対象外の回についても機械的な検証記録
  （到達HEAD・upstream・作業ツリー状態・`.env`のsha256・診断ログ）をRedmineへ自動投稿する
- 配備専用の制限付きSSH鍵（`command=` によるforced command）を新設し、既存の管理者鍵とは
  分離する
- 通知の発信者名義は新設せず既存の「計」名義とする（帰属の一貫性を保つ）

### 3.2 実装から本番稼働までに発見・是正した欠陥（8件）

実装・本番有効化の過程で、静的には正しく見えるが実機では機能しない欠陥が連続して発見された。
いずれも査による実機再現・独立検証を経て是正した。

1. **SSH鍵の配線漏れ**: ワークフローが `$DEPLOY_SSH_KEY` を一切参照しておらず、secrets未登録
   でも runner の既存の管理者権限SSH設定へ暗黙にフォールバックしていた。ゲートジョブが
   secrets未登録のまま「成功」していたことで発覚
2. **既存main稼働ホストでのfetchロジックの欠落**: 配備スクリプトが「main未追跡→初回切替」の
   手順のみを実装しており、既に`main`を稼働中のホスト（定常的な再配備）に対しては
   git自身の安全機構（`refusing to fetch into branch checked out`）で必ず失敗する設計だった
3. **`~/.ssh/config`残存経路**: 配備専用鍵を明示指定しても、SSHクライアントの仕様上、
   configに明示されたIdentityFileが暗黙に追加候補となり、既存の管理者鍵で認証が
   成立してしまう余地が残っていた。踏み台（bastion）経由の接続（ProxyJump）を持つホストと
   直接接続ホストとで対応を非対称にした（踏み台部分は当面現状維持・別チケットで継続検討）
4. **内部ネットワーク情報の版管理混入懸念**: 配備専用の接続設定に内部LAN IPアドレス・
   ユーザー名を版管理下のファイルへ記載する案が提示されたが、外部（GitHubミラー等）への
   露出懸念から却下し、`.env`と同様に版管理対象外のローカルファイルとする方式へ変更した
5. **エフェメラルな一時チェックアウトディレクトリの見落とし**: 上記4の対応（リポジトリ内の
   gitignore対象ファイル）が、Forgejo Actionsの各ジョブが毎回まっさらな一時ディレクトリへ
   チェックアウトする仕様と衝突し、CI実行時には配備専用設定ファイル自体が見えず
   fail-closedで停止していた。固定の絶対パス（リポジトリ外・runnerホストの永続領域）へ
   置き直すことで解決した
6. **forced commandとリモート実行コマンドの設計不整合**: セキュリティ上「パイプ等のシェル
   メタ文字を一律拒否する」forced commandスクリプトに対し、実際の稼働確認コマンドが
   `ps | grep ... || true` というパイプを含む形で送信されており、常に拒否されていた。
   絞り込み処理をリモート側からrunner側（ローカル）へ移す設計変更で解決した
7. **recordジョブのサイレント成功**: 各ジョブが独立した一時ワークスペースで動くため、
   配備ジョブが書き出す検証結果ファイル（相対パス）を記録ジョブが読めず、対象ファイルが
   0件のまま空振りしてジョブが正常終了（exit 0）していた。secrets未登録の間はこの欠陥が
   別のエラー（設定未登録）に隠れて気づかれなかった。永続的な絶対パスでの受け渡しへ変更した
8. **監査記録の回数表記のずれ**: 段階的移行の「5回」をrun単位で決裁したが、自動生成コメントの
   「第N回」表記はホスト単位（1回のrunで2件生成）の通し番号だったため、後から記録だけを
   見た者が回数を誤解しうるリスクがあった。コメントへrun idを併記することで解消した

### 3.3 現在の状態

## 4. 構造的な論点・課題（相談の核心）

1. **「静的には正しいが実機で異なる」型が8件連続した**: 単体テスト・コードレビューでは
   検出できず、実際にジョブを走らせて初めて判明する欠陥（SSHクライアントの識別情報選択、
   Forgejo Actionsのエフェメラルワークスペース、forced commandとのメタ文字衝突等）が
   連続した。これは個々の実装ミスというより、**CI/CD基盤特有の実行時制約
   （ジョブの隔離・SSHクライアントの暗黙的挙動）を、設計段階で十分に列挙できていなかった**
   ことが根本原因と考えられる

2. **段階的ロールアウトの意義**: 8件の欠陥はいずれも「まず手動ディスパッチ（`workflow_dispatch`）
   で試し、実際にmainを動かさずに実機検証を繰り返す」運用の中で発見された。もし最初から
   `push:[main]`のみで本番投入していれば、実際のmain反映のたびに欠陥へ遭遇していた可能性が
   高い。段階的な確認手段（手動トリガーの保持）が、結果的に安全網として機能した

3. **検証密度の低下と自動記録の設計**: 「全件検証→抜き取り検証」への移行を、機械的な監査記録
   （毎回生成されるRedmineコメント）で補う設計としたが、記録の表記（通し番号の単位）が
   決裁の単位（run単位）とずれるリスクを事前に想定しきれず、実装後に発見・是正する形になった

4. **セキュリティ境界の多層性**: 配備専用鍵・forced command・SSH設定の隔離・内部情報の
   版管理除外、といった複数の防御層を積み重ねる過程で、層同士の相互作用（例: 制限を
   強めるほど正当な操作まで拒否されるリスク）を都度確認する必要があった

## 7. 追記（2026-08-01・9件目の欠陥＝「検証済み」という記録自体の誤り）

段階的移行（最初の5回は査による事後独立検証を要求する采決裁）の実施記録に、**記録の伝言過程で
事実が徐々に誇張される**という新種の欠陥が見つかった。

### 7.1 経緯

査が「run181のジョブ状態確認（Forgejo API経由・成功）を行った」という事実が、計から采への
要約時に**「sa独立実測でも同一結果を確認済み」**という表現に変わった。この「独立実測」という
語が、実際には「APIでのジョブステータス確認」に過ぎなかったものを、より厳格な**「事後独立検証
（実機ホストへのssh等を伴う突き合わせ）」であるかのように読める表現**になっていた。

采がこの要約を受け取り、自身の別回答の中で「run181（deploy成功・査の全件独立検証済み）＝
1回目」とさらに踏み込んだ表現で記述し、これが計によりRedmineのjournalへそのまま転記された。
結果、実際には査による正式な事後独立検証が一度も行われていない回について、「検証済み・合格」
という記録がRedmineという恒久的な一次記録に残ってしまった。

### 7.2 発覚の経緯

この誤りは、直接の関係者（査自身）が**自らの全報告書・全Redmineコメントを棚卸しし**、
「事後独立検証（実機ホストへの接続を伴う）」を実施した回と「ジョブ状態のAPI確認のみ」を
行った回を再区分した結果、発覚した。査は「合格判定を出したかどうか」ではなく「何を確認する
行為として実施したか」を厳密に切り分けて棚卸ししたことで、伝言による意味の変質を検出できた。

その後、計は自らの発言（04:32:31の要約）と采の発言（05:12:49の回答）のどちらが誤りの発端かを
時系列で追跡し、**自分自身の要約表現の不正確さが発端であった**ことを認めた。

### 7.3 是正内容

- Redmineの該当journal・CLAUDE.mdの記述を、正確な内容（実際に査の正式な事後独立検証が
  完了したのは1回のみ）へ訂正
- 段階的移行のカウント方式を「査による正式な事後独立検証（実機ホストへの接続を伴う）が
  完了した回のみを1回として数える」へ明確化。過去の「発生した回数（run数）」との混同を防ぐ
- 訂正後、正しいカウント方式のもとで新たに1回の正式な事後独立検証が完了し、現在2/5

### 7.4 構造的な論点（追加）

6. 「検証済み」という記録それ自体が、複数の主体を経由する伝言（査→計→采→Redmine）の過程で
   徐々に厳密さを失い、実施されていない検証が「実施済み・合格」として恒久記録に残ってしまう
   リスクが実際に顕在化した。この種の「メタ的な誤り」（成果物や設定の誤りではなく、
   *検証行為が行われたことの記録自体*の誤り）を防ぐには、どのような構造的な対策が
   考えられるか（例: 検証の実施主体が必ず一次情報として直接記録し、要約や伝言を経由した
   表現をそのまま恒久記録へ転記することを禁じる、等）

7. この欠陥は、別の関係者（査）が自身の作業record を独立に棚卸しした結果として発見された。
   これは「検査対象の成果物を検査する」のではなく「検査という行為自体の実施記録を検査する」
   活動に近い。品質保証プロセスにおいて、こうした「メタ検証（検証が本当に行われたかの検証）」
   をどの頻度・どのタイミングで組み込むべきか、一般的な指針があれば助言がほしい
