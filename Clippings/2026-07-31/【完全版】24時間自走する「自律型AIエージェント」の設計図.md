# 【完全版】24時間自走する「自律型AIエージェント」の設計図

「寝ている間も、AIが仕事を進めてくれたら」

そう考えて、AIエージェントを作り始める人は増えています。

朝になれば、最新ニュースが整理されている。

X投稿の下書きが完成している。

問い合わせが分類され、返信案まで作られている。

コードがレビューされ、修正候補がまとめられている。

理想だけを見れば、AIエージェントは24時間働く社員のように見えます。

しかし、実際に長時間動かしてみると、多くの人が同じ壁にぶつかります。

- 最初は動くのに、数時間後から判断がズレる
- 同じ処理を何度も繰り返す
- 複数のエージェントが同じ仕事を始める
- 誰が何を担当しているのか分からなくなる
- 失敗しているのに処理だけは続く
- API料金やクレジットだけが減っていく
- 人間が監視しないと怖くて放置できない

ここで理解しておくべきことがあります。

**AIエージェントを作れることと、壊れずに運用できることは、まったく別の技術です。**

一度だけ動くデモなら、比較的簡単に作れます。

本当に難しいのは、数時間、数日、数週間と動かし続けても、

- 失敗したら安全に止まる
- 状態を失っても途中から再開できる
- 同じ処理を重複させない
- 与えられた権限を越えない
- コストが上限を超えない
- 人間が後から行動を追跡できる

という運用の仕組みを成立させることです。

つまり、24時間自走するAIエージェントの本質は、AIを増やすことではありません。

> **一度も止まらないことではなく、壊れても安全に止まり、原因を残し、正しい地点から再開できること。**

この記事では、Claude Codeの/loop、Routines、Hooks、Claude Agent SDK、Managed Agentsなどを整理しながら、長時間運用できるAIエージェントの設計方法を、実務レベルまで具体的に解説します。

特定のサービスを一つ選ぶだけでは完成しません。

先に作るべきなのは、**壊れにくく、止められ、再開できる構造**です。

# ■ 最初に結論

## 24時間運用は「AIの賢さ」ではなく「システム設計」で決まる

AIエージェントが長時間動かない原因を、モデルの性能不足だと考える人は少なくありません。

しかし、モデルを高性能に変えても、次の問題は残ります。

- 同じジョブが二重に実行される
- 外部APIが落ちたときに無限リトライする
- 成功と失敗の状態が保存されない
- 過去の会話が膨らみ、判断が不安定になる
- 依頼されていない操作まで行う
- 途中で落ちると最初からやり直す
- 失敗した理由を後から確認できない

これらは、モデルの知能ではなく、周囲の設計によって決まります。

長時間動くエージェントを作るときは、全体を次の4層へ分けて考えます。

## ■ 第1層：Trigger｜いつ始めるか

- 毎朝9時
- 1時間ごと
- GitHubでPRが作成されたとき
- フォームが送信されたとき
- Slackで特定の絵文字が付いたとき
- APIから呼び出されたとき

## ■ 第2層：Workflow｜何をどの順番で進めるか

- 情報を取得する
- 重複を除く
- AIへ判断させる
- 結果を保存する
- 人間へ通知する
- 承認後に外部へ反映する

## ■ 第3層：Agent｜どこで考えさせるか

- 内容を分類する
- 重要度を評価する
- 要約する
- 返信案を考える
- 問題の原因を調査する
- 次の行動候補を選ぶ

## ■ 第4層：Guardrail｜どこで止めるか

- 同じ処理は最大3回まで
- 外部送信は承認制
- 予算を超えたら停止
- 本番環境は読み取りのみ
- 削除操作は禁止
- 失敗時は人間へ通知
- 一定時間を超えたらタイムアウト

多くの失敗は、この4層を一体化し、すべてをAIへ判断させることで起きます。

例えば、次のような依頼です。

毎朝ニュースを集めて、 重要度を判断し、 記事を書き、 画像を生成し、 Xへ投稿し、 反応を見て改善してください。

一見すると、理想的な自動化に見えます。

しかし、この一文には、

- 決まった手順
- 創造的な判断
- 外部への書き込み
- 繰り返し処理
- 評価
- 改善
- 公開権限

がすべて混ざっています。

最初から全自動にすると、どこで失敗したのか分かりません。

まずは、機械的に決められる部分をコードやワークフローへ移し、判断が必要な部分だけをAIへ渡します。

# ■ まず作るべきは「AIエージェント」ではなく「状態機械」

24時間運用で最も重要なのは、会話を続けることではありません。

**現在の仕事が、どの状態にあるのかを明確にすること**です。

例えば、AIニュース収集エージェントなら、状態を次のように分けます。

queued ↓ collecting\_sources ↓ deduplicating ↓ ranking ↓ summarizing ↓ awaiting\_approval ↓ publishing ↓ completed

失敗した場合は、

retry\_wait failed cancelled

へ移動します。

このように状態を定義しておけば、エージェントが途中で停止しても、

- どこまで終わっているか
- 次に何をすべきか
- 再実行してよいか
- 人間の確認が必要か

を判断できます。

反対に、状態が会話の中にしか存在しない設計では、セッションが切れた瞬間に現在地を失います。

24時間動かすなら、AIに長い記憶を持たせるより、**仕事の状態を外部へ持たせること**が先です。

# ■ AIエージェントが長時間運用で壊れる5つの理由

# 理由1：コンテキストを「永続的な記憶」と勘違いする

![画像](https://pbs.twimg.com/media/HOcPIw4aYAAd_LP?format=jpg&name=large)

長時間動かすと、会話、ツール結果、読み込んだファイル、エラー、修正履歴が増えていきます。

コンテキストウィンドウが大きくても、すべての情報を同じ精度で扱い続けられるわけではありません。

情報が増えるほど、

- 重要な制約が埋もれる
- 古い状態と新しい状態が混ざる
- 一度解決した問題を再調査する
- 過去の誤った推測が残る
- 今回と関係のない情報が判断へ影響する

といった問題が起きます。

長時間運用では、会話履歴をそのまま記憶として使ってはいけません。

最低限、次の状態を外部へ保存します。

{ "job\_id": "news-2026-07-30", "workflow\_version": "1.2.0", "status": "ranking\_completed", "current\_step": "summarizing", "processed\_items": 42, "selected\_items": 5, "retry\_count": 0, "cost\_usd": 0.84, "next\_action": "generate\_summaries", "updated\_at": "2026-07-30T09:18:00+09:00" }

エージェントが再起動しても、この状態を読めば続きから進められます。

会話の流れを覚えていることより、**現在地と次の行動が保存されていること**の方が重要です。

# 理由2：圧縮された会話へ依存する

![画像](https://pbs.twimg.com/media/HOcO49obYAAbSQB?format=jpg&name=large)

Claude Code には「Compaction（圧縮）という機能があります。 コンテキストが満杯になってきたら、過去の会話を要約して、新しい会話のスペースを空ける仕組み。 長いセッションでは、過去の会話が要約・圧縮されることがあります。 圧縮は、コンテキストを空けるうえで有効です。

しかし、要約には必ず情報の損失があります。

特に消えやすいのが、次の情報です。

- なぜその設計を選んだのか
- どの候補を却下したのか
- 一時的な例外条件
- 未完了の作業
- 担当範囲の境界
- 正確な数値やID
- 失敗した試行
- 人間が承認した内容

したがって、重要な情報は会話の外へ出します。

## 外部へ保存するもの

- ジョブ状態
- 完了済みの工程
- 未処理項目
- 重要な意思決定
- エラー履歴
- 成果物の保存先
- 承認履歴
- 実行コスト
- 使用した入力データの識別子

コンテキストは思考のために使い、状態管理はシステムへ任せます。

# 理由3：テキストルールを「強制装置」として使う

![画像](https://pbs.twimg.com/media/HOcPRIyaYAAK6J-?format=jpg&name=large)

CLAUDE.mdへ、

本番環境を絶対に変更しないでください。

と書くことは大切です。

しかし、文章は方針であり、物理的な制限ではありません。

本当に本番環境へ書き込ませたくないなら、

- 読み取り専用の認証情報を使う
- 書き込みツールを渡さない
- 対象ディレクトリを制限する
- Hookで危険操作をブロックする
- 実行環境を分離する
- ネットワークの接続先を限定する

必要があります。

24時間動くエージェントにとって、文章だけの禁止は弱い設計です。

> **守られなければ困るルールは、プロンプトではなく権限・コード・実行環境で守る。**

これが基本です。

# 理由4：失敗したときの挙動を決めていない

正常に動く手順だけを考え、失敗時の行動を決めていないエージェントは、必ずどこかで止まります。

例えば、ニュース取得APIが失敗した場合。

- すぐ再試行するのか
- 何秒待つのか
- 最大何回試すのか
- 一部だけ取得できたら続けるのか
- 人間へ通知するのか
- 次回の実行へ持ち越すのか

を事前に決める必要があります。

悪い設計は、次です。

失敗したら、成功するまで再試行してください。

良い設計は、次です。

一時的な通信エラーのみ再試行する。 待機時間は30秒、2分、10分とし、 最大3回まで実行する。 認証エラー、権限不足、入力不備は再試行せず停止する。 3回失敗した場合は、 ジョブ状態をfailedへ変更し、 エラー内容、最後に成功した工程、 再開方法をSlackへ通知する。

AIに判断させる前に、エラーの種類と停止条件を決めます。

# 理由5：AIを増やせば速くなると思う

リサーチ担当、構成担当、執筆担当、編集担当、検証担当。

役割を分けると、立派なAI組織に見えます。

しかし、エージェントを増やすと、次のコストも増えます。

- 引き継ぎ
- 状態同期
- 重複作業
- 出力形式の調整
- コンテキストの複製
- 権限管理
- 失敗箇所の追跡
- 実行コスト
- 競合状態

独立して並列化できる仕事なら、複数エージェントは有効です。

一方、前工程の結果を待つ必要がある仕事を無理に分けると、引き継ぎコストの方が大きくなります。

最初は、1体のエージェントが小さなワークフローを順番に進める設計で十分です。

複数エージェントへ分けるのは、次の条件を満たす場合だけにします。

- 作業が明確に独立している
- 同時に進める意味がある
- 入出力形式が固定されている
- 失敗した作業だけ再実行できる
- 権限を役割ごとに分離できる
- 同じデータを同時更新しない
- コスト増加に見合う時間短縮がある

# ■ 壊れにくいAIエージェントを作る7つの設計原則

# 原則1：AIへ渡すのは「判断」だけにする

すべてをAIへ任せると、自由度が高すぎて結果が安定しません。

まず、処理を2種類へ分けます。

## 決定的な処理

同じ入力なら、同じ結果になってほしい作業です。

- APIからデータを取得する
- 日付で絞り込む
- 重複を削除する
- JSONを保存する
- Slackへ通知する
- ファイル名を変更する
- 数値を集計する
- スキーマを検証する

これらは、コードやワークフローで実行します。

## 非決定的な処理

文脈を読み、判断する必要がある作業です。

- 重要なニュースを選ぶ
- 読者に合う切り口を考える
- 問い合わせの意図を分類する
- コードの問題点を分析する
- 返信文を作成する
- 複数案から最適な案を選ぶ

ここだけをAIへ渡します。

例えば、AIニュース収集なら次の構造です。

\[コード\] RSS・APIから記事を取得 ↓ \[コード\] 日付、URL、タイトルで重複削除 ↓ \[AI\] 重要度と読者への関連性を評価 ↓ \[AI\] 上位5件を要約 ↓ \[コード\] JSONスキーマを検証 ↓ \[コード\] Notionへ保存 ↓ \[コード\] Slackへ通知

AIの担当範囲が狭いほど、テストと改善が簡単になります。

# 原則2：各工程に「完了条件」を持たせる

「ニュースを調べる」のような曖昧なタスクは、いつ終わったのか判定できません。

工程ごとに、入力、出力、完了条件を定義します。

## リサーチ工程

入力：

対象媒体：5件 対象期間：過去24時間 最大取得件数：100件

完了条件：

- 指定した5媒体を確認済み
- 過去24時間の記事だけを対象
- URLとタイトルの重複を除去済み
- 最低10件を取得
- 各記事に取得時刻と出典URLがある

## 要約工程

出力：

{ "selected\_articles": \[ { "title": "", "source\_url": "", "importance\_score": 0, "reason": "", "summary": "" } \] }

完了条件：

- 上位5件を選定
- 各要約は200文字以内
- 事実と推測を分離
- 元URLを保持
- JSONスキーマへ適合
- 重要度の理由を記載

完了条件があれば、AI自身の「できました」ではなく、システム側で判定できます。

# 原則3：状態を外部へ保存する

24時間運用では、セッションが落ちることを前提にします。

状態を保存していなければ、再起動するたびに最初からやり直します。

最低限、次を保存します。

{ "job\_id": "weekly-content-2026-W31", "workflow\_version": "1.0.0", "status": "running", "current\_step": "draft\_review", "completed\_steps": \[ "source\_collection", "deduplication", "topic\_selection", "draft\_generation" \], "pending\_steps": \[ "draft\_review", "human\_approval", "publication" \], "retry\_count": 1, "idempotency\_key": "weekly-content-2026-W31", "last\_error": null, "cost\_usd": 1.42, "updated\_at": "2026-07-30T09:00:00+09:00" }

保存先は、用途に応じて選べます。

- 小規模：JSON、SQLite
- チーム運用：PostgreSQL
- 長時間ワークフロー：[Trigger.dev](https://trigger.dev/)など
- クラウドエージェント：サービス側のセッション・イベント履歴

重要なのは、会話を再現することではありません。

**仕事の現在地を復元できること**です。

# 原則4：重複実行を「冪等性」で防ぐ

24時間運用では、同じイベントが複数回来ることがあります。

例えば、

- Webhookが再送される
- タイムアウトしたため再実行される
- 人間が誤って二度起動する
- スケジュールとAPI呼び出しが重なる

このとき、同じ投稿を二度公開したり、同じ顧客へ二度メールを送ったりしてはいけません。

そこで、各ジョブに一意のidempotency\_keyを持たせます。

news-summary:2026-07-30 invoice-reminder:customer-123:2026-07 x-post:campaign-88:post-03

処理開始前に、次を確認します。

このidempotency\_keyのジョブがcompletedなら、何もしない。 runningなら、既存ジョブの状態を返す。 failedなら、再開条件を確認する。 未作成なら、新規ジョブとして開始する。

特に、送信、公開、課金、削除のような副作用がある処理には必須です。

# 原則5：リトライに上限と種類を持たせる

リトライは便利ですが、無制限にすると最も危険な機能になります。

エラーを、少なくとも次の3種類へ分けます。

## 再試行してよいエラー

- 一時的なネットワーク障害
- レート制限
- サービスの一時停止
- タイムアウト
- 5xxエラー

## 人間の確認が必要なエラー

- 入力データの意味が曖昧
- 想定外の形式
- 重要な仕様の不一致
- 成果物が品質基準を満たさない
- AIの判断が低信頼

## 再試行してはいけないエラー

- 認証情報が無効
- 権限不足
- 対象が存在しない
- 禁止された操作
- 予算上限超過
- 入力値が不正

さらに、次を必ず決めます。

- 最大試行回数
- 待機時間
- 累計コスト上限
- 失敗時の通知先
- 再開方法

一時エラーのみ最大3回再試行する。 待機時間は30秒、2分、10分と増やす。 同じツール呼び出しが5分以内に3回連続した場合は停止する。 累計コストが3ドルを超えた場合も停止する。 停止時は、エラー、最後の成功工程、再開方法をSlackへ通知する。

# 原則6：権限は最小限から始める

24時間動くエージェントは、人間が見ていない時間にも操作します。

したがって、対話型AIより厳しい権限設計が必要です。

最初から渡してはいけない権限があります。

- 本番データの削除
- 無制限の外部送信
- 任意のシェル実行
- 全リポジトリへの書き込み
- 決済や購入
- SNSへの無承認投稿
- 機密情報への広範なアクセス

段階的に権限を広げます。

## 段階1：読み取りのみ

データを取得し、下書きを保存する。

## 段階2：限定された書き込み

専用フォルダ、専用ブランチ、下書きチャンネルだけに書き込む。

## 段階3：承認後の外部操作

人間が確認した後で、公開・送信・マージする。

## 段階4：条件付き自動実行

十分な運用実績があり、ロールバック可能な処理だけを自動化する。

最初から完全自動を目指すより、安全な半自動を積み上げた方が、結果的に早く本番へ到達します。

# 原則7：Hookと監視で「守る・見る・止める」を仕組みにする

![画像](https://pbs.twimg.com/media/HOcSSv5aEAAfC9Y?format=jpg&name=large)

Claude CodeのHooksは、ライフサイクル上の特定イベントで、自動処理を実行できる仕組みです。

例えば、

- ツール実行前
- ツール実行後
- ファイル編集後
- セッション開始時
- セッション終了時
- タスク完了時

などに処理を挟めます。

Hookの価値は、モデルへお願いするのではなく、決定的な処理として実行できる点です。

## 例1：危険なコマンドを止める

rm -rf、本番DBへの直接操作、強制pushなどを検知してブロックします。

## 例2：編集後に検証する

ファイル編集後にformatter、lint、型チェック、テストを自動実行します。

## 例3：同一処理の連続実行を検知する

短時間に同じツール呼び出しが繰り返されたら停止・通知します。

## 例4：作業記録を保存する

タスク完了時に、実行内容、変更ファイル、検証結果をログへ保存します。

## 例5：外部操作の前に承認を求める

送信、公開、削除などの前に処理を停止し、人間へ確認します。

さらに、最低限次を記録します。

- 開始時刻
- 入力データ
- 使用したツール
- 出力結果
- エラー
- リトライ回数
- 実行コスト
- 承認者
- 状態遷移

運用で重要なのは、「成功したか」だけではありません。

**人間が後から理由を説明できること**です。

# ■ 実践例

## 毎朝AIニュースを届ける自律型エージェント

ここまでの設計を、一つの具体例へ落とします。

目的は、

> 毎朝8時にAIニュースを収集し、重要度の高い5件を要約して、Slackへ届ける

ことです。

## Trigger

毎日8:00

## Workflow

1\. 対象媒体から記事を取得 2. 24時間以内の記事だけ残す 3. URLとタイトルで重複削除 4. AIが重要度を評価 5. 上位5件を要約 6. JSON形式を検証 7. Notionへ保存 8. Slackへ通知

## Agentが判断する部分

\- どのニュースが重要か - 読者への関連性 - 要約 - 注目すべき理由

## コードで固定する部分

\- 記事取得 - 日付フィルタ - 重複削除 - JSON検証 - Notion保存 - Slack送信 - ジョブ状態更新

## Guardrail

\- 取得件数が0件なら停止 - AI評価は最大1回 - JSON不正時のみ最大2回再生成 - Slack送信は1ジョブ1回 - 1回の実行コスト上限は2ドル - 元URLがない要約は送信しない

## 状態データ

{ "job\_id": "daily-ai-news-2026-07-30", "idempotency\_key": "daily-ai-news-2026-07-30", "status": "summarizing", "article\_count": 38, "selected\_count": 5, "slack\_sent": false, "retry\_count": 0, "cost\_usd": 0.62 }

## 失敗時の処理

通信エラー： 最大3回再試行 認証エラー： 即停止してSlack通知 記事0件： warningとして通知して終了 JSON不正： 最大2回だけ再生成 Slack送信失敗： 要約結果は保存し、送信工程だけ再実行

このように工程を分ければ、AIが失敗しても全体を最初からやり直す必要はありません。

# ■ 24時間動かす方法は、用途によって選ぶ

設計ができたら、次に実行環境を選びます。

すべてを一つの方法で解決しようとしないことが重要です。

# 1．/loop｜その場で試す短時間の繰り返し

![画像](https://pbs.twimg.com/media/HOcQNcca8AAZ3wQ?format=jpg&name=large)

Claude Codeの/loopは、開いているセッション内でプロンプトを定期実行するための方法です。

/loop 10m PRの状態を確認し、完了したら結果を要約してください

向いている用途：

- デプロイ完了の監視
- ビルド状況の確認
- PRやIssueの短時間ポーリング
- 開発中の一時的な監視
- 自動化の試作

向いていない用途：

- PCを閉じても継続したい処理
- 数週間以上の永続運用
- 厳密な時刻が必要な基幹処理
- 完全無人の本番業務

/loopは、セッションが開いている間に使う軽量なスケジューリングです。

現在の公式ドキュメントでは、定期タスクは作成から7日で終了します。永続運用にはRoutinesやDesktopのスケジュール済みタスクなどが案内されています。

/loopは、本番運用の完成形ではなく、短時間で挙動を確認する実験環境として使うのが適しています。

# 2．Claude Routines｜PCを閉じても動く定期・イベント実行

![画像](https://pbs.twimg.com/media/HOcQV92aQAAkbPa?format=jpg&name=large)

Claude Routinesは、Anthropicが管理するクラウド環境でClaude Codeの処理を実行する仕組みです。

- スケジュール
- API呼び出し
- GitHubイベント

などをトリガーとして利用できます。

PCを閉じても動作するため、次のような処理に向いています。

- 毎朝の情報収集
- Issueの定期整理
- GitHub PRのレビュー
- デプロイ後の検証
- ドキュメント差分の監視
- Slackや外部サービスへの通知

Routinesは無人で実行されるため、実行中に承認ダイアログへ答えることはできません。

そのため、

- 接続するリポジトリ
- ブランチへのpush権限
- 使用するコネクタ
- ネットワークアクセス
- 環境変数
- 外部サービスの権限

を必要最小限へ絞る必要があります。

Routinesは現在リサーチプレビューで、挙動や制限は変更される可能性があります。定期実行の最小間隔は1時間です。

より短い間隔で監視するなら/loop、イベントへ即時反応するならAPIまたはGitHubトリガーを検討します。

# 3．Modal・Trigger.devなど｜決まったワークフローをクラウドで回す

![画像](https://pbs.twimg.com/media/HOcQaNqbYAA1dnq?format=jpg&name=large)

AIの判断がほとんど不要な場合は、Claude Codeを常時動かす必要はありません。

例えば、

- APIからデータを取得
- 形式を変換
- データベースへ保存
- 通知を送信

という処理は、通常のサーバーレス基盤や永続ワークフロー基盤で十分です。

## Modalが向いている場面

- Python中心
- バッチ処理
- データ処理
- 必要なときだけ計算資源を使いたい
- AI以外の処理が中心

## Trigger.devが向いている場面

- TypeScript中心
- 長時間ワークフロー
- ステップ単位の再試行
- ジョブ状態の追跡
- イベント駆動処理

AI判断が必要なら、その工程だけAPIまたはAgent SDKを呼びます。

ワークフロー全体をAIにするのではなく、**AIを一つの処理部品として組み込む**のがポイントです。

# 4．Claude Agent SDK｜自分のアプリ内でエージェントを動かす

![画像](https://pbs.twimg.com/media/HOcQdUca0AAsuHX?format=jpg&name=large)

Claude Agent SDKは、Claude Codeを支えるエージェントループやツール利用を、自分のPython・TypeScriptアプリケーションへ組み込むためのSDKです。

向いている用途：

- 自社サービスへエージェントを組み込む
- 独自UIからClaudeを動かす
- 自分のインフラでジョブを管理する
- ツールや権限を細かく制御する
- 複雑なエージェントワークフローをコード化する

Agent SDKは自由度が高い一方で、周辺の運用は自分で設計します。

- 実行環境
- スケジューリング
- データ保存
- キュー
- 監視
- リトライ
- シークレット管理
- コスト制御

「SDKを使えば24時間動く」のではありません。

SDKは、エージェントの頭脳と実行ループを提供します。

24時間運用に必要な身体と運用体制は、自分で作ります。

# 5．Managed Agents｜実行基盤の管理を減らす

![画像](https://pbs.twimg.com/media/HOcQgzebQAAVK3T?format=jpg&name=large)

Managed Agentsは、Anthropicがエージェントの実行基盤を提供するサービスです。

モデル、システムプロンプト、ツール、MCP、Skillsなどを定義し、Anthropic管理またはセルフホスト型のサンドボックスでセッションを実行できます。

向いている用途：

- 長時間・非同期エージェントを動かしたい
- 自前でサンドボックスを管理したくない
- セッションやイベント履歴を保存したい
- APIからエージェントを起動したい
- 再利用可能なエージェント設定を持ちたい

Managed Agentsは、長時間実行、ステートフルなセッション、イベント履歴の永続化などを提供します。

一方で現在はベータ版であり、データ保持やコンプライアンス要件も含めて確認が必要です。

Agent SDKとの違いは、誰が実行基盤を管理するかです。

- Agent SDK：自分のプロセスとインフラで動かす
- Managed Agents：Anthropic管理またはセルフホスト環境を利用する

細かい制御が必要ならAgent SDK。

基盤管理を減らし、エージェント開発へ集中したいならManaged Agentsが候補になります。

# ■ 最初のAIエージェントは「1時間・1体・1業務」で作る

初心者が最初から作るべきなのは、24時間完全自動で働く巨大なAI組織ではありません。

次の条件で始めます。

- 実行時間：1時間以内
- エージェント数：1体
- 対象業務：1つ
- 外部書き込み：下書きのみ
- 再試行：最大2〜3回
- 人間の承認：公開前に必須

例えば、AIニュース収集なら次です。

## 第1段階

毎朝ニュースを取得し、候補をSlackへ送る。

AI判断なし。

## 第2段階

AIが重要度を付け、上位5件を要約する。

外部公開はしない。

## 第3段階

AIがX投稿の下書きを作る。

人間が確認する。

## 第4段階

承認された投稿だけ、予約投稿へ登録する。

## 第5段階

十分な運用実績ができた一部だけ、自動実行する。

この順番なら、失敗した工程を特定できます。

いきなり全自動にすると、取得、判断、生成、公開のどこで壊れたのか分かりません。

# ■ 本番投入前に確認する15項目

- 1ジョブに一意のIDがある
- 二重実行を防止できる
- 現在の状態を外部保存している
- 途中から再開できる
- 各工程に完了条件がある
- AIの出力形式を検証している
- リトライ回数に上限がある
- タイムアウトがある
- コスト上限がある
- 読み取りと書き込み権限を分けている
- 削除・公開・課金は承認制になっている
- 同じツールの連続実行を検知できる
- 失敗時に通知される
- 実行ログを後から確認できる
- 人間が緊急停止できる

一つでも答えられない項目があるなら、まだ完全自動へ進める段階ではありません。

# ■ まとめ

## 最強のAIエージェントは、止まらないエージェントではない

24時間動くAIエージェントを作るとき、多くの人は、

- 何体作るか
- どのモデルを使うか
- どのサービスへデプロイするか

から考えます。

しかし、本当に重要なのは、その前です。

- AIへ任せる判断を限定する
- 決まった処理はコードへ移す
- 状態を外部へ保存する
- 二重実行を防ぐ
- リトライへ上限を付ける
- 権限を最小限にする
- Hookで重要な制約を強制する
- ログと通知で観測可能にする
- 失敗しても続きから再開できるようにする

この土台がなければ、どれだけ高性能なモデルを使っても、長時間運用では不安定になります。

反対に、設計ができていれば、最初は1体の小さなエージェントでも、確実に業務を進められます。

最強のAIエージェントとは、24時間一度も止まらない存在ではありません。

> **異常を検知して安全に止まり、原因を残し、必要な地点から再開できる存在です。**

最初から何十体ものエージェントを作る必要はありません。

まずは、1体に、1つの業務を、1時間だけ任せてください。

そして、成功したかどうかより先に確認します。

- 失敗したら止まれるか
- 何をしたか追跡できるか
- 同じ処理を重複しないか
- 途中から再開できるか
- 人間が安全に引き継げるか

ここまでできて初めて、「任せられるAIエージェント」になります。
