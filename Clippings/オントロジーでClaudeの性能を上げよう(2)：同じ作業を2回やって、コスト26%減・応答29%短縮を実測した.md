第1回ではオントロジーという概念そのものを扱いました。今回は実践編です。Claude Codeに知識グラフを持たせる手順を示したうえで、まったく同じ作業を「グラフあり」「グラフなし」で1回ずつ実行し、コストと時間とトークンと中身を比較します。

結論を先に置きます。**コストは約26パーセント減、API応答時間は約29パーセント短縮、キャッシュ読み取りトークンは約33パーセント減**でした。

![画像](https://pbs.twimg.com/media/HOKQUy8bkAAvl2o?format=jpg&name=large)

# 先に用語を整理します

本題に入る前に、この記事で使う言葉の意味をおさらいしておきます。

## オントロジー

**ある領域に登場する概念と、概念どうしの関係を、機械が読める形で明示的に書き下したもの**です。

もとは哲学の用語（存在論）ですが、情報科学では上の意味で使われます。人工知能研究者のトム・グルーバーによる「概念化の明示的な仕様」という定義が有名です。

難しく聞こえますが、やっていることは単純です。「AとBはこういう関係にある」という、頭の中にしかない了解を、外に取り出して文字にする。それだけです。新しいデータを作るのではなく、すでにあるデータに意味の層をかぶせる作業だと考えてください。

## 知識グラフ

オントロジーを、点と線のネットワークとして表現したものです。実務上はオントロジーとほぼ同じ意味で使っています。

## エンティティ（entity）

グラフの点にあたるもの。登場する要素そのものです。種類（type）を付けて登録します。

x-collect (type: Skill) browser-use (type: ExternalTool) articles/industry (type: OutputStore)

## リレーション（relation）

グラフの線にあたるもの。要素どうしの関係です。ここが最も重要な部分になります。

x-collect --writes-to--> references/x-collect x-collect --uses--> browser-use

線に名前が付いているところが要点です。「関係がある」ではなく「書き込む関係がある」「使う関係がある」と、型で区別されています。

## オブザベーション（observation）

各エンティティに添える短い説明です。役割や制約を1行から2行で書きます。

x-collect: 指定トピックでXをバズ順検索し、上位20件を保存する

## MCP（Model Context Protocol）

AIと外部ツールをつなぐための共通規格です。この記事で知識グラフを持たせるときも、このMCP経由でサーバーを追加します。Claude Code本体にも内部の記憶機能がありますが、そちらとは別系統です。詳しくは導入手順のあとで触れます。

> **【補足】** Claude Codeには、これとは別に内部のメモリ機能があります。Claudeが作業内容を自動で保存していく仕組みで、ここで入れるMCPのメモリサーバーとは系統が違い、中身が同期することもありません。 MCPのほうを使うのは、管理と見た目の分かりやすさが理由です。保存先を自分で決められて、中身をテキストとしてそのまま読めて、間違いがあれば手で直せます。自動で溜まる記憶は手間がかかりませんが、何が入っているのかを確認しづらく、構造もありません。

ここから先は実践に入ります。

# そもそもAIの精度が上がらない理由

Claude Codeを使い込んでいる人ほど、この壁にぶつかります。

指示は丁寧に書いた。CLAUDE.mdにもルールを足した。関係しそうなファイルは@で全部指定した。それでも、日によって答えの質が変わる。同じことを聞いても、前回と違う結論が返ってくる。

原因を「AIの気まぐれ」で片付けたくなりますが、実際はもう少し構造的な問題です。

## 資料は並んでいるが、つながっていない

order-service.md と payment-service.md があるとします。どちらも丁寧に書かれています。仕様も、責務も、エラー処理も網羅されている。

では、この2つがどう連携しているかは、どのファイルに書いてありますか。

たいてい、どこにも書いてありません。書き手にとっては自明だからです。自明なことは、ドキュメントに書かれない。これがあらゆる社内資料に共通する構造的な穴です。

AIはこの穴を推測で埋めます。ファイル名から推測し、関数名から推測し、文脈から推測する。だいたい当たります。だいたい、というのが問題です。5回に1回外れると、その1回が「なんか今日は調子が悪い」の正体になります。

つまり、こういうことです。

- **ある**：情報の保存、名前付け、分類、検索
- **ない**：情報どうしの関係と、それを辿る手段

## 資料を足すと、かえって悪化することがある

ここが直感に反する部分です。

不安になって関連ファイルを追加すると、多くの場合そのぶんノイズも増えます。長いマルチターンの作業ではコンテキストが汚れていき、精度が落ちるという報告もあります。

段ボールを増やしても、ラベルがなければ探索コストが増えるだけです。

# AIに関係を入れるとは何をすることか

ここでオントロジーが出てきます。やることは3つだけです。

1. 登場する要素を、種類を付けて登録する（エンティティ）
2. 要素どうしのつながりを、型を付けて登録する（リレーション）
3. 各要素に短い説明を足す（オブザベーション）

具体例です。このリポジトリを解析させたとき、実際に登録されたものはこういう形をしています。

エンティティ: x-collect （型: Skill） articles/industry （型: OutputStore） browser-use （型: ExternalTool） リレーション: x-collect --writes-to--> references/x-collect x-article --reads-from--> references/x-collect x-collect --uses--> browser-use claude-code --delegates-to--> x-article オブザベーション: x-collect: 指定トピックでXをバズ順検索し上位20件を保存する

矢印に名前が付いているところが要点です。「関係がある」ではなく「書き込む関係がある」「委譲する関係がある」と型で区別されています。

Claudeはこれを読むと、ファイルを開かずに構造を答えられます。しかも2段階以上辿れます。「references/x-collect を読むスキルは何か」から「そのスキルの成果物はどこに出るか」まで、線を辿るだけで到達します。

# なぜ速くなり、なぜ正確になるのか

ここを飛ばすと、あとの実測データが「なんとなく減った」で終わってしまいます。仕組みから説明します。

## スピードが上がる理由：探索が消える

グラフがない状態で「決済まわりの構成を教えて」と聞いたとき、Claudeの中では次のことが起きています。

1\. ファイル一覧を取得する 2. 関係しそうな名前のファイルを開く 3. 読む 4. 違った。次を開く 5. 3〜4を繰り返す 6. ようやく必要な情報が揃う

このうち、2から5がまるごと無駄になる可能性を含んだ工程です。しかも開いたファイルの中身は、外れだった分も含めて全部コンテキストに残ります。トークンを消費し、時間を消費します。

グラフがあると、この工程が置き換わります。

1\. payment に関係するノードを検索する 2. その周辺の関係を辿る 3. 終わり

ファイルを開く回数がゼロになる場面が出てきます。読む量が減れば、そのまま処理時間と費用が下がります。この記事の後半で示す「応答時間29パーセント短縮」は、ここから来ています。

## 精度が上がる理由1：推測が減る

AIは、書かれていない部分を必ず推測で埋めます。

order-service.md と payment-service.md の間に関係が書かれていなければ、Claudeはファイル名や関数名から関係を推理します。だいたい当たりますが、推理なので毎回わずかに揺れます。

同じ質問なのに日によって答えが変わる現象は、推測の余地が残っていることが原因です。関係を明示した分だけ、その揺れが消えます。

## 精度が上がる理由2：嘘をつける範囲が狭くなる

関係を「決められた型から選ぶ」形にすると、選べる選択肢が有限になります。

自由に文章を書かせれば、もっともらしい嘘はいくらでも作れます。writes-toreads-from uses の3択なら、作れる嘘はその3つの中に限られます。しかも、存在しないノードとはつなげられません。

ハルシネーションは自由度の高いところで起きます。型を決めるのは、その自由度を構造的に下げる作業です。

## 精度が上がる理由3：渡す情報が濃くなる

AIは、情報を多く渡すほど賢くなるわけではありません。関係ない情報が混ざるほど判断がぶれます。長い作業を続けるとコンテキストが汚れ、精度が落ちていくという報告もあります。

グラフは「関連するノードだけを濃く渡す」ことを可能にします。ファイル10個を丸ごと渡す代わりに、ノード5個と関係8本を渡す。情報量は減っているのに、答えの質は上がります。

減らすことで良くなる、というのがこの仕組みの面白いところです。

# CLAUDE.mdとの違い

「それ、CLAUDE.mdに書けばよくない？」と思った方へ。役割が違います。

![画像](https://pbs.twimg.com/media/HOE_7HlbEAAdD5W?format=png&name=large)

決定的な差はここです。CLAUDE.mdは毎回全部読まれます。だから長くすると、毎回のコストが確実に増えます。一方の知識グラフは、Claudeが必要と判断したノードだけを検索して取ってきます。

私の感覚では、**ルールはCLAUDE.md、事実はグラフ**という分担が一番きれいに収まります。「インデントはスペース2つ」はCLAUDE.mdです。「x-collectはbrowser-useを使う」はグラフです。

# Claude Codeにオントロジーを入れる手順

実際の導入は3ステップで終わります。所要時間は初回で10分もかかりません。

## ステップ1：memory MCPサーバーを追加する

MCP（Model Context Protocol、AIと外部ツールをつなぐ共通規格）のメモリサーバーを入れます。ターミナルで1行です。

```text
# 知識グラフを保存するMCPサーバーを追加する
claude mcp add --transport stdio memory -- npx -y @modelcontextprotocol/server-memory
```

グラフの実体は memory.jsonl という1行1レコードのテキストファイルです。中身は普通に開いて読めます。ブラックボックスではありません。

初回起動時に「Pending approval」と出たら承認してください。MCPの初回起動は、一度セッションを閉じてからサイド開いて、許可をする必要があります。この許可は最初の一度だけ求められます。

## ステップ2：Claudeにグラフを作らせる

ここが山場です。とはいえ、やることは指示を1つ出すだけです。Claude Codeを起動して、次のプロンプトをそのまま貼り付けてください。

```text
このプロジェクトを読んで、構造を知識グラフとして memory に登録してください。

- 登場する要素には、それぞれ種類(entities)を付ける
- 要素どうしのつながりには、「何をする関係か(relations)」が分かる名前を付ける
- 各要素が何を担当しているかを、1行の説明(observations)として添える
```

これだけです。3行しかありませんが、必要なことは全部入っています。

- 何を調べるか：主要なモジュール・サービスと、その依存・呼び出し関係
- どこに記録するか：memory
- どういう形で記録するか：entities（種類つき）とrelations
- 補足情報：observationsに短く

Claudeはこれを受けて、コードベースを読み、create\_entitiescreate\_relations add\_observations の3つのツールを順に呼びます。私のリポジトリでは、31個のエンティティと69個のリレーションが登録されました。作業時間は数分です。

## 精度を上げたい場合は型を指定する

上のプロンプトのままでも動きます。ただし、後で辿りやすいグラフにしたいなら、関係の型をこちらから決めたほうがいいです。

型を指定すると、Claudeは同じ意味の関係を同じ名前で登録します。表記が一致し検索精度が上がるでしょう。

型を固定する場合は、以下のように書き足します。(これは一例なので、自分のプロジェクトに沿うように変更してください)

```text
このリポジトリの主要なモジュール・サービスと、その依存・呼び出し関係を調べて、
memory に entities（種類つき）と relations として記録して。
各要素の役割は observations に短く添えて。

entities の種類は次から選ぶこと:
  Service / Database / ExternalAPI / Config / Library

relations の型は次から選ぶこと:
  calls / depends-on / owns / configures / uses
```

## ステップ3：グラフを確認する

登録内容は以下のようなプロンプトでいつでも確認できます。

```text
今の知識グラフの中身を見せてください（read_graph）
```

```text
x-collect に関係する要素だけ出してください（search_nodes）
```

この段階で明らかにおかしい関係があれば、削除して作り直します。グラフが間違っていると、その間違いをAIが自信を持って再生産します。ここのチェックは省かないほうが良いです。

# 実測：同じ作業を2回やってみた

ここからが本題です。

同じリポジトリに対して、まったく同じ内容の指示を2回出しました。

**指示内容**：このリポジトリのアーキテクチャを解説するドキュメントを作成する（全体構成、主要モジュール、依存・呼び出し関係、設計上の特徴を含む）

**条件A（グラフなし）**：MCPメモリを使わず、ファイルを直接読んで解析する **条件B（グラフあり）**：登録済みの知識グラフを情報源とし、ファイル探索は基本的に行わない

モデルはどちらもClaude Opus 5。同じ日、同じ環境で実施しました。

## 数字の比較

![画像](https://pbs.twimg.com/media/HOE_yw9agAAXufk?format=png&name=large)

引用元の事例では「コスト半減、3倍速」とありましたが、26パーセント減になりました。理由は私のリポジトリが小さいからかと思われます。

グラフの効果は、読まずに済むファイルの量に比例します。数百から数千ファイルある大規模なコードベースなら、探索の省略幅が大きくなり、削減率も跳ね上がります。私のリポジトリはスキル11個の小規模構成なので、そもそも省ける量に上限がありました。

裏を返すと、この規模でも4分の1は減るということでもあります。

## 中身の比較のほうが面白かった

数字より興味深かったのは、出てきたドキュメントの質の違いです。同じ指示なのに、書かれる内容の種類が変わりました。

**グラフなし版が強かった点**

実ファイルを読んでいるので、グラフには登録されていない細部を拾ってきました。

- articles/claude-code/ に xxx.md\_note.html という命名規約違反のファイルが2件残っている
- drafts/ ディレクトリが設計上は存在するが、実際にはどのスキルからも書き込まれていない
- 4つのスキルにpandocの変換手順が丸ごとコピーされており、修正時に4か所直す必要がある

3つ目のような改善提案は、実物を読まないと出せません。特に「規約違反のファイルが残っている」は、グラフ版には絶対に書けない指摘です。

**グラフあり版が強かった点**

こちらは構造の抽象化が明確に上でした。

- スキルを「収集系・企画系・生成系・後処理系・補助系」の5系統に分類した
- references/x-collect がハブであることを、参照回数16回という数値で示した
- X系4スキルが相互に delegates-to で参照し合う密なクラスタを形成していることを発見し、これがトリガー誤爆を防ぐ設計だと解釈した
- browser-useとpandocが単一障害点であり、どちらかが止まると系統ごと停止すると指摘した

4つ目のような指摘は、依存関係を全体として俯瞰しないと出てきません。ファイルを順に読んでいく方式では、視野が1ファイルずつになるので気づきにくい。

要するに、**グラフありは構造に強い**という結果でした。グラフありでは、細部を拾わないのかと思われるかもしれませんが、グラフありの場合では、ファイルをあまり見ないように指示していた点を踏まえると優秀と言えるでしょう。

## 弱点も1つ書いておきます

グラフが古いと、AIは古い情報を迷いなく語ります。根拠がグラフにあるぶん口調が断定的で、読む側が疑いにくい形で出てきます。

対策は単純です。定期的にグラフを更新するようにしましょう。

# 結局、どこが良いのか

3点に絞ります。

**1\. 毎回の探索が消える**

グラフがあると、Claudeは「探す」工程を飛ばして「辿る」工程から始めます。ファイルを1つも開かずに答えが出る場面が生まれます。速さも安さも、ここから来ています。

**2\. 全体を俯瞰した指摘が出てくる**

単一障害点、循環依存、参照の集中。人間が見落とす種類の情報は、たいてい全体を見渡したときだけ見える形をしています。コスト削減より、こちらのほうが価値があると感じました。

**3\. 説明する手間が積み上がらない**

@で渡した情報は、セッションが終われば消えます。翌日また同じ説明をすることになります。グラフは残り、しかも毎回全部が読まれるわけではありません。残るのに重くならない。この性質を持っているのは、この方式だけです。

そのうえで、規模の目安も書いておきます。ファイルが数十個のプロジェクトなら、素直に@で指定したほうが速い。効いてくるのは数百ファイル以上の規模か、長期間にわたる継続作業です。

いちばん良かった使い方は、グラフで全体像を掴んでから、気になった部分だけファイルを読む流れでした。地図で行き先を決めてから、現地を歩く。この順番だと、探索範囲が最初から絞られます。

# Anthropicの公式見解も同じ方向

Anthropicのプロダクト担当であるThariq（[@trq212](https://x.com/trq212)）がXへ投稿した「[The new rules of context engineering for Claude 5 models](https://x.com/trq212/status/2080710971228918066)」を読むと、Claude Opus 5やClaude Fable 5といった最新モデルに対して、Claude Codeのシステムプロンプトの80パーセント以上を削除したにもかかわらず、社内のコーディング評価では測定できるほどの性能低下が起きなかったと書かれていました。

指示を8割減らして、悪くならなかったということです。この記事で「渡す情報を減らしたのに答えの質が上がった」と書いたのと、同じ形の現象が起きています。

## CLAUDE.mdに書く内容は、思っているより少なくていい

投稿では、CLAUDE.mdの書き方についてこう説明されています。

- 軽いままに保つ
- リポジトリが何のためのものかを手短に説明する
- トークンの大半は、コードベースに潜む落とし穴の説明に使う
- ファイルシステムやリポジトリを見ればClaudeが分かる当たり前のことは書かない
- 細かい内容は別ファイルに切り出し、CLAUDE.mdからは参照するだけにする

落とし穴の例として挙げられていたのは「型定義は1つの巨大なファイルにまとめていて、他の場所には置かない」といった記述でした。読めば分かることではなく、読んでも気づけないことを書け、という基準です。

この記事の「CLAUDE.mdとの違い」の章で、ルールはCLAUDE.md、事実はグラフという分担を書きました。公式の説明はさらに踏み込んでいて、ルールですら書きすぎるなという話になっています。

理由も明快でした。社内の利用ログを読むと、1つのリクエストの中に「ドキュメントは適切に残すこと」と「コメントを絶対に追加するな」といった矛盾する指示が同時に入り込んでいる場面が見つかったそうです。システムプロンプトとskillsとユーザーの依頼が、互いにぶつかり合っていたわけです。

書けば書くほど賢くなるわけではない。この記事で資料について書いたことは、CLAUDE.mdにもそのまま当てはまります。

## 記憶の置き場所は、CLAUDE.mdからmemoryへ移った

この記事の主題に直結する記述もありました。

かつては、# ホットキーでCLAUDE.mdへ自動的に書き込む形で、覚えておいてほしい情報を保存するようユーザーに勧めていた。今はClaudeのほうが、作業内容やユーザー自身に関することを自動でmemoryへ保存するようになった、という説明です。

記憶の置き場所は、すでにCLAUDE.mdからmemoryへ移っています。この記事でやったのは、その移った先に構造を与える作業でした。

ここで言うmemoryは、先ほどの補足で触れたClaude内部の記憶機能のほうです。この記事で入れたMCPのメモリサーバーとは別物なので、公式が「自動で保存されるようになった」と書いていても、こちらの知識グラフが勝手に育つわけではありません。 それでも、流れとして読み取るべき点は同じです。覚えておいてほしいことの置き場所は、指示書から記憶領域へ移りました。この記事でやったのは、同じ方向の動きを、中身を自分で管理できる側で行う作業でした。

自動で溜まっていく記憶は、放っておけばただのメモの山になります。エンティティとリレーションの形に整えておくと、そこから線を辿れるようになる。違いはそれだけです。

自動で溜まる記憶は手間がかからない代わりに、何が入っているのかを把握しづらく、構造もありません。どこに何があるかを自分で握っておきたいなら、こちらのほうが扱いやすいと感じています。

## 知識グラフは、事実に対する段階的開示です

投稿では段階的開示（progressive disclosure、必要になった段階で必要な分だけ読み込ませる考え方）が繰り返し強調されていました。「Claudeはそうしないと見つけられないのだから、CLAUDE.mdやskillsをあらゆる知見の中央リポジトリにしておくべきだ」というのは神話であり、そうではなく適切なタイミングで読み込めるファイルのツリーを作れ、という指摘です。

この記事の実測でキャッシュ読み取りトークンが約33パーセント減ったのは、まさにこれが起きたからでした。グラフは全部を毎回渡しません。Claudeが必要と判断したノードだけを取りに行きます。

手順や作法を段階的に開示するのがskillだとすれば、事実と関係を段階的に開示するのが知識グラフです。同じ考え方を、別の種類の情報に当てはめているだけとも言えます。

## 注意点

「制約を減らす」という話を、グラフの型設計にまで持ち込まないでください。

減らすべきなのは、Claudeの判断を縛る指示のほうです。関係の型を揃えることは、Claudeを縛る行為ではなく、データの表記を揃える行為にあたります。この記事で型のリストを指定したのは、calls と invokes と uses がばらばらに登録されると後から検索できなくなるからでした。ここは緩めるところではありません。
