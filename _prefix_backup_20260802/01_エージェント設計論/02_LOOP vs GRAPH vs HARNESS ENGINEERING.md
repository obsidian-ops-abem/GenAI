# LOOP vs GRAPH vs HARNESS ENGINEERING

「AIエージェント開発者が理解すべき3つのシステム」を整理した記事。要旨は、エージェントが失敗するのはモデルが弱いからではなく、モデルを取り巻く"システム"がそもそも設計されていないからだ、という診断。その上で、信頼できるエージェントを支える3つの異なるエンジニアリング層を提示している。

## なぜ失敗するのか

ツールが信頼できない、実行のたびに状態が消える、何も学ばずにリトライを繰り返す、ワークフローの分岐を誰も追跡できない——こうした不具合はすべてモデルのせいにされがちだが、それは診断を誤っている、というのが記事の出発点。

## 3層の定義

| 層 | 一言 | 役割 |
|---|---|---|
| Harness（ハーネス） | 環境 | モデルが作業する場所を与える |
| Loop（ループ） | フィードバック | 作業に検証サイクルを与える |
| Graph（グラフ） | フロー | プロセスに明示的な経路を与える |

覚え方: **HARNESS＝環境／LOOP＝フィードバック／GRAPH＝フロー**。3つは重なり合い、互いを内包し得るが、解決する問題が異なる。モデルが「決める」、ハーネスがそれを「実行させる」、ループが「結果を証明させる」、グラフが「次に何が許されるか制御する」。

小さなプロトタイプでは3層が1本のスクリプトに埋まっているため混同しやすいが、ツール定義や状態保存は Harness の設計、テスト＆リトライの方針は Loop の設計、役割分担（リサーチャー／レビュアー／パブリッシャーなど）は Graph の設計、というように担当が分かれる。

## Layer 1: Harness Engineering

モデルは「知性」、ハーネスはその知性を実用化する「機構」。ハーネスを外した後もアーキテクチャ図に残るものは、だいたいハーネスの一部。

**含まれる要素**

- コンテキスト: システム指示、検索知識、会話状態、タスク方針、スキル
- 実行面: API、ブラウザ操作、シェル/コード実行、DB、MCPツール、専門エージェント
- 永続化: ファイル、チェックポイント、セッション状態、進捗ログ、git履歴、長期記憶
- 実行制御: タイムアウト、リトライ上限、トークン/コスト予算、モデルルーティング、承認ゲート
- 安全性: 隔離環境、最小権限、許可リスト、シークレット管理、人間承認
- 可観測性: トレース、入出力ログ、状態遷移、コスト/レイテンシ、評価結果

**効いてくる場面**: タスクが1コンテキストウィンドウを超えて続くとき。チャット履歴だけに頼らず、進捗ファイル・git commit・リスクの高い操作前のチェックポイント・検証ツールといった「持続する成果物」が要る。

**着手すべきサイン**: 必要な機能にアクセスできない／セッションをまたぐと進捗を失う／権限が広すぎる／環境によって挙動が変わる／実行を一時停止・検査・再開できない／失敗を再現できない。

## Layer 2: Loop Engineering

ツール利用エージェントには元々「モデル→行動→観測→モデル」という内部ループがある。Loop engineeringは、このサイクルを意図的に設計し、一発勝負の試行を「管理されたプロセス」に変えること。

**検証ループの基本形**: 生成 → 根拠と照合 → 合格なら停止／不合格なら具体的なフィードバックを返し、上限つきで再試行。チェックはテスト合格やスキーマ検証のように決定的な場合もあれば、論拠の完全性やトーンの適合性のようにレビュアー判断が要る場合もある。

鉄則は「自信ではなく根拠でループを回す」こと。「エージェントが完了したと言っている」は証拠にならない。

**実用ループの7要素**: トリガー／ゴール（測定可能な状態）／状態（次の試行が知るべき最小限の情報）／行動方針（変更・呼び出し・委譲・支出の許可範囲）／根拠（テスト・引用・diff・指標・人間レビュー）／フィードバック（失敗理由の簡潔な説明）／停止規則（成功・最大試行回数・予算枯渇・タイムアウト・エラー・人間へのエスカレーション）。

ループは入れ子にできる。エージェントループ（作業実行）を検証ループ（作業確認）が包み、イベントループ（新規作業の起動）がそれを包み、さらに改善ループ（本番トレースを見てハーネス自体を更新する）が最上位に来る。追加のコスト（レイテンシ・支出）は避けられないため、検証コストより失敗コストが高い場面でループを足すのが判断基準。

## Layer 3: Graph Engineering

問いが異なる。「エージェントはどう働くべきか」ではなく「次に何が実行を許されるか」。作業がノード、許可された遷移がエッジになり、状態がグラフを移動する。固定シーケンス、条件分岐、並列展開、合流、有界サイクル、リカバリ経路、人間の割り込みを表現できる。

**決めるべきこと**: ノードの境界（通常コード／LLM呼び出し／専門エージェント／人間レビューのどれに属するか）、状態スキーマ（各ノードの読み書き範囲・並列結果のマージ方法）、ルーティング条件（どの根拠で前進・後退・エスカレーションするか）、並行性（何を並列実行し何を合流待ちにするか）、サイクルと終了条件、永続性（チェックポイント位置・再開方法）。

**グラフを使うべきとき**: 意味のある分岐、並列の専門エージェント、承認、リカバリ経路、状態を持つ引き継ぎがあるとき。単にステップが複数あるというだけでグラフから始めるべきではない。ありがちな失敗は、チームが実際の作業を理解する前にワークフローを形式化し、間違った前提を美しい図に固めてしまうこと。まずシンプルなハーネスで始めて実トレースを観察し、安定した経路だけを形式化するのが正しい順序。

## 3層が1つのシステムで動く例

事実確認つきの業界ブリーフィングを作るリサーチ＆パブリッシングエージェントを例に：

- **Harness** が提供: ブラウザ/検索ツール、ソース保存、執筆ワークスペース、引用チェック、権限・承認ルール、チェックポイント・トレース
- **Graph** が制御するルート: RESEARCH → DRAFT → FACT CHECK（不合格ならRESEARCHへ差し戻し）→ EDITORIAL REVIEW（不合格ならDRAFTへ差し戻し）→ HUMAN APPROVAL → PUBLISH
- **Loop** はそのルートの内側で動く: リサーチノードはソースの網羅性が十分になるまで検索を続け、ドラフトノードはスタイル評価に合格するまで改稿し、ファクトチェックノードは曖昧な却下ではなく具体的な未サポート主張を返す

重要なのは入れ子構造 — グラフはハーネスの中で動き、ループはグラフの一部の中で動き、ハーネスがそれらループに必要なツール・状態・根拠を供給する。

## 故障診断表

| 症状 | まず見る層 | 対処の方向性 |
|---|---|---|
| 必要なデータに安全にアクセスできない | Harness | ツール契約の改善、権限、サンドボックス、コンテキスト注入 |
| セッション間で進捗を忘れる | Harness | 永続状態、チェックポイント、進捗成果物 |
| 最初の試行は惜しいが不安定 | Loop | 外部評価者、決定的テスト、実行可能なフィードバック、上限付き再試行 |
| 成功後も続く／証明前に止まる | Loop | 根拠ベースの終了状態、予算を意識した停止規則 |
| 専門エージェントを決まった順序で動かす必要がある | Graph | 明示的なノード・エッジ・ルーティング条件・合流 |
| 複数ステップにまたがる失敗の原因箇所が特定できない | Graph + Harness | ノード・遷移に対応した状態付きトレース |
| プロセスの変化が速すぎて固定図に追いつかない | よりシンプルなHarness | 計画をモデル駆動のままにし、グラフの形式化を遅らせる |

## よくある高コストな間違い

- **グラフを早く作りすぎる** — 強いエージェントの実際の動きを見る前に、想像上の業務プロセスを何十ノードにも変換しない。トレースが先、形式化は後
- **作り手自身に採点させる** — 自己レビューは元の試行と同じ盲点を持つ。可能なら決定的チェックを優先し、主観的な判断は隔離されたレビュアー文脈で行い、影響の大きい行動には人間承認を必須にする
- **ループを「とにかく試行し続ける」と定義する** — 上限のないリトライは信頼性ではなくコストの垂れ流し。毎サイクル新しい根拠・最大試行回数・名前付きのエスカレーション経路が要る
- **ハーネスを倉庫化する** — ツールを増やしても良いエージェントにはならない。ツールが多いほど選択ミスが増え、ノイズの多いコンテキストは混乱を増やし、広すぎる権限はリスクを増やす。タスクを完了できる最小の環境を与えるべき
- **オーケストレーションの失敗をモデルのせいにする** — モデルを強くしても、古い状態・壊れたAPI・曖昧なツールスキーマ・欠けた終了条件は直らない。モデルが本当に原因だと証明する前にアップグレードしない

## 本番投入前チェックリスト（要約）

- **Harness**: ツールは狭く文書化され観測可能か／状態はセッションをまたいで永続化されるか／権限は最小か／実行を一時停止・検査・再開できるか／重要な行動はトレースから再構成できるか
- **Loop**: 何が成功の根拠か／失敗後どんなフィードバックを返すか／リトライは何回までか／予算が尽きたらどうなるか／どこで人間の判断が要るか
- **Graph**: どの経路が決定的であるべきか／どこで並列実行できるか／合流・承認・リカバリ経路はどこか／どのサイクルが合法でどう終了するか
- **評価・運用**: 実際のトレースを再生できるか／改善を特定の変更に紐付けられるか／コスト・レイテンシ・失敗率・人間の介入頻度を可視化しているか

## まとめ

- Harness engineering ＝ モデルを運用可能にする
- Loop engineering ＝ 作業を反復的・検証可能にする
- Graph engineering ＝ 複雑な実行を明示的・制御可能にする

どれも他を代替しない。完璧なグラフも状態を失うエージェントは救えないし、完璧なハーネスも根拠と停止規則のないループがあれば無駄になる。強いループも、分岐・並列・承認がアドホックなコードに隠れていれば運用しづらい。3層すべてを一緒に設計し、各層に明確な役割を持たせたときに、信頼できるエージェントが生まれる——というのが結論。
