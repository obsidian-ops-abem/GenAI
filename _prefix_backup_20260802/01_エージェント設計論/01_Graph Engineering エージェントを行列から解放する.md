# Graph Engineering: エージェントを行列から解放する

> [!info] 出典
> MIKE（@mikenevermiss）、2026年7月27日13:52公開（X記事）
> [元記事](https://x.com/mikenevermiss/status/2081603616570212372)
> 詳細メタデータ: [[05_Graph Engineering How to Stop Building AI Agents That Wait in Line（出典）]]

原題「Graph Engineering: How to Stop Building AI Agents That Wait in Line」。マルチステップAIエージェントを「鎖（chain）」ではなく「グラフ」として設計するための実践ガイド。題材は Claude Code の dynamic workflows（実装済み機能）だが、考え方は複数エージェントを協調させる場面全般に当てはまる、という前提で書かれている。

[[02_LOOP vs GRAPH vs HARNESS ENGINEERING]] のGraph層を、実装レベルまで深掘りした内容と言える。

## 1. 問題: なぜエージェントは行列で待たされるのか

典型的なエージェントは「読む→要約→ルールと照合→報告書を書く」のような to-do リスト形式になりがちで、各ステップが前のステップの完了を律儀に待つ。短いタスクなら問題ないが、長時間・広範囲・自己採点を伴うタスクで破綻する。Anthropicのエンジニアリングチームが挙げる3つの失敗モード:

| 失敗モード | 内容 |
|---|---|
| エージェントの怠慢 | マルチパートタスクを途中で終えたのに完了と宣言する（50項目中35項目だけ終えたセキュリティレビューが典型例） |
| 自己優遇バイアス | 自分の出力を自分で判定させると、既に出したものを好む傾向が出る |
| 目標のドリフト | ターンを重ねるほど当初の依頼への忠実さが劣化する。会話が要約された後、エッジケースや「〜しないで」という制約から失われやすい |

これらはチェーンにステップを足しても解決しない。形そのものを変え、各作業に独立したクリーンなコンテキストを与え、結果を信用する前に検証することで解決する。

**診断法**: 「そして」で繋がる各工程について、次のステップが本当に前のステップの出力を読んでいるか確認する。読んでいなければ、それは独立した2つの仕事を無理に鎖でつないでいるだけで、待ち時間は純粋な無駄。

鎖もグラフの一種ではある——ただし最小・最も脆いグラフ（1入力1出力、分岐のない一本道）。冗長性がなく、どこか1つが詰まると下流全部が止まり、上流の結果は行き場を失う。

## 2. 概念: ノードとエッジ

- **ノード**: 境界の明確な1単位の作業。1エージェント、1つの明確な仕事、1入力・1出力（例:「1件のチケットを分類する」であって「顧客対応全般を処理する」ではない）
- **エッジ**: 依存関係。あるノードの出力が別のノードの入力になること。順番や見た目の近さはエッジではない。実際にデータが渡っているかどうかだけがエッジを成立させる

**テスト法**: 既存のエージェントの各矢印について「実際に何かそこを渡っているか」を問う。何も渡っていなければ、その2ステップは独立していて、間の待ち時間は無駄。

ノードを安全に大きなグラフへ組み込むには「契約」が要る——境界の明確な入力と、検証済みの構造化された出力（次のステップが解析して期待する自由文ではなく）。これがあって初めて、エッジ両端のエージェントを差し替えたり、複数ノードを並列実行しても壊れなくなる。

## 3. アーキテクチャ: 6つのトポロジー

| トポロジー | 内容 |
|---|---|
| **Fan-out（分岐）** | 独立した複数の仕事を同時実行。1ノードの失敗でバッチ全体を沈めないよう、失敗ユニットは空の結果を返し次段の前に除外する |
| **Fan-in（合流）＝バリア** | 全上流結果が揃うまで次に進めない地点。例外的に使うべきもので、デフォルトにしない。重複排除・全体ランキング・早期終了判断など、本当に全体が必要な場合のみ使う |
| **ダイヤモンド型** | fan-outとfan-inの組み合わせ。分岐して幅を集める→普通のコードで縮約（重複排除など、エージェント不要・無料）→1エージェントが完全な縮約結果を使って統合、という3部構成 |
| **ルーティング** | 結果を見てどのエッジを発火させるか決める。分類自体はエージェントの判断でよいが、ルーティングそのものは普通のコードにし、同じ入力なら毎回同じ経路にする |
| **検証(Verification)** | グラフの強みはエージェントを増やすことではなく、結果への確信を作る構造。検証者は結果が下流に渡る前のエッジに座り、その所見を反証しようとするのが唯一の仕事。反証できなければ通す |
| **収束するサイクル** | 事前にサイズが分からない仕事（1件見つかると3件見つかるバグ探し等）には前のノードへ戻る制御ループが要る。実用的なのは「連続して何ラウンドも新発見がなければ止める」loop-until-dry方式。新発見は「確認済みのもの」だけでなく「これまで見た全て」と照合しないと、却下済みの結果が何度も再浮上する |

この6形はAnthropic自身が名付けた6パターンに対応する：**classify-and-act**（ルーティング）、**fan-out-and-synthesize**（ダイヤモンド）、**adversarial verification**（検証者）、**loop until done**（収束サイクル）、それに加えて **generate-and-filter**（候補を大量生成しルーブリックを通過したものだけ残す）と **tournament**（エージェント同士を対戦させ審判が勝者を決める）。

## 4. 実装のポイント

- **失敗の分離と書き込みの分離は別問題** — ノード単体の失敗は、失敗したノードを空扱いにしてバッチ全体を沈めない設計で対処する。並列ノードが同じファイルに書き込んで衝突する問題は別で、共有コードベースを複数エージェントが編集する場合にだけ、各自に隔離された作業スペースを与えて後でマージする（全トポロジーに課す税ではなく必要な場合だけの対策）
- **モデルの階層化** — 定型的なノード（1フィールド抽出など）は安いモデル、最終統合や係争中の所見の裁定など本当の判断が要るノードには最良のモデルを充てる。デフォルトでは生成ノードは起動元セッションのモデルを継承するため、階層化はノードごとに明示しない限り起きない
- **トポロジーこそが本当のコストレバー** — バリアは、他の9個が先に終わっていても最も遅い1個の完了を全員が待つ。同期点を設けず各アイテムを独立して流せば、速いアイテムが遅いアイテムの後ろで無駄に待つことがない。デフォルトは独立して流すこと。バリアは、そのステージが本当に完全なセットを必要とする場合に限る。「コードがきれいだから」はバリアを正当化する理由にならない
- **実際の構築方法** — Claude Codeでは目的を説明して「ワークフローとして」と伝えるか、`ultracode`というトリガーワードを使うと通常の逐次対応ではなくワークフローとして構築される。繰り返し使うものは定期実行（`/loop`）と完了条件（`/goal`）を組み合わせ、トークン上限も設定する。うまくいった回はスクリプトを保存すれば、次回作り直さずに使える資産になる
- **実例** — Bunのランタイムを Zig から Rust へ書き換えた実際の移行がこの形そのもの。1コールサイト・1失敗テスト・1モジュールという単位に分解し、それぞれに1サブエージェントを隔離ワークスペースで割り当て、2つ目のエージェントが全変更を敵対的にレビューしてからマージする。1本のスクリプトが艦隊を統率し、レビューは後付けではなくトポロジー自体に組み込まれていた

## 5. よくある落とし穴

- **偽のエッジ** — その順番でタイプしただけで、後段が前段の出力を実際には読んでいない
- **デフォルトでバリアにする** — 次段が完全なセットを必要としないのに、整って見えるからと同期待ちを選ぶ
- **自分の配管に家賃を払う** — リストの平坦化や重複排除のような、決定的なコード数行で済む仕事にエージェントを立てる
- **決して枯れないループ** — 新発見を「確認済みのもの」だけと照合し、「これまで見た全て」と照合しない。却下済みの結果が毎ラウンド再浮上する
- **時間的プレッシャーで検証を省く** — 何も反証を試みないまま所見を通すと、検証が防ぐはずだった怠慢・自己優遇の失敗モードを呼び戻す
- **必要ないのに持ち出す** — ほとんどのタスクは5人のレビュアーパネルを必要としない。グラフは協調コストに見合う価値を証明しなければならない

## 6. この先の展望

手描きのグラフは鎖より進歩だが天井ではない。より面白いフロンティアは、グラフを手で描くことすらせず、目的を説明するだけでシステム自身がタスクを分解し自らfan-outを選び、その回に合わせたオーケストレーションスクリプトを書くこと。うまくいった回のスクリプトは保存・コミットして、チームメイトが名前で呼び出せる共有資産にできる。

具体例として挙げられている6パターン: 全ルートのセキュリティ一斉点検、引用付きリサーチレポート、モジュールのファイル単位移植、差分の敵対的レビュー、速く動く分野の定期スキャン、オープンエンドな発見——いずれも上記6トポロジーの組み合わせとして説明されている。
