[株式会社ジェイテックジャパン](https://www.jtechs.com/japan) CTOの [高丘 @tomohisa](https://twitter.com/tomohisa) です。

AIエージェントを4体、止まりを見つけて再開させながら回して開発を進める、ということを日常的にやっています。設計・オーケストレーション・実装・レビューの4スレッドが、GitHub の Issue と PR を通じて協調する仕組みです。この土台に **Intent CLI** （プロジェクト名 intent-system）という OSS を使っています。

これまでに、考え方の [コンセプト編](https://zenn.dev/jtechjapan_pub/articles/intent-cli-concept) 、手順の [実践編](https://zenn.dev/jtechjapan_pub/articles/intent-cli-practice) 、そして [Loop Engineering との接続](https://zenn.dev/jtechjapan_pub/articles/intent-cli-loop-engineering) を書きました。今回書くのは、その運用を止まりにくくするために、何を工夫し、どこでつまずき、どう直したか、です。

具体的には、agmsg というエージェント間メッセージングを必須の依存から外し、 [herdr](https://herdr.dev/) というターミナルワークスペース管理ツールだけで回す「herdr-only」モードを作った話と、その最初の運用で見つかった「起こす経路」の欠落を、どう埋めたかを説明します。同じ考え方なら Intent CLI を使わなくても組めるはずなので、再現できる粒度で書きます。

## まず前提: 4スレッドと「設計スレッドだけと話す」

[実践編](https://zenn.dev/jtechjapan_pub/articles/intent-cli-practice) では設計・実装・レビューの3スレッドを紹介しました。いまはそこに **オーケストレーション** を足した4スレッドで回しています。役割の違う4つのスレッド（＝コーディングエージェントのセッション）で、指示の流れはこうです。

<iframe src="https://embed.zenn.studio/mermaid#zenn-embedded__9b7522fb5442" frameborder="0"></iframe>
- **設計スレッド** — 意図をまとめ、判断（ADR）を残し、作業単位（packet）と受け入れ基準を決める。
- **オーケストレーションスレッド** — 準備できた packet を GitHub の Issue として1回に1件だけ切り出し、実装・レビューへ渡し、CI やレビューの完了を待ち、マージと締め（closeout）を進める。判断はせず、進行役に徹する。
- **実装スレッド** — Issue を受けて実装し、PR を作る。見るのは GitHub の Issue/PR とコードだけ。
- **レビュースレッド** — PR を、元の Issue・packet・意図・ADR と突き合わせて確認する。

通常運用では、人間の入口を **設計スレッドだけ** に限定しています。実装やレビューの細かい進捗は、人間ではなくオーケストレーションスレッドに報告されます。人間まで上がってくるのは、意図の曖昧さ、受け入れ基準の欠落、セキュリティや破壊的操作といった「人間が決めるしかないこと」だけです（UI の探索的な調整で実装スレッドに入り込む、といった例外は [Loop Engineering 編](https://zenn.dev/jtechjapan_pub/articles/intent-cli-loop-engineering) で書いたとおり残しています）。

この分担のおかげで、複数のプロジェクトを並行させても頭がパンクしません。いまは intent-cli 本体・sekiban-as-a-service・sekiban-wasm-runtime・robocon の4ドメインを、1台のマシンで並行して回しています。規模でいうと、直近およそ4か月で作業単位が1,537件（うち完了1,531件）、マージした PR がおよそ1,460件、という積み上がりです（2026年8月時点、`.intent-cli` の集計より）。

## なぜ「turn を起こすメッセージ」が要るのか

ここが今回の話の出発点です。コーディングエージェントのセッションは、 **turn（発話）が来て初めて動く** ものです。1回の turn を終えると、次に何かが turn を作るまで、ただ待っています。

最初、実装とレビューはタイマーループで回していました。5分ごとに自分で自分を起こし、 `intent-cli worker next-action` で次の作業を拾う。これは今でも「壊れてはいない」やり方で、選択肢としては残しています。ただ、スレッドが本来のやり方から逸れたとき、人間が毎回「intent-cli に聞いて、正規の手順に戻って続けて」と言い直す雑務が発生していました。

そこで、4つ目のスレッドとしてオーケストレーションを追加し、スレッド間をメッセージでつなぎました。ここで agmsg（ [fujibee/agmsg](https://github.com/fujibee/agmsg) 製のエージェント間メッセージング）を使いました。agmsg には monitor という仕組みがあり、 **受信メッセージを会話の中の turn に変換してくれます** 。「実装が終わりました」というメッセージが届くと、それがオーケストレーションの次の turn になる。だから速いタイマーで空回りさせなくても、メッセージ駆動で回り続けます。

この設計から学んだことが2つあります。どちらも、あとで herdr に移るときの判断材料になりました。

1つ目。 **黙って完了してはいけない** 。受信側が作業を終えても、完了を報告しなければ、オーケストレーションを起こすものが何もありません。報告のないまま終わった作業が「失われた仕事」になり、実測で88分放置された例があります。完了報告は、委譲の「必須の最終ステップ」なのです。

2つ目。 **publish と委譲は同じ turn の中でやりきる** 。次の Issue を切り出したのに委譲を後回しにすると、メッセージ駆動では次の turn を作るものが他にないので、委譲されないまま残ります。これを後回しにしたことで、あるドメインでは合計およそ60時間の停止を招いたことがあります。

## herdr で「任意のスレッドを起こす」

agmsg でうまく回っていたのに、なぜ herdr に寄せたのか。中心にあったのは、受信側の常駐という故障点を減らしたい、という理由でした。

agmsg には codex bridge という層があります。これは「TUI（対話画面）の外からメッセージを届ける」ための仕組みで、私が数えたときは agmsg のコードのおよそ27%、行数にして約2,900行を占めていました（対象コミットでの概算です）。届け先のエージェントに monitor や bridge が常駐していないと、メッセージが見える形で配送されない。この「受信側の常駐」を成立させ続けるのが、地味に手間でした。

herdr はターミナルワークスペース管理ツールで、ペイン（端末）を直接操作できます。 `herdr agent prompt <ペイン>` で、任意のペインにテキストを送り込める。つまり、 **どのスレッドの turn でも、観測する側から起こせる** 。受信側に専用の monitor を常駐させておく必要がなくなります。「TUI の外から届ける」という問題が消えるわけではありませんが、受信側 bridge の問題を、herdr の「ペインを特定して prompt を送る」という別の問題に置き換えられる。この置き換えが、herdr-only モードを作った一番の動機です。

もう一つ、以前から考えているのが **マルチマシン対応** です。いまの herdr-only は1台のマシンが前提ですが、将来は herdr のマシンどうしがメッセージを送り合って協働する形を作りたいと思っています。依存を減らして土台を単純にしておくと、その一歩が踏み出しやすくなります。

agmsg を「やめた」わけではありません。agmsg モードと herdr-only モードの2つを選べるようにして、どちらも選択可能な状態で残しています。いまの位置づけは、agmsg が既定（PRIMARY）、herdr-only はプレビュー扱いです。プレビューといっても実運用していないという意味ではなく、限定しているのは「メッセージの運び方（トランスポート）」の新実装という範囲で、4スレッドの協調の形そのものはどちらのモードでも変わりません。チームごとに、どちらのモードかを記録して切り替えます。切り替えは可逆で、agmsg に戻すのも普通の操作です。1チームにつき1モードで、混在は許していません（混ぜると配送が壊れます）。

この経緯は、agmsg の作者である fujibee さんと X でやり取りしました。

<iframe src="https://embed.zenn.studio/tweet#zenn-embedded__9e4dbf8ce2322" frameborder="0" height="24"></iframe>

私の返信で書いたことを、そのまま引いておきます。

> 開発ループを最初はタイマーループで実装していたのを agmsg に書き換えてチームでメッセージを送り合えるようになりました。ただ権限プロンプトや質問で止まることがあったのですが、agmsg+herdr にしたことで、ブロック検知および、質問に対しての返信を API 経由で、オーケストレータースレッドから設計スレッドに対して行うことができ、安定性が増しました。（中略）実はマルチマシン対応を考えているのと、あと依存を減らしたほうが安定すると考えて agmsg を剥がして herdr only モードを作りました。

fujibee さんからは、herdr 対応でプロアクティブな動作ができるようになるはず、agmsg のリモート対応（別マシンを含むメッセージング）も近く発表予定、という返信をもらいました。agmsg にはずっと助けられてきましたし、これからも使う場面はあります。今回は「必須の依存から外した」という話で、否定ではありません。

## agmsg を外したら、誰も次を起こさなくなった

agmsg に依存しないバージョンを作って、最初の実仕事を流してみたら、あっさり止まりました。

オーケストレーションスレッドが Issue を publish して実装に委譲し、turn を終える。実装は PR を作って CI を通し、完了マーカーを **自分のペインに** 出力する。ところが3つのロールが全員 idle のまま、そこで止まってしまいました。

原因ははっきりしていました。agmsg では、受信側の完了報告メッセージが monitor 経由でオーケストレーションを起こしていた。herdr-only にした瞬間、その経路が消え、完了が自分のペインにしか現れなくなった。誰もオーケストレーションを起こさない。

この欠落は、事前に流した模擬タスクでは出ませんでした。模擬タスクは「worker が自分のペインに完了を出すだけ」というケースを含んでいなかったからです。実際の Issue を使った1サイクル目で初めて表に出た。以後は、実 Issue での1サイクルを受け入れ確認に含めるようにしました。

直し方は、wake（起こす）経路を1本に頼らず、冗長にすることでした。いまは3つの経路を重ねています。

<iframe src="https://embed.zenn.studio/mermaid#zenn-embedded__7eecfa7594285" frameborder="0"></iframe>
1. **一次: 完了報告で起こす** — 委譲の最終ステップとして、worker が `intent-cli notify report` を実行し、その中でオーケストレーションのペインを prompt して起こす。task id・状態・成果物を運ぶ、いちばん情報量の多い経路です。agmsg の push を、herdr の prompt で置き換えた形になります。
2. **二次: 状態変化で起こす** — herdr の socket API に `events.subscribe` で購読を張り、 `pane.agent_status_changed` というイベントを監視します。監視対象のペインごとに購読を1つ持ち、 `working` から settled（ `idle` / `done` / `blocked` ）へ移った瞬間だけ起こす。短い間の二重発火を防ぐため、settle delay とロール単位の重複排除を入れています。これなら worker が完了報告を出し忘れても、プロセスの状態変化だけで拾えます。ただしこのイベントは成否（task の結果）を運びません。だから起きたあとに `herdr pane read --source recent-unwrapped <pane>` でペインを覗いて、承認待ちや質問で止まっていないかを確かめ、正規の状態（intent-cli / GitHub の事実）を取り直します。まず手元で試すなら、CLI の `herdr agent wait <pane> --until idle --until done --until blocked` が同じ「settle まで待つ」入り口になります。（確認したのは herdr 0.7.5。API の形はバージョンで変わりうるので、 `herdr --help` を正としてください。）
3. **最後の網: 定期点検で拾う** — 一次も二次も落ちたときのために、 `intent-cli automation stalled-work --domain <ドメイン> --repo <owner/repo> --format json` を定期的に走らせ、「止まっている作業」を洗い出します。たとえば「承認済みなのにマージされていない PR」などを、次に手を打つべき項目として拾います。intent-cli を使わない場合は、 `gh pr list` と自分の状態記録を突き合わせる点検を、同じ間隔で回せば代わりになります。

基準は「 **どの単一の経路が落ちても、停止は検出できる状態を保つ** 」ことにしました。1本の経路が完璧であることに賭けない、という考え方です。

ここで大事にしているのは、 **状態が変わったことは、作業が成功したことを意味しない** 、という一点です。ペインが idle になっても、承認待ちで一時停止しているだけかもしれない。だから完了の判定を、状態だけで下すことはしません。次の条件を合わせて確認します ── settle した状態であること、承認や質問でペインが止まっていないこと、成果物が実在して検証を通ること、最新の intent-cli / GitHub の事実と一致すること。

## 止まる原因の多くは「承認プロンプト」

繰り返し遭遇した停止要因が、権限の承認プロンプトでした。実装スレッドが `rm -rf /tmp/...` の承認で止まる、PR 作成の承認で止まる、PR コメント追加の承認で止まる。CI は全部緑なのに、承認待ちで前に進めない。

ここでの方針は明確です。 **オーケストレーションスレッドはこの承認を勝手に押さない** 。認証・セキュリティ・権限・破壊的操作・設計判断は、常に人間（設計スレッド経由）にエスカレーションします。「セッションを進めることと、セッションの代わりに判断することは、別のことだ」という一線を引いています。

一方で、 `rm -rf /tmp/...` の承認が頻発すること自体は、作業環境の設計のにおいだと考えました。だから任意の `/tmp` を消させるのをやめ、git 管理から外した専用の worktree 置き場（`.intent-cli/worktrees/` 配下）だけを対象にし、後片付けは、置き場配下であることを確認したうえで `git worktree remove` を使う形にしました。これで承認が「なくなる」わけではありませんが、危ない承認に人手で付き合う回数はかなり減りました。

## 複数ロール・複数ドメインを衝突させない工夫

ここでいう並列は3種類あります。実装とレビューという役割の並行、4ドメインの並行、そして同一リポジトリ内の複数 Issue です。最後の「同一リポジトリの複数 Issue」だけは、あえて絞っています。実運用で追加した対策を並べます。intent-cli を使わなくても、同じ考え方は再現できます。

- **ロールごとに作業場所を分ける** — 実装とレビューは、独立したクローンか、git 管理下の worktree に分ける。1つのフォルダを2つのロールで共有しない（実践編では独立クローンを勧めましたが、いまは置き場を決めた worktree も併用しています）。フォルダを共有すると、agmsg 側の識別が `(プロジェクト, 種別)` で同じものに解決され、片方が静かに受信を止めることがありました。
- **メタデータとコードのブランチを分ける** — 意図や作業状態のメタデータは `main-metadata` 、実装コードは `main` 。実装の PR は `main` に向け、メタデータはメタデータ側に留める。PR 一覧が「メタデータ変更」で埋まらず、衝突面も減ります。
- **実装は GitHub の契約だけを見る** — 実装スレッドはホスト側のメタデータを読み書きしない。だからホストの状態と衝突しません。
- **WIP を1件に絞る** — 対象リポジトリに未完了の作業が1件でもある間は、新しい Issue を切り出さない。同時多重を防ぎ、レビューと実装の精度を保ちます。
- **`git add -A` を使わない** — 該当するファイルだけを add し、他の automation が使う一時ファイルを巻き込まない。push の直前には `git pull --ff-only` を同じ手順の中で入れる。これは衝突を消すのではなく、他の書き手が先に push していたら fast-forward できずに push を失敗させ、取り直しに回すための安全弁です。
- **アイドル時に push しない** — 数分おきの空 wake が空コミットを積むと、GitHub の草が生い茂ってしまう。起動プロンプトに「何もなければ push しない」を必ず入れています。

これらは最初から分かっていたわけではなく、事故から足しました。2つ挙げます。

- **共有プロセスの所有境界** — 共有していた codex の app-server を、別プロジェクトの整理で kill してしまい、接続中だった他チームの画面を巻き添えにしたことがあります。以後、消す前に「その資源が自チームのものか」を作業ディレクトリなどで確認し、他チームのものは消さずに退避する、という手順にしました。
- **起動報告の検証** — エージェントが「起動しました」と報告した直後に基盤が落ちて全滅していたのに、設計スレッド側は「起動待ち」のまま、ということがありました。 **自己申告は、生きている証明にはならない** 。だから起動報告のあとに、実際に応答するかを確認してから次へ進めるようにしました。

## サブエージェントを「設計スレッドに頼むだけ」で立てる

herdr に寄せて、地味にいちばん楽になったのがここです。

設計スレッドは、herdr を通じてチームのセッション層を組み立て、面倒を見る役割も持っています。workspace を作り、ロールごとにペインを分割し、エージェントを起動し、準備が整ったかを確認する。これらを設計スレッドが実行できる。

だから私が設計スレッドに頼むのは、これくらいの短さです。実際に投げている依頼はこんな形です。

```
intent-cli の最新の機能を使って、herdr-only のチームを作ってください。
ここを設計、
orchestrator  codex sol high
implement     codex sol middle
reviewer      claude opus 5
で構成してください。
```

指定しているのは、herdr-only モードを使うことと、どのスレッドをどのエージェント（とモデル）に担わせるか、だけです。手順もコマンドも書いていません。これを受けて設計スレッドが、intent-cli に現在のやり方を聞き、herdr 上に必要なペインを立て、各エージェントを起動し、どのペインがどの役割かを記録して、チームを組み上げてくれます。

裏側でやっているのは、難しいことではありません。この記事を書くときにも、査読用の codex を1体立てるのに、実際に次のコマンドを使いました（herdr 0.7.5 で確認。返ってくる JSON からペイン ID を取り、推測 ID を使わないのがコツです）。

```
# 1) 独立したワークスペースを作る（返却 JSON の pane_id / workspace_id を使う）
herdr workspace create --label tomohisa_zenn --cwd "$HOME/dev/GitHub/zenn_tomohisa" --no-focus
# => "pane_id":"wP:p1", "workspace_id":"wP" が返る

# 2) そのペインに codex を起動する（対話シェルの shim 経由で立ち上がる）
herdr agent start zenn-review --kind codex --pane wP:p1 --timeout 180000

# 3) プロンプトを送り、idle/done になるまで待ち、出力を読む
herdr agent prompt wP:p1 "この草稿を査読して…"
herdr agent wait   wP:p1 --until idle --until done --timeout 300000
herdr agent read   wP:p1 --source recent
```

ロールを1体足したいときも同じで、ペインを `herdr pane split` で1枚割り、 `herdr agent start` で起動し、どのワークスペースのどのペインがどの役割か、を記録するだけです（intent-cli を使う場合は `intent-cli session-layer topology record` がその記録を担い、宛先はエージェント名ではなく「ワークスペース＋ペイン」で解決されます）。

実際に、依頼だけで herdr-only のチームが立ち上がっていく様子を、早回しの録画で上げています。ペインが分割され、各エージェントが起動し、役割が埋まっていくところが見られます。

専用の難しいコマンドを覚える必要はありません。設計スレッドが窓口になっていて、そこに頼めば組み上がる。私が手で触る操作は、ペイン作成・エージェント起動・初回プロンプトの3種から、設計スレッドへの1回の依頼に減りました。並行プロジェクトが増えるほど、この差は大きくなります。

## 実際、どう使っているか

規模は前述のとおり4ドメインを1台で並行、という具合です。速度の感覚としては、直近だと intent-cli 本体で十数スライスを1〜2日で回せた日もありました（Issue 番号でいうと #1257〜#1291 の範囲で、間に別種の作業も混ざります）。

分かりやすい目安として、この1年の GitHub の contribution が2万を超えました。もちろん、私が手で打ったぶんだけでなく、オーケストレーションのループが積み上げたコミットや PR も含んだ数字です（空 wake では push しないようにしているので、中身のある変更が主です）。

グラフの色が濃くなる時期と、この運用を本格的に使い出した時期は、はっきり重なっています。因果を厳密に測ったわけではありませんが、ひとりで手を動かしていた頃とは量が変わった、というのが実感です。

ループの間隔は、メッセージ駆動が主ですが、それを補う「見張り」として設計スレッド側で長め（30分級）のリマインダを回し、Claude Code のセッション内なら `/loop 3m` 、別マシンやクラウドなら5分間隔を使います。3分にしているのは、私の Claude Code 環境では既定のプロンプトキャッシュが5分で切れるので、その前に次を回したいから、という程度の理由です。短すぎるとラベルの取り合いが起き、長すぎると観察が遅れます。なお herdr-only の実装・レビューは基本メッセージ駆動なので、そこに速いタイマーは重ねません。

そして、私が設計スレッドに投げているのは、ほとんどが「intent-cli に聞いて、正規のやり方で次を進めて」に近い自然言語です。コマンドを覚えて打つのではなく、意図と判断を伝える。実装やレビューの細かいやり取りは、オーケストレーションが受け止めて、私のところには上がってきません。止まっても、たいていは「intent-cli に聞いて直して進めて」で戻ります。

## 自分で組むなら / intent-cli なら

ここまでの工夫は、特別な魔法ではありません。要点を取り出すと、こうなります。

- コーディングエージェントは turn が来ないと動かない。だから「誰が turn を起こすか」を設計する。
- 起こす経路は1本に頼らず、冗長にする（完了報告・状態変化の購読・定期点検）。
- 「状態が変わった」を「成功した」と混同しない。成果物と外部の事実で確かめる。
- ロールごとに worktree とフォルダを分け、メタデータとコードのブランチも分ける。
- 承認・判断は人間に返し、それ以外は自動で回す。人間が話すのは設計スレッドだけにする。

これらは、herdr と gh CLI と、自分のエージェント（Claude / Codex など）があれば、原理的には自分で組めます。ただ、ここまで書いてきたつまずき（最初の1サイクルで全員 idle になる、承認プロンプトで止まる、自己申告を信じて全滅に気づかない）を、一つずつ踏んで直していく必要があります。私はそれを数か月かけてやりました。

役割分担でいうと、こうなります。 **herdr** （や同等のツール）が、ペインへの prompt 送信と状態の観測を担う。 **intent-cli** は、宛先のロール対応（どのワークスペースのどのペインが何の役割か）、委譲と報告の形式、モードの記録、止まりの点検、設計境界のイベント記録、といった「決めごと」を生成・検証する。intent-cli 自身は AI を起動しません。あなたの使っているエージェントが intent-cli に聞き、正規の手順で進めます。intent-cli は herdr を同梱も内包もしないので、同じ規約を満たせば別の同等ツールに置き換えられます。

自分で全部組むのも面白いと思います。一方で、この「決めごと」を毎回自分で書いて検証するのが面倒なら、そこを intent-cli に任せられます。踏むべき失敗をあらかじめ手順に織り込んでおきたい人向け、という位置づけです。

## まとめ

AIエージェントを速く回すこと自体は、もう珍しくありません。難しいのは、速く回るチームが止まったときに、それを見つけて再開させ続けることです。

今回やったのは、「誰が turn を起こすか」を作り直したことです。agmsg の monitor に頼っていた起こし方を、herdr が任意のペインを起こせる性質に置き換え、そのうえで起こす経路を、一次（完了報告）・二次（状態変化の購読）・最後の網（定期点検）の3段に冗長化しました。そして、状態が変わっただけでは完了と判定しない。依存を1つ減らしたことで土台が単純になり、いつか作りたいマルチマシン対応にも進みやすくなりました。マルチマシンはまだ将来の課題です。
